# T5: типы, классы, инварианты и операции — авторская проверка

Эта папка проверяет **45 изменённых текстовых шагов модулей 12–13** и **37 полных объясняющих программ**. В уроки не добавлены задания, самостоятельные упражнения, тесты для учащихся или видео. Существующие оценочные шаги не изменены.

Исходный снимок: `d96e5b9cffa65010c53894a9b65b1a497cb6b58a`. Исторический опубликованный пакет из 88 шагов не переписывается. Точные ID, пути и смысл изменений находятся в [changes_t5.json](../../changes_t5.json), редакторские решения — в [review_t5.json](../../review_t5.json).

## Что показывает код

- `Person`, `Make` и `Model`: тип и объект, инициализация, композиция, строки со своим временем жизни, невладеющий доступ к полям.
- `layout.cpp`, `union_size.cpp`, `bit_fields.cpp`: диапазоны и условия представления. Числа ABI не выдаются за обязательные размеры языка.
- `union_active.cpp`, `union_pointer.cpp`, `variant.cpp`: активная альтернатива, смена времени жизни, безопасный доступ к значению `variant` и отказ при неверном `get`.
- `Level` и `Distance`: определённое начальное состояние, проверки конструктора/операций, отказ без нарушения инварианта. `Distance` намеренно хранит целые неотрицательные дюймы; допустимы 0–1 000 000 футов и 0–11 остаточных дюймов.
- `Counter`: префиксный `++` возвращает ссылку на тот же объект, постфиксный — прежнее значение; максимум отклоняется без перехода к нулю.
- `CheckedArray`: изменяемая и константная ссылки, проверка границы через `std::array::at`. Это явно выбранный контракт обёртки, а не гарантия встроенного `[]`.
- Наследование: базовый доступ без копии, срезка при копировании базы, виртуальное переопределение, общий виртуальный базовый подобъект, порядок разрушения и очистка при исключении конструктора.

`cards.cpp` — законченный разбор заранее известных перестановок. В нём нет предложения ученику угадывать карту, дописывать программу или выполнять самостоятельное действие.

## Запуск

Нужны Python 3.10+ и GCC с C++17/C++20 и поддержкой UndefinedBehaviorSanitizer. Сеть, CMake и GoogleTest для этого блока не требуются.

```bash
python3 improvements/86957/theory-continuation-2026-11-23/examples/t5/verify.py
```

Чтобы сохранить более ранний протокол, новый путь задают явно:

```bash
python3 improvements/86957/theory-continuation-2026-11-23/examples/t5/verify.py --report /tmp/t5-new-run.json
```

`CXX` может задавать исполняемый файл совместимого компилятора. Команды сборки используют `-Wall -Wextra -Wpedantic -Werror -O1 -g -fsanitize=undefined -fno-sanitize-recover=all`. Временные исполняемые файлы не попадают в пакет.

## Что проверяет verify.py

Сначала скрипт сравнивает все 45 payload с неизменяемыми baseline (до создания baseline — с текущим снимком) и разрешает только изменение `block.text` типа `text`. Затем проверяет, что каждый полный листинг с `main` зарегистрирован в `cases.json`, побайтно совпадает с C++-файлом после HTML-декодирования и имеет ожидаемый результат либо явно заданную платформенную проверку. Незарегистрированный полный листинг вызывает отказ проверки.

Каждая из 37 программ собирается в обоих режимах языка и запускается с заявленным результатом. Для `distance_input.cpp` проверяются обычный ввод, ноль, максимально допустимая длина, отрицательные футы, ненормализованные дюймы, превышение предела, неверный токен и конец ввода. Размеры структуры и объединения проверяются по переносимым соотношениям, а фактический вывод сохраняется в протоколе.

`checks.cpp` — отдельная преподавательская проверка контрактов. Она проверяет типы результатов `++`, `+=` и `[]`, все существенные границы конструкторов, перенос дюймов, самодобавление, сохранение значения при ошибке, согласованность сравнений, максимальное значение счётчика, границы массива, валидность карты, площадь прямоугольника и вызов производного деструктора при обычном удалении через базовый указатель. Фрагмент вложенного тривиального `union` тоже компилируется и проверяется без чтения неактивного члена.

Пять намеренно недопустимых фрагментов в каждом стандарте должны не скомпилироваться: увеличение константного счётчика, прямой доступ к закрытому полю, запись через константный индексатор, создание самостоятельного объекта абстрактного класса и неописанное преобразование разных структур. Диагностика проверяется по относящемуся к контракту признаку, а не только по ненулевому коду компилятора.

`distance.hpp` и `counter.hpp` содержат те же определения, которые показаны в заключительных программах соответствующих последовательностей. Они нужны для граничных авторских проверок. Новые Stepik-шаги из них не создаются.

## Результат и ограничения

Текущий запуск фиксируется отдельно от старых пакетов в [validation.json](validation.json): GCC 14.2.0, Linux, C++17 и C++20; 76 успешных компиляций, 90 запусков программ, 10 ожидаемых отказов компиляции и 2 запуска граничной проверки.

Это проверка выбранных законченных иллюстраций и указанных контрактов, а не доказательство для всех состояний и не проверка всех 283 текстовых шагов курса. Windows/MSVC и macOS в этом запуске не использовались. Данные об ABI относятся только к запущенной реализации. Проверка не обращается к Stepik, прогрессу учащихся, решениям или настройкам оценивания.

## Источники

Точные ссылки по каждому шагу находятся в журнале изменений. Для языка использованы разделы закреплённого [N4659 (C++17)](https://timsong-cpp.github.io/cppwp/n4659/) и проверка отличий [N4861](https://timsong-cpp.github.io/cppwp/n4861/). [Официальный отчёт N4859](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2020/n4859.html) поясняет соответствие технического содержимого N4861 проекту DIS C++20 N4860. В частности, различие условий агрегатности для явно объявленного defaulted-конструктора описано отдельно.

[C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines) используются только как рекомендации о стиле, обычном смысле операторов и «правиле нуля», а не как нормативные требования языка.
