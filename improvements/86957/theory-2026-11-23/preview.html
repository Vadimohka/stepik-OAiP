Свойства алгоритма и границы задачи

В этом курсе сначала рассматриваются детерминированные алгоритмы: при одинаковых входных данных они выполняют одинаковые действия и получают одинаковый результат. Существуют и рандомизированные алгоритмы; наличие случайного выбора не делает описание неточным, если правила этого выбора заданы.

Для рассматриваемого алгоритма необходимо указать допустимые входные данные, смысл результата и последовательность выполнимых действий. Это первые элементы контракта — соглашения о том, что требуется на входе и что обещано на выходе.

  • Дискретность: решение описано отдельными действиями и правилами перехода между ними. Здесь используются последовательность, выбор и повторение; параллельные вычисления пока не рассматриваются.
  • Определённость: исполнитель понимает каждое действие и правило выбора следующего шага без догадок.
  • Завершение: алгоритм решения конечной задачи должен закончиться на каждом допустимом входе. Постоянно работающая программа, например сервер, может содержать такие алгоритмы, продолжая ждать новые запросы.
  • Корректность результата: завершение само по себе недостаточно — результат должен соответствовать задаче.
  • Область применимости: описание обычно подходит классу входных данных, например любой паре целых чисел в заданном диапазоне.

Для деления дробей ненулевой знаменатель каждой дроби и ненулевой делитель — условия допустимого входа. Для поиска в пустой последовательности допустимым результатом может быть «не найдено». Отсутствие решения тоже может быть корректным результатом, если так определена задача.

Позже эти условия станут контрактами функций, а в модуле алгоритмов к корректности добавится оценка затрат.

Один алгоритм — разные способы записи

Алгоритм можно описать словами, формулами, псевдокодом, блок-схемой или программой. Форма записи меняется, но допустимые входные данные и смысл результата должны сохраняться.

Разобранный пример: максимум двух чисел a и b. Если a ≥ b, результат равен a; иначе результат равен b. При равенстве подходит любое из них: значения совпадают.

вход: числа a и b
если a >= b:
    результат = a
иначе:
    результат = b
выход: результат

Это псевдокод, а не готовый исходник C++: в нём важна логика, а не правила объявления переменных и расстановки скобок. Блок-схема выражает тот же выбор ромбом с двумя выходами. В программе C++ выбор будет записан конструкцией if; типы определят, какие числа можно передать.

Словесное описание удобно для объяснения смысла, псевдокод — для обсуждения шагов, схема — для просмотра ветвлений. Конкретный язык программирования нужен для исполнения. Подробность выбирается по читателю: фраза «отсортировать» может быть одним шагом внешнего алгоритма, хотя внутри неё много операций.

Далее блок-схемы показывают порядок действий, а функции позволяют дать такой последовательности имя и использовать её как одну операцию.

Функция как именованная операция

Функция объединяет действия под одним именем. Определение описывает эти действия, а вызов запускает их для конкретных аргументов. Функция может вычислять результат, выполнять действие вроде вывода или сочетать оба варианта.

Например, операция «перевести метры в сантиметры» получает длину в метрах и возвращает длину в сантиметрах. Внутри выполняется умножение на 100. Вызывающий код может пользоваться этой операцией, зная единицы измерения и допустимые значения, без повторения формулы.

Имя помогает читать программу, но само по себе не гарантирует корректность. У функции есть контракт: смысл аргументов, ограничения, результат и возможные побочные эффекты. Для числовых типов C++ дополнительно важны диапазон и точность.

Зачем выделять функции

Функция даёт части алгоритма смысловую границу. Вычисление стоимости заказа можно отделить от чтения данных и вывода чека: у этих действий разные обязанности и причины изменения.

Если одна формула используется в нескольких местах, её определение в одной функции уменьшает риск исправить только одну копию. Но повторение — не обязательное условие: отдельная функция полезна и для единственного сложного действия, если её имя и контракт упрощают чтение.

Разбор: функция расчёта получает цену и количество, возвращает стоимость и ничего не печатает. Функция вывода получает готовую стоимость. Изменение оформления чека тогда не меняет арифметику. Если функция расчёта начнёт неожиданно записывать файл, изменится и её контракт — это следует явно отразить в интерфейсе.

Такое разделение помогает независимо рассуждать о частях программы и проверять их. Функции не делают программу автоматически быстрой, переносимой или безошибочной: эти свойства зависят от выбранных операций, контрактов и реализации.

Полный пример с функцией

Следующая программа не требует ввода. Она продолжает разобранный перевод единиц и выводит 250.

#include <iostream>

double meters_to_centimeters(double meters) {
    return meters * 100.0;
}

int main() {
    const double length_m = 2.5;
    const double length_cm = meters_to_centimeters(length_m);
    std::cout << length_cm << '\n';
}

double обозначает тип с плавающей точкой; const запрещает изменение значения через это имя. При вызове значение length_m передаётся параметру meters. Выражение после return вычисляется и становится результатом вызова. Затем std::cout выводит этот результат и перевод строки.

main — главная функция обычной программы C++. std::cout — объект стандартного потока вывода, а << здесь обозначает вставку данных в поток. Это разные сущности, хотя все они участвуют в одном выражении.

Сейчас достаточно проследить путь исходное значение → вызов → возвращённое значение → вывод. Подробные правила типов появятся в модуле 4, а параметры, возвращаемые значения и контракты — в модуле 7.

Программа, данные и выполнение

Алгоритм задаёт способ решения задачи. Программа выражает действия и данные средствами конкретного языка; реализация языка обеспечивает их выполнение. Полезная учебная формула «алгоритм + данные» подчёркивает, что без смысла данных нельзя оценить правильность действий.

Числа с плавающей точкой и округление

Конечное число бит не позволяет хранить все вещественные числа. Значение типа double — одно из представимых чисел выбранного формата. Например, десятичная дробь 0,1 имеет бесконечную двоичную запись и в обычном двоичном формате округляется.

Распространённые платформы используют IEEE 754 binary32 для float и binary64 для double. Это не универсальное требование C++. Свойства реализации доступны через std::numeric_limits, включая digits, radix и is_iec559.

Нормальное конечное число binary64 имеет вид (−1)S · 1.M · 2E. Хранятся знак, 11-битное поле порядка и 52 бита дробной части. Ведущая единица нормального числа подразумевается; порядок восстанавливается вычитанием смещения 1023. Специальные значения полей обозначают нули, субнормальные числа, бесконечности и NaN, поэтому формулу нормального числа нельзя применять к любому шаблону.

Разобранная модель округления

Возьмём учебный двоичный формат только с двумя битами после ведущей единицы. Это не тип C++ и не полный формат IEEE 754. Число 7,25 записывается как 111.01₂ = 1.1101₂ · 2². Соседние представимые значения здесь — 1.11₂ · 2² = 7 и 1.00₂ · 2³ = 8. Расстояния равны 0,25 и 0,75, поэтому округление к ближайшему даёт 7. При обратном преобразовании получится 7, а не исходные 7,25.

Если расстояния равны, режим «к ближайшему, при равенстве — к чётному» выбирает значение с нулевым младшим сохраняемым битом. Существуют и другие режимы округления; пример предполагает именно этот.

Что следует для программ

  • Изменение порядка сложений может изменить результат из-за промежуточных округлений.
  • Вычитание близких приближённых чисел может увеличить относительную ошибку.
  • Допуск при сравнении выбирается по смыслу и масштабу задачи; одной универсальной константы для всех вычислений нет.
  • Точно представимые ожидаемые значения иногда корректно сравнивать через ==. Запрета на любое равенство вещественных чисел нет.
  • При поддержке NaN сравнение NaN с самим собой через == ложно; проверку выполняет std::isnan из <cmath>.

Первый запуск: от исходного файла до результата

Цель шага: проследить превращение исходного файла в программу с предсказуемым выводом. В примере файл main.cpp:

#include <iostream>

int main() {
    std::cout << "Hello, C++!\n";
}

#include <iostream> подключает объявления потоков. main — главная функция обычной программы. std::cout выводит текст, а \n обозначает перевод строки. Достижение конца main эквивалентно return 0; — успешному завершению.

GCC или Clang: Linux и macOS

Команды выполняются из каталога с main.cpp. Если установлен GCC:

g++ -std=c++20 -Wall -Wextra -Wpedantic -g main.cpp -o hello
./hello

Для Clang замените g++ на clang++. Первая команда собирает программу, вторая запускает результат. Запускайте вторую команду после успешной сборки: при ошибке на диске может остаться исполняемый файл от предыдущего запуска.

MSVC: Windows

В окружении установленного MSVC используется Developer PowerShell for Visual Studio в каталоге проекта:

cl /std:c++20 /EHsc /W4 /Zi main.cpp /Fe:hello.exe
.\hello.exe

Если работаете в IDE, создайте консольный C++-проект, добавьте этот исходный файл, выберите C++20 и выполните сборку и запуск. На Windows с GCC можно собрать hello.exe командой g++ -std=c++20 -Wall -Wextra -Wpedantic -g main.cpp -o hello.exe и запустить .\hello.exe в PowerShell.

Ожидаемый вывод во всех вариантах:

Hello, C++!

Флаги -Wall -Wextra -Wpedantic включают полезные диагностики GCC/Clang; /W4 — высокий уровень предупреждений MSVC. -g и /Zi добавляют отладочную информацию. Наличие предупреждений проверяйте даже тогда, когда сборка завершилась.

Разбор результата

После успешной сборки вывод равен Hello, C++! и переводу строки. Редактирование приветствия меняет только исходный файл; новый текст появится после новой успешной сборки. Точка останова перед выводом показывает, что программа уже запущена, но операция вывода ещё не выполнена.

Как читать первые ошибки

Цель шага: найти причину диагностики и проверить исправление. Следующая программа намеренно ошибочна и не должна успешно компилироваться:

#include <iostream>

int main() {

Компилятор сообщает, что имя cout не объявлено или не найдено. Точная формулировка зависит от GCC, Clang или MSVC и их версии. Имя объекта потока — std::cout: замена cout на std::cout устраняет именно эту ошибку. Заголовок подключён, но неквалифицированное имя cout в этой области не находится.

Настройка среды выполнения

Ниже перечислены типичные обязанности кода запуска и загрузчика в рассматриваемой ELF/Linux-среде. Набор действий и их распределение зависят от платформы; это не универсальный список функций runtime, обязательный для любой программы C++:

  1. Выполнить необходимые релокации (если они не обрабатываются загрузчиком или компоновщиком)
  2. Инициализация глобальной и статической памяти
  3. Подготовить argc и argv согласно требованиям main: argc неотрицателен, argv указывает на массив, а argv[argc] — нулевой указатель

Инициализация глобальной и статической памяти разбита на два отдельных этапа, которые заслуживают дополнительной информации.

Во-первых, должна быть обеспечена статическая инициализация объектов со статическим временем хранения: постоянная инициализация, когда она применима, либо нулевая инициализация. Это не определяется только наличием знака = в объявлении: возможны и другие формы инициализатора. В типичном ELF-образе данные с начальным нулевым содержимым размещаются в .bss; обнуление соответствующей памяти обеспечивает загрузчик или код запуска. Объём памяти при этом не становится нулевым — нулевым становится её содержимое.

Во-вторых, для объектов C++ может понадобиться динамическая инициализация. Она часто выполняется до main, однако стандарт допускает и отложенную инициализацию в оговорённых случаях. В реализациях на основе ELF для вызова функций инициализации могут использоваться .init, .init_array и другие механизмы. GCC также предоставляет расширение __attribute__((constructor)), помечающее функцию для вызова до main; это не стандартный синтаксис C++.

Эти дополнительные шаги инициализации среды выполнения выполняются для многих программ (но не для всех):

  1. Инициализация кучи
  2. Инициализация stdio (т.е. stdin, stdout, stderr)
  3. Инициализация поддержки исключений (при использовании C++)
  4. Регистрация деструкторов и другие функции очистки, которые будут выполняться при выходе из программы (используя atexit и __cxa_atexit)
  5. Подготовка переменных среды

На практике грань между обязанностями _start и инициализацией среды выполнения языка C может быть нечеткой. Некоторые реализации _start обрабатывают части настройки среды выполнения напрямую, такие как установка содержимого раздела .bss равным 0 и вызов глобальных конструкторов. Другие реализации обрабатывают эти задачи как часть процедур настройки среды выполнения языка C.

Ассемблерные исходники, которые могут встречаться во время этой части процесса запуска, - это crtbegin.s, crtend.s, crti.s и crtn.s. Компиляторы часто поставляют предварительно скомпилированные объектные файлы для поддерживаемых архитектур. Эти файлы связаны с вызовом глобальных конструкторов и деструкторов. Когда файлы не используются, эквивалентная функциональность часто реализуется на языке C и вызывается во время инициализации среды выполнения.

Цель шага: различать рабочие файлы, подготовленные изменения и сохранённую версию. Git — распределённая система контроля версий: обычный локальный репозиторий хранит историю проекта, поэтому коммиты и просмотр истории доступны без подключения к серверу.

Git и GitHub — разные вещи. Git ведёт историю локально; GitHub и другие серверы помогают хранить общую копию и обсуждать изменения. Локальный коммит ещё не отправлен на сервер: для отправки служит git push.

Коммит описывает сохранённое состояние проекта и ссылается на предшествующие коммиты. Git хранит объекты содержимого, деревья каталогов и коммиты; их идентификаторы вычисляются из содержимого. В представлении истории это позволяет связать конкретную версию файла с конкретным изменением.

Логическая модель — снимки состояния. Внутреннее хранение может использовать сжатие и дельты похожих объектов, но разработчик работает с версиями, а не вручную собирает цепочку текстовых исправлений.

Разбор: если в коммите изменена строка вывода, новый коммит имеет другой идентификатор. Старый коммит продолжает обозначать прежний снимок, пока остаётся доступным в репозитории. Имя ветки может передвинуться на новый коммит; идентификатор старого коммита от этого не меняется.

Хеш помогает обнаруживать несоответствие содержимого идентификатору, но сам по себе не подтверждает личность автора. Проверка подписи и доверия к ключу — отдельный механизм. История исходников также не восстанавливает никогда не сохранённые изменения и не заменяет резервное копирование всех рабочих данных.

Ветки, общий репозиторий и обсуждение изменений

Ветка Git — перемещаемая ссылка на коммит. Она даёт отдельной линии изменений имя. В одном рабочем дереве переключение ветки обычно меняет видимые файлы; ветка не является отдельной физической папкой.

Разбор: main и explain-output сначала указывают на один коммит. После нового коммита во второй ветке она продвигается, а main сохраняет прежнюю позицию. При объединении веток Git пытается совместить изменения. Если они несовместимы автоматически, возникает конфликт, который требует осмысленного разрешения.

Удалённый репозиторий хранит другую доступную копию истории. fetch получает сведения и объекты из него, push передаёт локальные изменения согласно правилам сервера. Сам по себе локальный коммит ещё не опубликован.

GitHub и похожие сервисы дополняют Git обсуждениями, pull request и автоматическими проверками. Pull request — запрос на рассмотрение и объединение изменений в сервисе, а не отдельный вид коммита Git. Ни наличие ветки, ни успешное слияние автоматически не доказывают корректность C++.

Эта модель останется полезной при обновлении функций: история отвечает «что изменилось», сборка — «собирается ли версия», а проверка результата — «соответствует ли она контракту».

Разобранная история двух версий

Пусть в репозитории уже есть полный main.cpp, выводящий Hello, C++!. В этом объяснении команды иллюстрируют действия автора; создавать отдельный учебный репозиторий для чтения не требуется.

git add main.cpp
git diff --staged
git commit -m "Add greeting"

add поместил текущее содержимое в индекс. diff --staged показал будущую разницу с последним коммитом. commit сохранил подготовленное состояние. Имя и адрес автора должны быть настроены заранее; это метаданные коммита, а не вход на GitHub.

Далее автор заменил приветствие на Hello, reader!, успешно собрал программу и получил именно этот вывод. Следующая последовательность сохраняет вторую версию:

git diff
git add main.cpp
git diff --staged
git commit -m "Clarify greeting"
git show HEAD~1:main.cpp

Первый diff показывает рабочие изменения относительно индекса; после add версия для коммита уже выбрана. Последняя команда показывает файл из предыдущего коммита этой простой линейной истории и не заменяет рабочий файл.

Собираем первую программу с CMake

Разберём полное описание сборки одной программы: выбранный стандарт, команды и расположение результата. Нужны три отдельных инструмента: CMake, компилятор C++ и выбранная система сборки, например Make, Ninja или MSBuild. Установка одного CMake не устанавливает автоматически все остальные компоненты.

Установите CMake версии 3.22 или новее по официальной инструкции или через пакетный менеджер своей ОС. Команда cmake --version показывает установленную версию.

В каталоге примера находятся два файла. Содержимое main.cpp:

#include <iostream>

int main() {
    std::cout << "Hello C++\n";
}

Содержимое CMakeLists.txt:

cmake_minimum_required(VERSION 3.22)
project(FirstProgram LANGUAGES CXX)

set(SOURCES main.cpp)
add_executable(hello ${SOURCES})
set_target_properties(hello PROPERTIES
    CXX_STANDARD 20
    CXX_STANDARD_REQUIRED YES
    CXX_EXTENSIONS NO
)

if(MSVC)
    target_compile_options(hello PRIVATE /W4 /permissive-)
elseif(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
    target_compile_options(hello PRIVATE -Wall -Wextra -Wpedantic)
endif()
  • add_executable создаёт цель сборки hello. Здесь переменная SOURCES содержит имя одного исходного файла, а ${SOURCES} подставляет её значение.
  • Свойства цели задают C++20, запрещают незаметно понижать запрошенный стандарт и отключают запрос расширенного диалекта компилятора. Поддержка отдельных возможностей языка и библиотеки всё равно зависит от установленного компилятора.
  • Предупреждения задаются для конкретной цели через target_compile_options. Флаги GCC/Clang и MSVC различаются; при другом компиляторе нужно посмотреть его документацию. Предупреждения помогают обнаруживать ошибки, но не доказывают правильность программы.

При использовании Make или Ninja выполните из папки с CMakeLists.txt:

cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build

Первая команда настраивает проект и сохраняет служебные файлы в отдельную папку build. Вторая запускает компиляцию и компоновку. Debug — конфигурация, удобная для отладки. Для генератора Visual Studio конфигурацию выбирают на этапе сборки:

cmake -S . -B build
cmake --build build --config Debug

В Linux/macOS при Make или Ninja программа обычно запускается командой ./build/hello. В PowerShell при генераторе Visual Studio — .\build\Debug\hello.exe. Расположение зависит от генератора и настроек. Ожидаемый вывод:

Hello C++

Разбор изменения: если автор меняет приветствие в main.cpp, повторная сборка обновляет программу. Если удалена обязательная точка с запятой, компиляция завершается ошибкой; оставшийся старый исполняемый файл не содержит новое состояние исходника. После исправления и успешной сборки новый вывод соответствует исправленному тексту.

Один проект в терминале и в IDE

IDE позволяет запускать те же инструменты сборки из своего интерфейса. IDE открывает каталог с CMakeLists.txt и связывает его с выбранным компилятором, конфигурацией Debug и целью hello. Названия кнопок могут отличаться; исходники и описание сборки остаются теми же.

Функция: входные данные, результат и контракт

Предварительные знания: значения, условия, циклы и указатели и ссылки. Здесь они объединяются в интерфейс операции.

Цель: по объявлению и описанию функции понять, какие данные ей передать и какой результат получить.

Функция даёт имя законченной операции. Например, sum(a, b) вычисляет сумму двух чисел. Это позволяет использовать одну реализацию в разных местах программы и проверять её отдельно.

В записи int sum(int a, int b) первое int — тип результата, sum — имя, а a и b — параметры. В вызове sum(10, 32) числа 10 и 32 — аргументы: значения, передаваемые параметрам.

Сначала договоримся о поведении

  • Предусловие: оба аргумента — целые числа от −1000 до 1000 включительно.
  • Результат: их математическая сумма.
  • Побочные эффекты: функция не читает ввод, ничего не печатает и не меняет переменные вызывающего кода.

Такое описание называют контрактом. Здесь это понятное человеку соглашение, а не специальный синтаксис языка. Оно ограничивает входные данные так, чтобы сумма помещалась в int. Проверку ввода выполняет main.

#include <iostream>

// Contract: -1000 <= a, b <= 1000. Returns their sum.
int sum(int a, int b) {
    return a + b;
}

int main() {
    int a = 0;
    int b = 0;
    if (!(std::cin >> a >> b) || a < -1000 || a > 1000 ||
        b < -1000 || b > 1000) {
        std::cerr << "input error\n";
        return 1;
    }
    const int total = sum(a, b);
    std::cout << total << '\n';
    return 0;
}

Ввод: два целых числа, например 10 32. Вывод: 42 и перевод строки. При неверном вводе программа пишет input error в поток ошибок и завершается с кодом 1.

При вызове sum(a, b) управление переходит в функцию. Оператор return a + b; вычисляет результат, завершает этот вызов и передаёт значение в total. Затем main выводит его. Возврат значения и печать — разные действия: результат можно сохранить, сравнить или передать следующей функции.

Разбор границ и другого результата

Для входов 0 0, -1000 1000 и 1000 1000 суммы равны 0, 0 и 2000. Все три случая входят в контракт. Функция разности с теми же параметрами возвращала бы a - b, лежащее от −2000 до 2000; проверки ввода по-прежнему относятся к main. Печать разности вместо возврата создала бы другой интерфейс: значение нельзя было бы сразу использовать в следующем вычислении.

Контракт связывает математическую операцию с допустимыми значениями C++. Понятия объекта и времени жизни из темы указателей далее объяснят, когда функция возвращает самостоятельное значение, а когда обращается к уже существующему объекту. Позже функция станет и частью интерфейса класса: контракт операции будет дополнять инвариант его состояния.

Объявление, определение и вызов

Цель: расположить код так, чтобы компилятор знал интерфейс функции до её использования.

Объявление сообщает имя функции, тип результата и типы параметров: int minimum(int left, int right);. Точка с запятой завершает объявление; тела здесь нет. Определение содержит тело в фигурных скобках и одновременно является объявлением.

В этой полной программе перед main стоит объявление, а реализация находится ниже. Контракт minimum: принять любые два значения типа int и вернуть меньшее; при равенстве вернуть это общее значение. Функция не выполняет арифметику, способную переполнить тип.

#include <iostream>

int minimum(int left, int right);

int main() {
    int a = 0;
    int b = 0;
    if (!(std::cin >> a >> b)) {
        std::cerr << "input error\n";
        return 1;
    }
    std::cout << minimum(a, b) << '\n';
    return 0;
}

int minimum(int left, int right) {
    if (left < right) {
        return left;
    }
    return right;
}

Ввод: два представимых в int целых числа. Для 7 -2 вывод равен -2; для 4 4 — 4. В самом вводе используйте обычный знак минуса -.

Что проверяет компилятор

На месте вызова должно быть видно подходящее объявление. Благодаря ему компилятор проверяет аргументы и знает тип выражения minimum(a, b). Объявления и определение должны согласовываться по типам. Имена параметров в объявлении можно опустить: int minimum(int, int);. Имена в определении нужны, чтобы обращаться к параметрам в теле.

Несколько согласованных объявлений допустимы. В одной единице трансляции допускается не более одного определения этой функции. Единица трансляции — исходный файл после обработки его #include и других директив. Для вызываемой обычной функции определение должно существовать в программе или подключённой библиотеке; одно объявление не создаёт реализацию. Правила нескольких определений в разных единицах трансляции рассмотрим для inline в следующем шаге.

Имена и чтение чужого кода

  • Выбирайте имя по действию или результату: minimum, count_positive. Имя не может начинаться с цифры.
  • Не придумывайте имена с двойным подчёркиванием или с подчёркиванием и следующей заглавной буквой: они зарезервированы. Имена, начинающиеся с подчёркивания, зарезервированы и в глобальном пространстве имён: там нельзя вводить свою _func.
  • В C++14 и новее допустимо объявление auto calculate(); с выводимым типом результата. До использования, которому нужен этот тип, компилятор должен увидеть определение. В первых собственных функциях пишите тип явно.
  • Функции одного имени с различными списками типов параметров могут образовывать перегрузки, например варианты с двумя и тремя int. Различия только в типе результата недостаточно.

Разбор двух расположений кода

Если определение minimum находится перед main, отдельное объявление не требуется: определение уже сообщает интерфейс. Если реализация находится после main, перед вызовом нужно объявление. При его отсутствии компилятор не знает имя функции; это ошибка компиляции. Иная ситуация — объявление видно, но определение не передано компоновщику: тогда возникает ошибка сборки на этапе компоновки.

В многофайловом примере общий заголовок будет сообщать один интерфейс и вызывающему коду, и файлу реализации. Согласованность типов проверяется при компиляции каждого из них.

constexpr, inline и static: разные свойства функции

Цель: различать возможность вычисления константы, правила определений и видимость реализации. Для обычной функции ни одно из этих ключевых слов не обязательно.

constexpr: функция пригодна и для константных вычислений

constexpr разрешает вычислить подходящий вызов при вычислении константного выражения. Оно не означает, что каждый вызов обязательно выполнится во время компиляции: результат может зависеть от введённых пользователем данных.

Пример совместим с C++17 и C++20. Контракт: основание от −10 до 10, целая степень от 0 до 18. В этих пределах промежуточные произведения помещаются в long long. По соглашению интерфейса нулевая степень даёт 1, включая power(0, 0); это явно выбранное правило данной функции.

#include <iostream>

// Contract: -10 <= base <= 10, 0 <= exponent <= 18.
// This interface defines base^0 as 1, including 0^0.
constexpr long long power(long long base, int exponent) {
    long long result = 1;
    for (int i = 0; i < exponent; ++i) {
        result *= base;
    }
    return result;
}

static_assert(power(2, 10) == 1024);
static_assert(power(0, 0) == 1);

int main() {
    long long base = 0;
    int exponent = 0;
    if (!(std::cin >> base >> exponent) || base < -10 || base > 10 ||
        exponent < 0 || exponent > 18) {
        std::cerr << "input error\n";
        return 1;
    }
    std::cout << power(base, exponent) << '\n';
    return 0;
}

static_assert проверяет константное выражение во время компиляции. Вызов в main принимает данные из ввода: для 2 10 он печатает 1024, для -2 3 — -8. Отрицательная степень не входит в контракт: её нельзя незаметно трактовать как нулевую.

inline: правило размещения определения

inline позволяет при соблюдении правила одного определения разместить согласованные определения одной функции в нескольких единицах трансляции — например, через общий заголовочный файл. Это не разрешение написать два определения в одном исходном файле. inline также не гарантирует подстановку тела на месте вызова: решение об оптимизации принимает компилятор. Функция с constexpr неявно является inline.

static у свободной функции

На уровне пространства имён static задаёт внутреннее связывание: имя функции относится к этой единице трансляции. Поэтому в разных .cpp могут существовать разные такие функции с одним именем. Это другое применение static, чем у локальной переменной, сохраняющей состояние между вызовами.

Что пока достаточно узнавать

noexcept в объявлении сообщает, что исключение не должно выходить из функции. Нарушение этого обещания приводит к завершению через std::terminate, а не к автоматическому исправлению ошибки. Сначала мы освоим обычные функции; условные спецификации noexcept, шаблоны и свойства методов классов понадобятся в соответствующих разделах.

Разбор границ контракта

Для 0 0, 0 5, -2 4 и 10 18 результаты равны 1, 0, 16 и 1000000000000000000. Дополнительные множители за пределами контракта могут переполнить тип. Отрицательная степень требует другого математического результата и обычно другого типа. Поэтому расширение диапазона требует анализа реализации, а не только удаления проверки.

constexpr, inline и static отвечают на разные вопросы: пригодность для константного вычисления, допустимое размещение определений и связывание имени. Эти свойства не заменяют контракт функции.

Возврат значения и время жизни результата

Цель: вернуть результат вычисления так, чтобы вызывающий код мог безопасно использовать его после завершения функции.

Тип перед именем функции описывает результат вызова. Для обычного вычисления удобно вернуть значение. В примере square принимает число от −1000 до 1000 и возвращает его квадрат как long long.

#include <iostream>

// Contract: -1000 <= value <= 1000. Returns value squared.
long long square(int value) {
    const long long result = 1LL * value * value;
    return result;
}

int main() {
    int value = 0;
    if (!(std::cin >> value) || value < -1000 || value > 1000) {
        std::cerr << "input error\n";
        return 1;
    }
    const long long answer = square(value);
    std::cout << answer << '\n';
    return 0;
}

Ввод: одно целое число из указанного диапазона. Для -12 программа печатает 144. Множитель 1LL переводит умножение в тип long long до вычисления произведения: один лишь широкий тип переменной результата не расширяет уже выполненное умножение.

Локальный объект result существует во время выполнения функции. При return result; значение результата вызова формируется до уничтожения локального объекта. Переменная answer в main получает самостоятельное значение; возвращаться к уничтоженному объекту ей не нужно.

Почему нельзя вернуть ссылку на этот result

Ссылка обозначает уже существующий объект; это не отдельная копия его значения. Если заменить тип результата square на const long long&, та же строка return result; будет возвращать ссылку на локальный объект. При выходе из функции его время жизни закончится. Читать значение через такую висячую ссылку нельзя. const не продлевает время жизни локального объекта, на который возвращают ссылку. Та же опасность возникает при возврате его адреса.

Возврат ссылки бывает полезен, когда объект принадлежит вызывающему коду или живёт заведомо дольше использования результата. Тогда срок жизни объекта — часть контракта. Для первого решения числовой задачи выбирайте возврат значения. Возврат контейнера по значению также допустим: современные правила C++ позволяют избежать лишнего копирования или переместить результат; не следует ради предполагаемой экономии возвращать ссылку на локальный контейнер.

return завершает текущий вызов

После выполненного return остальные операторы тела в этом вызове не выполняются. У обычной функции с результатом каждая возможная ветвь нормального завершения должна вернуть значение. Достижение конца такой функции без возврата, кроме особого правила для main, приводит к неопределённому поведению. Функция с типом void может дойти до конца или выполнить return; без значения.

Разбор двух способов возврата

Запись return 1LL * value * value; даёт то же самостоятельное значение, что и возврат через локальную переменную. Для 0, −1000 и 1000 ответы равны 0, 1000000 и 1000000. В строке return result; безопасность определяется объявленным типом результата: long long возвращает значение, а const long long& в этом примере оставил бы ссылку на уничтоженный объект. Похожее написание выражений не означает одинаковое время жизни результата.

Декомпозиция: одна операция — одна понятная функция

Цель: разделить задачу на вычисления и взаимодействие с пользователем, затем собрать решение из вызовов.

Пусть нужно найти максимум трёх целых чисел. Выделим maximum_of_two, возвращающую большее из двух значений, и используем её в maximum_of_three. При равенстве можно вернуть любой из равных аргументов: результат один и тот же. Обе функции работают с любыми значениями int, не изменяют аргументы и не обращаются к потокам.

#include <iostream>

int maximum_of_two(int a, int b) {
    if (a > b) {
        return a;
    }
    return b;
}

int maximum_of_three(int a, int b, int c) {
    return maximum_of_two(maximum_of_two(a, b), c);
}

int main() {
    int a = 0;
    int b = 0;
    int c = 0;
    if (!(std::cin >> a >> b >> c)) {
        std::cerr << "input error\n";
        return 1;
    }
    std::cout << maximum_of_three(a, b, c) << '\n';
    return 0;
}

Ввод: три целых числа, представимых в int. Для -7 -2 -9 вывод равен -2; для 4 4 1 — 4.

Внутренний вызов maximum_of_two(a, b) даёт одно число. Внешний сравнивает его с c. Так результат одной функции становится аргументом другой. Из-за return в первой ветви maximum_of_two отдельный else не обязателен: если первый возврат не выполнен, функция возвращает b.

Граница ответственности

main читает вход, проверяет успешность чтения и печатает ответ. Вычисляющие функции получают уже готовые значения. Благодаря этому их можно вызвать из другой программы или проверить на наборе значений без имитации диалога с консолью. Перенос std::cin внутрь maximum_of_two сделал бы повторный вызов неожиданно зависимым от нового ввода.

return 0; в main сообщает среде об успешном завершении. Это не математическое доказательство правильности ответа. В наших примерах ошибка чтения приводит к сообщению в std::cerr и коду 1; вычисление вызывается только после проверки ввода.

Разбор композиции и ошибочного алгоритма

Для 1 9 3 максимум равен 9. Реализация, ошибочно вычисляющая минимум, дала бы 1: этот вход различает два поведения. Случаи с максимумом в начале и конце, отрицательными и одинаковыми числами проверяют другие ветви. Максимум четырёх значений выражается как maximum_of_two(maximum_of_two(a, b), maximum_of_two(c, d)). Вложенные вызовы только вычисляют значения, поэтому их взаимный порядок не меняет ответ.

Отдельная функция полезна, когда у неё есть ясное назначение и небольшой интерфейс. Та же декомпозиция сохраняется при появлении классов: часть операций станет методами, а самостоятельные вычисления смогут остаться свободными функциями.

Область видимости: передавайте данные явно

Цель: отличать локальные переменные разных функций и передавать нужное значение через параметр.

Имя, объявленное внутри main, не становится автоматически доступным в теле другой функции. Для передачи данных используйте параметры, а для результата — return.

#include <iostream>

// Contract: -1000 <= value <= 1000. Returns twice the value.
int doubled(int value) {
    const int result = 2 * value;
    return result;
}

int main() {
    int value = 0;
    if (!(std::cin >> value) || value < -1000 || value > 1000) {
        std::cerr << "input error\n";
        return 1;
    }
    const int result = doubled(value);
    std::cout << value << ' ' << result << '\n';
    return 0;
}

Контракт: doubled получает целое от −1000 до 1000, возвращает удвоенное значение и не меняет переменные вызывающего кода. Для ввода 7 программа выводит 7 14.

Здесь есть разные объекты с одинаковыми именами. value в main содержит исходный ввод; параметр value принадлежит вызову doubled. Точно так же result в теле функции и result в main — две разные переменные. Совпадение имён не создаёт между ними общую память.

Как читать вложенные блоки

Локальное имя доступно после объявления до конца соответствующей области видимости, включая вложенные блоки, если его не скрыло другое объявление. Если во внутреннем блоке заново объявить переменную с тем же именем, это будет отдельный объект: внутреннее имя временно скрывает внешнее. Для понятного учебного кода лучше выбирать различающиеся имена, когда оба значения важны.

Обычную именованную свободную функцию нельзя определить внутри тела другой функции. В наших примерах определения располагаются на уровне пространства имён, а вызовы — внутри main или другой функции.

Нужны ли глобальные переменные?

Общую константу можно объявить на уровне пространства имён перед функциями, которым она нужна. Тогда имя доступно им, если не скрыто. Однако изменяемая глобальная переменная создаёт неявную зависимость: результат вызова может зависеть от того, кто раньше изменил общее состояние. Параметр делает входные данные видимыми в месте вызова и облегчает проверку.

Область видимости имени в одном исходном файле не означает его автоматическую доступность во всех файлах проекта. Для нескольких файлов нужны подходящие объявления и правила связывания — они рассматриваются далее.

Разбор имён и передачи значения

Переименование параметра value в number меняет обращения только в теле doubled. Имя value в main остаётся прежним: аргумент передаёт значение, а не своё имя. Локальное имя другой функции из main недоступно; нужный результат выходит через интерфейс функции. Это позволяет читать каждую функцию отдельно, зная её параметры и результат.

Параметры по значению и аргументы по умолчанию

Цель: читать вызов функции с пропущенным последним аргументом и размещать значение по умолчанию в одном месте.

Параметр типа int получает собственное значение. Присваивание такому параметру внутри функции само по себе не меняет переменную вызывающего кода. Поэтому небольшие входные числа удобно передавать по значению.

У scaled два параметра: число и множитель. Если второй аргумент не указан, используем 3. Контракт: оба значения находятся от −1000 до 1000; функция возвращает произведение как long long и ничего не печатает.

#include <iostream>

// Contract: -1000 <= value, factor <= 1000. Returns their product.
long long scaled(int value, int factor = 3);

int main() {
    int value = 0;
    int factor = 0;
    if (!(std::cin >> value >> factor) || value < -1000 || value > 1000 ||
        factor < -1000 || factor > 1000) {
        std::cerr << "input error\n";
        return 1;
    }
    std::cout << scaled(value) << ' ' << scaled(value, factor) << '\n';
    return 0;
}

long long scaled(int value, int factor) {
    return 1LL * value * factor;
}

Ввод: число и множитель. Для 4 5 вывод — 12 20: первый вызов использует множитель 3, второй — явно переданный 5. Для -4 0 вывод — -12 0.

Где пишется значение по умолчанию

Значение должно быть видно в объявлении на месте вызова. Поэтому здесь оно задано в объявлении перед main; в определении ниже его не повторяют. Определение тоже является объявлением: если оно стоит до всех вызовов и отдельного объявления нет, значение можно записать прямо там.

Повторно задавать аргумент по умолчанию в той же области видимости нельзя, даже если повторить то же число. В первом объявлении обычной функции после параметра с умолчанием все следующие параметры тоже должны иметь умолчания. Поэтому void f(int a = 1, int b); — неправильное первое объявление.

Пропускают последние аргументы. Запись scaled(4) допустима; оставить «пустое место» перед вторым аргументом нельзя. Значение по умолчанию не создаёт вторую функцию и не меняет количество параметров определения.

Разбор изменения умолчания

В варианте объявления long long scaled(int value, int factor = 10); вход 4 5 дал бы 40 20. Явный аргумент 5 сохраняет своё значение, а пропущенный берётся из видимого объявления. Присваивание параметру factor внутри тела влияет лишь на текущий вызов: оно не меняет переменную в main и не переписывает правило будущего вызова.

Передача по значению и изменяемой ссылке

Цель: выбрать интерфейс по тому, должна ли функция менять объект вызывающего кода.

Параметр int value содержит отдельное значение. Параметр int& value — ссылка на уже существующий изменяемый объект. Присваивание через такую ссылку меняет этот объект.

#include <iostream>

// Both functions require -1000 <= value <= 1000.
int incremented(int value) {
    value += 1;
    return value;
}

void increment(int& value) {
    value += 1;
}

int main() {
    int value = 0;
    if (!(std::cin >> value) || value < -1000 || value > 1000) {
        std::cerr << "input error\n";
        return 1;
    }
    const int next = incremented(value);
    std::cout << value << ' ' << next << '\n';
    increment(value);
    std::cout << value << '\n';
    return 0;
}

Контракт обеих функций: исходное число от −1000 до 1000. incremented возвращает число на единицу больше и не меняет аргумент; increment изменяет сам аргумент и имеет тип результата void.

Для ввода 5 программа выводит две строки:

5 6
6

После первого вызова исходный value равен 5, а next равен 6. Во втором вызове параметр-ссылка обращается к объекту value из main; теперь он становится равен 6. У void-функции результатом действия служит изменение состояния, отдельного числового значения вызов не даёт.

Что можно передать

  • incremented(5) допустим: аргументом может быть значение выражения.
  • Если объявлено const int fixed = 5;, вызов incremented(fixed) допустим: копируется значение.
  • Для increment нужен изменяемый объект подходящего типа. Вызовы increment(5) и increment(fixed) недопустимы: обычная изменяемая ссылка int& не связывается с такими аргументами.

Если задача состоит в вычислении одного нового значения, возврат результата часто делает код понятнее. Изменяемая ссылка уместна, когда изменение переданного объекта — явная цель операции, например очистка контейнера. Для чтения большого объекта без копии используем ссылку на const в следующем шаге.

Оговорка о значении: копия указателя всё ещё может указывать на общие данные. Передача указателя по значению не копирует массив и не запрещает менять элементы через этот указатель. Случай встроенных массивов разберём отдельно.

Разбор порядка операций

Если при начальном значении 5 первым вызывается increment(value), объект становится равен 6. Последующий incremented(value) возвращает 7, оставляя объект равным 6. Возвращаемое значение меняет исходную переменную лишь при явном присваивании, например value = incremented(value);. Поэтому интерфейс должен ясно показывать, какая операция изменяет состояние.

const-ссылка: читать контейнер без его копирования

Цель: различать входной параметр, изменяемый параметр и самостоятельный результат функции.

Для небольшого числа обычно достаточно передачи по значению. Когда функция только читает контейнер, удобно принять const std::vector<int>&: она обращается к исходному вектору без создания его копии и не может изменять элементы через этот параметр.

Контракт sum: не более 1000 элементов, каждый от −1000 до 1000; результат — сумма типа long long; исходный вектор остаётся прежним. Для пустого вектора сумма равна нулю.

#include <cstddef>
#include <iostream>
#include <vector>

// Contract: at most 1000 elements; each element is in [-1000, 1000].
// Returns their sum, leaves the vector unchanged; empty sum is 0.
long long sum(const std::vector<int>& numbers) {
    long long total = 0;
    for (int value : numbers) {
        total += value;
    }
    return total;
}

int main() {
    int count = 0;
    if (!(std::cin >> count) || count < 0 || count > 1000) {
        std::cerr << "input error\n";
        return 1;
    }
    std::vector<int> numbers(static_cast<std::size_t>(count));
    for (int& value : numbers) {
        if (!(std::cin >> value) || value < -1000 || value > 1000) {
            std::cerr << "input error\n";
            return 1;
        }
    }
    std::cout << sum(numbers) << ' ' << numbers.size() << '\n';
    return 0;
}

Ввод: количество элементов, затем сами элементы. Для 4 7 -3 0 2 вывод — 6 4: сумма и размер вектора. Для 0 вывод — 0 0. Если элементов не хватает или нарушен диапазон, программа сообщает об ошибке.

const относится к доступу через этот параметр: он не делает исходный изменяемый вектор навсегда константным. Внутри sum нельзя записать numbers[0] = 5 или вызвать изменяющий вектор push_back. Вызывающий код после возвращения может менять свой вектор как обычно.

Если параметр записан как const int value, это отдельное значение, которое нельзя переназначить внутри тела. Такая запись не означает передачу по ссылке и не требует константного аргумента. Для типа int форма const int& обычно не даёт учебного или практического выигрыша перед обычным int.

Разбор читающего интерфейса

Подсчёт положительных элементов тоже только читает вектор. Его возможный интерфейс — int count_positive(const std::vector<int>& values) при той же границе длины 1000. Счётчик, начинающийся с нуля и увеличивающийся при value > 0, дал бы 2 для [7, -3, 0, 2] и 0 для пустого вектора или [0, -1]. Ноль не является строго положительным. Результат помещается в int, а ссылка на const выражает отсутствие изменения элементов через параметр.

Массив в параметрах: адрес не заменяет размер

Цель: передать последовательность без потери границ и отличать невладеющий указатель от контейнера.

В списке параметров обычной функции записи const int values[] и const int* values задают один и тот же тип параметра. При вызове со встроенным массивом функция получает указатель на первый элемент; весь массив не копируется. Длина в типе такого параметра не сохраняется.

Поэтому sizeof(values) внутри такой функции — размер указателя, а не количество элементов. Если в условии теста явно дано sizeof(int*) == 8, результат будет 8. Размер указателя зависит от реализации; в программе нельзя подставлять 4 или 8 как универсальную величину.

Явный размер и пустая последовательность

Контракт sum_array: не более 1000 элементов от −1000 до 1000. При положительном count указатель должен обозначать начало доступной последовательности минимум из count элементов. При нулевом размере допустим nullptr: функция не обращается к памяти и возвращает 0.

#include <cstddef>
#include <iostream>
#include <iterator>

// Contract: count <= 1000; elements are in [-1000, 1000].
// For count > 0, values points to at least count readable int elements.
// For count == 0, values may be nullptr; the result is 0.
long long sum_array(const int* values, std::size_t count) {
    long long total = 0;
    for (std::size_t i = 0; i < count; ++i) {
        total += values[i];
    }
    return total;
}

int main() {
    int numbers[5]{};
    for (int& value : numbers) {
        if (!(std::cin >> value) || value < -1000 || value > 1000) {
            std::cerr << "input error\n";
            return 1;
        }
    }
    std::cout << sum_array(numbers, std::size(numbers)) << '\n';
    std::cout << sum_array(nullptr, 0) << '\n';
    return 0;
}

Ввод: ровно пять требуемых чисел. Для 1 2 3 4 5 вывод — две строки: 15 и 0. В main имя numbers ещё обозначает сам массив, поэтому std::size(numbers) из C++17 возвращает 5. Внутри функции тот же приём для параметра-указателя недоступен.

Нельзя передать размер больше реально доступного диапазона: указатель сам его не проверит. Второй распространённый интерфейс — пара указателей на начало и на позицию за концом одного диапазона. Для настоящего массива std::begin(numbers) и std::end(numbers) из <iterator> дают эти границы; указатель за последним элементом не разыменовывают.

Нулевой символ '\0' завершает корректную C-строку, но не является общим признаком конца произвольного массива чисел. Не пытайтесь угадать длину по значениям элементов. Для нового кода, где уместен владеющий контейнер, std::vector хранит свой размер; функция может принять его по const&. В C++20 для невладеющего представления диапазона есть std::span; здесь достаточно освоить явную пару «указатель и длина».

Двумерные данные без ручного управления памятью

Встроенный int table[3][5] при преобразовании даёт указатель на строку типа int (*)[5], а не int**. Эти типы нельзя взаимозаменять. Для таблицы с размерами, известными во время выполнения, покажем владеющий контейнер: вектор строк. Он освобождает память автоматически.

#include <cstddef>
#include <iostream>
#include <vector>

// Contract: at most 20 rows, at most 20 elements in each row;
// each element is in [-1000, 1000]. Empty rows are allowed.
long long sum_matrix(const std::vector<std::vector<int>>& matrix) {
    long long total = 0;
    for (const auto& row : matrix) {
        for (int value : row) {
            total += value;
        }
    }
    return total;
}

int main() {
    int rows = 0;
    int columns = 0;
    if (!(std::cin >> rows >> columns) || rows < 0 || rows > 20 ||
        columns < 0 || columns > 20) {
        std::cerr << "input error\n";
        return 1;
    }
    std::vector<std::vector<int>> matrix(
        static_cast<std::size_t>(rows),
        std::vector<int>(static_cast<std::size_t>(columns)));
    for (auto& row : matrix) {
        for (int& value : row) {
            if (!(std::cin >> value) || value < -1000 || value > 1000) {
                std::cerr << "input error\n";
                return 1;
            }
        }
    }
    std::cout << sum_matrix(matrix) << '\n';
    return 0;
}

Ввод: число строк и столбцов от 0 до 20, затем элементы от −1000 до 1000 в порядке строк. Для 2 3 1 2 3 4 5 6 вывод — 21. Для нуля строк или столбцов сумма равна 0. Контракт вычисляющей функции допускает и строки различной длины в тех же пределах; main здесь строит прямоугольную таблицу.

Разбор потери длины

Выражение sizeof(values) / sizeof(values[0]) внутри sum_array делит размер указателя на размер элемента. Оно не восстанавливает длину массива и не зависит от фактически переданного количества элементов. Надёжный интерфейс сохраняет размер явно или принимает контейнер. Изменение элементов потребовало бы int* либо изменяемую ссылку на контейнер и отдельного описания побочных эффектов.

Здесь указатель — невладеющий доступ к диапазону: функция не выделяет и не освобождает память. Эта граница ответственности останется важной для строк, потоков и умных указателей.

Рекурсия: базовый случай и движение к нему

Цель: проверить завершение рекурсивной функции, допустимый диапазон результата и максимальную глубину вызовов.

Рекурсивная функция вызывает саму себя для более простого случая той же задачи. Для факториала неотрицательного целого числа используются правила 0! = 1 и n! = n × (n - 1)! при n > 0.

Контракт: принимаем только 0 ≤ n ≤ 20 и возвращаем n! как unsigned long long. Этот диапазон выбран так, чтобы результат помещался и при минимально гарантированной для этого типа разрядности в 64 бита. Вход проверяется до вызова и до преобразования к беззнаковому типу.

#include <iostream>

// Contract: 0 <= n <= 20. Returns n!, including 0! = 1.
unsigned long long factorial(unsigned int n) {
    if (n == 0) {
        return 1;
    }
    return n * factorial(n - 1);
}

int main() {
    int n = 0;
    if (!(std::cin >> n) || n < 0 || n > 20) {
        std::cerr << "input error\n";
        return 1;
    }
    std::cout << factorial(static_cast<unsigned int>(n)) << '\n';
    return 0;
}

Ввод: одно целое число от 0 до 20. Для 5 ответ 120; для 0 — 1. Для 20 ответ 2432902008176640000. Значения −1 и 21 отклоняются.

Как возвращается результат

Для factorial(3) вычисление сводится к 3 * factorial(2), затем к 2 * factorial(1) и 1 * factorial(0). Базовый вызов возвращает 1; при возвратах получаются 1, 2 и 6. У каждого вызова есть собственное значение параметра n.

Здесь легко проверить три условия: базовый случай n == 0 возвращает готовый ответ; при каждом рекурсивном шаге неотрицательное n уменьшается на 1; предел 20 ограничивает глубину цепочки 21 вызовом. Простого наличия if недостаточно: изменение аргумента должно действительно приближать к базовому случаю.

Программа выполняет n умножений. В обычной реализации незавершённые вызовы требуют дополнительной памяти, пропорциональной глубине. Рекурсия не даёт бесконечного стека: без ограничения глубины даже корректная формула может исчерпать ресурсы. Переполнение целого типа — отдельная проблема, которую базовый случай сам по себе не решает.

Разбор итеративного варианта

Итеративный факториал хранит unsigned long long result = 1; и последовательно умножает его на числа от 2 до n. Для n == 0 и n == 1 цикл не выполняется, ответ равен 1. Число умножений линейно зависит от n, но цепочки незавершённых рекурсивных вызовов нет. Именно эту реализацию с прежним контрактом 0 ≤ n ≤ 20 далее выделим в отдельный исходный файл.

Перенос полного перебора огромного диапазона из цикла в рекурсию не ускоряет алгоритм. В теме сложности и в деревьях будут отдельно связаны число операций, глубина вызовов и дополнительная память.

Область видимости, время жизни и static

Цель: различать три вопроса: где доступно имя, когда существует объект и сохраняется ли его состояние между вызовами.

Область видимости определяет, где можно найти имя. Время жизни — период существования объекта. Длительность хранения описывает, как долго доступна память для него. Эти понятия связаны, но не заменяют друг друга: локальное имя может обозначать объект, который сохраняется между вызовами.

Автоматическая и статическая локальная переменная

#include <iostream>

int next_local() {
    int counter = 0;
    return ++counter;
}

// Demonstration: called twice; the counter must not overflow int.
int next_static() {
    static int counter = 0;
    return ++counter;
}

int main() {
    const int local_first = next_local();
    const int local_second = next_local();
    const int static_first = next_static();
    const int static_second = next_static();
    std::cout << local_first << ' ' << local_second << '\n';
    std::cout << static_first << ' ' << static_second << '\n';
    return 0;
}

Ввод не требуется. Программа выводит:

1 1
1 2

В next_local каждый вызов создаёт свой автоматический counter со значением 0. В next_static оба вызова работают с одним статическим объектом: после первого вызова значение 1 сохраняется, после второго становится 2. В примере каждая функция вызывается дважды; для произвольного счётчика нужно отдельно обеспечить отсутствие переполнения.

Имена обоих counter доступны только внутри своих функций. Ключевое слово static не делает локальное имя глобальным. Автоматический локальный объект уничтожается при выходе из блока; статический сохраняется между вызовами и имеет длительность хранения, охватывающую выполнение программы. Нельзя выводить из этого обязательное физическое выделение памяти «на стеке при каждом вызове»: стандарт описывает поведение объектов, а реализация может оптимизировать хранение.

Когда происходит инициализация

Динамическая инициализация локального статического объекта выполняется при первом достижении объявления и после успешного завершения не повторяется. Нулевая и константная инициализация могут происходить раньше; в нашем static int counter = 0; используется константная инициализация. Не следует учить общее правило «все static обязательно создаются ровно при первом вызове».

Переменные уровня пространства имён без thread_local также имеют статическую длительность хранения. Их имена видны в соответствии с объявлениями и правилами области видимости. Зависеть от порядка динамической инициализации обычных глобальных объектов из разных .cpp без специальных гарантий нельзя: порядок файлов в проекте сам по себе таких гарантий не даёт.

Связывание и const — другие свойства

const ограничивает изменение объекта через соответствующее имя или ссылку; оно не означает extern. extern не делает объект константным. У обычной переменной const int на уровне пространства имён без extern и inline по умолчанию внутреннее связывание. В следующем шаге понадобится разделять объявления в заголовке и определения в исходном файле.

Разбор зависимости от истории

Третий вызов next_local() снова даёт 1, третий next_static() — 3. Поэтому результат функции со скрытым состоянием зависит от истории предыдущих вызовов. Когда счётчик относится к данным задачи, его можно хранить у вызывающего кода и передавать явно по изменяемой ссылке. Такой интерфейс позволяет видеть зависимость и выбирать исходное состояние.

Вызовы в примере записаны отдельными операторами. В C++17/20 нельзя в общем случае считать, что аргументы одного вызова вычисляются слева направо: неподтверждённый порядок побочных эффектов не должен определять результат.

factorial.hpp содержит интерфейс — объявление функции и именованную границу допустимых аргументов:

#ifndef COURSE_FACTORIAL_HPP
#define COURSE_FACTORIAL_HPP

inline constexpr unsigned int factorial_limit = 20;

// Precondition: n <= factorial_limit. Returns n!, including 0! = 1.
unsigned long long factorial(unsigned int n);

#endif

Защита #ifndef/#define/#endif не даёт повторно обработать содержимое заголовка внутри одной единицы трансляции. Имя макроса выбрано специфичным для этого заголовка. #pragma once широко поддерживается, но не является директивой стандарта C++. inline constexpr у переменной доступно с C++17 и позволяет поместить согласованное определение общей константы в заголовок; подробнее о связывании — в следующем шаге.

factorial.cpp содержит единственное обычное определение функции и включает собственный заголовок:

#include "factorial.hpp"

unsigned long long factorial(unsigned int n) {
    unsigned long long result = 1;
    for (unsigned int factor = 2; factor <= n; ++factor) {
        result *= factor;
    }
    return result;
}

При n == 0 или n == 1 цикл пропускается, ответ равен 1. Для 5 последовательные произведения дают 2, 6, 24, 120. Для 20 ответ 2432902008176640000 помещается в unsigned long long при минимально гарантированном диапазоне этого типа. Собственный заголовок позволяет компилятору проверить соответствие интерфейса и определения; ручная копия объявления в каждом файле создала бы риск рассогласования.

main.cpp отвечает за проверку ввода и вывод:

#include "factorial.hpp"
#include <iostream>

int main() {
    int n = 0;
    if (!(std::cin >> n) || n < 0 || n > static_cast<int>(factorial_limit)) {
        std::cerr << "input error\n";
        return 1;
    }
    std::cout << factorial(static_cast<unsigned int>(n)) << '\n';
}

Отрицательное значение отклоняется до преобразования в беззнаковый тип. Для ввода 5 программа выводит 120, для 0 — 1; −1, 21 и нечисловой ввод дают сообщение input error и код завершения 1. Функция вычисления полагается на своё предусловие: внешний пользователь библиотеки также обязан его соблюдать.

Единицы трансляции и компоновка

После препроцессирования каждого .cpp вместе с включёнными заголовками получается отдельная единица трансляции. Директива #include предоставляет объявления, но не компилирует другой .cpp и не подключает его объектный файл. В обычной схеме каждый .cpp компилируется в объектный файл, а компоновщик связывает вызовы с определениями.

g++ -std=c++20 -Wall -Wextra -Wpedantic -c factorial.cpp -o factorial.o
g++ -std=c++20 -Wall -Wextra -Wpedantic -c main.cpp -o main.o
g++ main.o factorial.o -o factorial_demo

Это запись этапов для GCC; драйвер может выполнить их одной командой g++ -std=c++20 main.cpp factorial.cpp -o factorial_demo. В Visual Studio используются те же роли компилятора и компоновщика, хотя имена файлов и параметры другие. Обычное определение функции не помещается в оба .cpp: для всей программы здесь нужно одно определение. Заголовок с inline-определениями подчиняется отдельным условиям правила одного определения.

При изменении тела factorial.cpp пересобирается этот исходник и затем выполняется компоновка. При изменении общего заголовка могут потребоваться все зависящие от него единицы трансляции. Это объясняет роль системы сборки: она отслеживает зависимости, а не просто количество исходных файлов.

Область видимости отвечает за поиск имени в тексте, а связывание — за то, обозначают ли объявления в разных единицах трансляции одну сущность. Само совпадение имён в двух файлах ещё не описывает все эти правила.

В предыдущем примере inline constexpr unsigned int factorial_limit = 20; задаёт неизменяемую границу в заголовке. Начиная с C++17 такая inline-переменная с внешним связыванием может иметь согласованные определения в нескольких единицах трансляции и обозначать одну сущность. Должны соблюдаться условия правила одного определения; произвольно разные значения в копиях заголовка недопустимы.

Когда нужен extern

Другой способ разделяет объявление и определение объекта. В следующем самостоятельном по составу файлов примере objects.hpp только объявляет два объекта:

#ifndef COURSE_OBJECTS_HPP
#define COURSE_OBJECTS_HPP

extern const int configured_limit;
extern double calibration;

#endif

extern без инициализатора здесь не определяет новый объект. Файл objects.cpp включает объявление и задаёт единственные определения:

#include "objects.hpp"

const int configured_limit = 5;
double calibration = 3.4;

Из-за ранее видимого extern-объявления configured_limit имеет внешнее связывание, хотя определён как const. Без такого объявления обычная не-inline переменная const уровня пространства имён по умолчанию имела бы внутреннее связывание. extern и const описывают разные свойства.

Файл main.cpp использует объявления:

#include "objects.hpp"
#include <iostream>

int main() {
    std::cout << configured_limit << ' ' << calibration << '\n';
}

При сборке g++ -std=c++20 main.cpp objects.cpp -o objects_demo программа печатает 5 3.4. Если не включить objects.cpp в сборку, объявления останутся видны, но определения для компоновки не найдутся. Если обычное определение double calibration = 3.4; поместить в заголовок нескольких исходников, получится нарушение правила одного определения.

Общее состояние — решение интерфейса

Изменяемая calibration показана для объяснения языка, а не как обязательный способ передачи данных. Глобальное состояние создаёт зависимость от истории вызовов и усложняет изоляцию проверок. Значение или ссылку на конфигурацию часто понятнее передать явно. Далее инвариант класса позволит описывать допустимое состояние группы данных, а владение — того, кто отвечает за его время жизни.

Библиотека: интерфейс, реализация и зависимость

Библиотека объединяет средства для некоторой области: функции, типы и другие объявления вместе с необходимой реализацией. Пользователь работает через интерфейс и его контракт, а детали вычисления могут меняться. Пример factorial уже разделяет эти роли: factorial.hpp сообщает контракт, factorial.cpp реализует его, main.cpp использует.

Подключение готовой библиотеки обычно затрагивает три разных этапа:

  1. Компиляция: доступны заголовки и нужный режим языка; компилятор понимает вызовы и типы.
  2. Компоновка: доступны необходимые определения из объектных файлов или библиотек. Одного #include для этого недостаточно.
  3. Запуск: если используется разделяемая библиотека, загрузчик должен найти совместимый файл и его зависимости.

Не все библиотеки требуют отдельного бинарного файла. Реализация header-only доступна из заголовков — например, через шаблоны и inline-функции. Подключение такого заголовка тоже требует соблюдения его условий и может увеличить время компиляции. Это не то же самое, что статическая библиотека.

Стандартная библиотека C++ задаётся стандартом языка и поставляется реализацией C++; сторонние библиотеки имеют собственные версии, поддержку и правила распространения. Наличие готового кода само по себе не доказывает его пригодность. Важны документированный контракт, поддерживаемые платформы, совместимость, лицензия и стоимость сопровождения зависимости.

Статическая библиотека на примере factorial

Используем без изменений три файла из многофайлового примера: factorial.hpp, factorial.cpp, main.cpp. Добавление библиотечной цели меняет организацию сборки, а не контракт 0 ≤ n ≤ 20. Заголовок остаётся доступен и реализации, и приложению.

Полное описание сборки CMakeLists.txt:

cmake_minimum_required(VERSION 3.22)
project(FactorialLibrary LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20 CACHE STRING "C++ language standard")
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
option(BUILD_SHARED_LIBS "Build a shared library" OFF)

add_library(course_math factorial.cpp)
target_include_directories(course_math PUBLIC "${CMAKE_CURRENT_SOURCE_DIR}")
set_target_properties(course_math PROPERTIES WINDOWS_EXPORT_ALL_SYMBOLS ON)

add_executable(factorial_demo main.cpp)
target_link_libraries(factorial_demo PRIVATE course_math)

foreach(target IN ITEMS course_math factorial_demo)
    if(MSVC)
        target_compile_options(${target} PRIVATE /W4 /permissive-)
    elseif(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
        target_compile_options(${target} PRIVATE -Wall -Wextra -Wpedantic)
    endif()
endforeach()

add_library создаёт цель course_math. Без явного типа она выбирает STATIC или SHARED по BUILD_SHARED_LIBS; здесь значение по умолчанию — OFF, то есть статическая библиотека. Эквивалентный жёстко заданный вариант — add_library(course_math STATIC factorial.cpp). Каталог заголовка задан как PUBLIC: он нужен самой библиотеке и передаётся использующему её приложению. target_link_libraries сообщает зависимость компоновщику через систему сборки.

Свойство WINDOWS_EXPORT_ALL_SYMBOLS пригодится для варианта DLL в следующем шаге; в статической сборке оно не меняет контракт. Это средство CMake для MS-совместимых инструментов Windows, а не ключевое слово C++.

Команды для статического варианта:

Проверяемый отказ и неопределённое поведение

Вектор предоставляет два разных интерфейса. values[index] требует допустимого индекса и не обещает исключения при нарушении. values.at(index) проверяет границу и сообщает о недопустимом индексе исключением std::out_of_range. Полный пример C++17/20:

#include <iostream>
#include <stdexcept>
#include <vector>

int main() {
    const std::vector<int> values{10, 20};
    try {
        std::cout << values.at(values.size()) << '\n';
    } catch (const std::out_of_range&) {
        std::cout << "index outside the range\n";
    }
}

Здесь values.size() равно 2. Метод at не возвращает элемент, а бросает исключение; управление переходит к соответствующему catch. Вывод — index outside the range. Замена at на operator[] не создаёт альтернативный способ обработки ошибки: произошло бы нарушение предусловия доступа. Исключение обработано по ссылке, без копирования объекта исключения.

Одна задача, два уровня анализа

Разбираемый пример: среди целых чисел от 1 до n включительно подсчитать те, у которых сумма десятичных цифр больше суммы цифр следующего числа. Для пользовательского ввода 1 ≤ n ≤ 109. Например, 8 не подходит: 8 < 9. Число 9 подходит: 9 > 1. Среди чисел 1..19 подходят 9 и 19, ответ 2. Эта формулировка не зависит от изображения условия.

Ниже полный фрагмент двух вычисляющих функций; ввода и main в нём нет. Для внутреннего контракта дополнительно разрешён n == 0, означающий пустой интервал.

// Precondition: num >= 0.
int sum_of_digits(long long num) {
    int result = 0;
    do {
        result += static_cast<int>(num % 10);
        num /= 10;
    } while (num != 0);
    return result;
}

// Precondition: 0 <= interval_end <= 1'000'000'000.
long long count_by_enumeration(long long interval_end) {
    long long count = 0;
    for (long long value = 1; value <= interval_end; ++value) {
        if (sum_of_digits(value) > sum_of_digits(value + 1)) {
            ++count;
        }
    }
    return count;
}

Операции с остатком и делением выделяют десятичные цифры неотрицательного числа. Тип long long вмещает границу 109, значение value + 1 и счётчик во всём заявленном диапазоне даже при минимальных гарантиях стандарта.

Перебор посещает n чисел; обработка цифр добавляет число шагов, пропорциональное их количеству. При переменном числе разрядов это O(n log n) простых операций. Под ограничением 109 разрядов не больше десяти, но миллиард итераций всё равно велик. Точное время зависит от среды; корректность формулы и соответствие лимиту времени — разные вопросы.

Следующий шаг выводит формулу без полного перебора. Перебор остаётся понятной независимой моделью для небольших значений при авторской проверке этой формулы.

От перебора к формуле и отдельной функции

Пусть число заканчивается ровно k девятками. При прибавлении единицы они превращаются в нули, а соседний разряд увеличивается на один; если разряда не было, появляется ведущая единица. Поэтому сумма цифр меняется на 1 − 9k. Она уменьшается тогда и только тогда, когда k ≥ 1, то есть последняя цифра исходного числа — девятка.

Подходящие числа: 9, 19, 29, …. Среди чисел от 1 до n включительно их ровно (n + 1) / 10, где деление целочисленное. Для n = 8 ответ 0, для 9 и 10 — 1, для 19 — 2. Формула выполняет постоянное число арифметических операций, в отличие от перебора всего интервала.

Оптимизация меняет способ вычисления ради эффективности. Рефакторинг меняет внутреннюю структуру с сохранением наблюдаемого поведения. Далее выделим вычисление из консольной программы, чтобы вызывать его и из приложения, и из тестов.

Готовый пример состоит из трёх файлов в одной папке. interesting.hpp содержит объявление функции и её предусловие. Для локальной функции дополнительно разрешим n = 0: в пустом интервале ответ равен нулю. В задании Stepik граница остаётся 1 ≤ n ≤ 109.

#ifndef INTERESTING_HPP
#define INTERESTING_HPP

// Precondition: 0 <= interval_end <= 1'000'000'000.
long long CountInterestingInInterval(long long interval_end);

#endif

Файл interesting.cpp — единственное определение алгоритма:

#include "interesting.hpp"

long long CountInterestingInInterval(long long interval_end) {
    return (interval_end + 1) / 10;
}

Тип long long позволяет представить все значения заявленного диапазона и промежуточное n + 1. За пределами предусловия функция здесь не проверяется; этот контракт не следует расширять без анализа переполнения.

Первые автоматические тесты и CTest

В разобранном проекте рядом с interesting.hpp, interesting.cpp и main.cpp находится tests.cpp. В нём нет второй копии формулы: тесты подключают заголовок и вызывают функцию из того же interesting.cpp, что и приложение.

#include "interesting.hpp"
#include <iostream>

bool Check(long long input, long long expected) {
    const long long actual = CountInterestingInInterval(input);
    if (actual == expected) {
        return true;
    }
    std::cerr << "n=" << input << ": expected " << expected
              << ", got " << actual << '\n';
    return false;
}

int main() {
    int failures = 0;
    failures += !Check(0, 0);
    failures += !Check(1, 0);
    failures += !Check(8, 0);
    failures += !Check(9, 1);
    failures += !Check(10, 1);
    failures += !Check(18, 1);
    failures += !Check(19, 2);
    failures += !Check(20, 2);
    failures += !Check(99, 10);
    failures += !Check(100, 10);
    failures += !Check(880'055'535, 88'005'553);
    failures += !Check(999'999'999, 100'000'000);
    failures += !Check(1'000'000'000, 100'000'000);
    if (failures != 0) {
        return 1;
    }
    std::cout << "13 checks passed\n";
}

Check возвращает true, если результат совпал. Выражение !Check(...) даёт true при ошибке и при сложении увеличивает счётчик на единицу. Неудачная проверка печатает вход, ожидаемое и фактическое значения. Ненулевой код завершения сообщает системе запуска, что тесты провалились.

Значения 8, 9, 10 и 18, 19, 20 проверяют переход через последнюю цифру 9; 99 и 100 — перенос через несколько разрядов. Есть пустой интервал для локального контракта, минимальный вход задания и большие границы. Ожидаемые ответы записаны явно, а не вычисляются копией проверяемой формулы.

Здесь используются обычные условия, поэтому проверки работают и в сборке Release. Стандартный макрос assert может быть отключён при определении NDEBUG; он не подходит для таких обязательных проверок без контроля настроек.

Полный CMakeLists.txt этого примера:

add_executable(interesting_app main.cpp)
target_link_libraries(interesting_app PRIVATE interesting)

    add_executable(interesting_tests tests.cpp)
    target_link_libraries(interesting_tests PRIVATE interesting)
    add_test(NAME InterestingNumbers COMMAND interesting_tests)
endif()

    list(APPEND learning_targets interesting_tests)
endif()
foreach(target IN LISTS learning_targets)
    set_target_properties(${target} PROPERTIES
        CXX_STANDARD 20
        CXX_STANDARD_REQUIRED YES
        CXX_EXTENSIONS NO
    )
    if(MSVC)
        target_compile_options(${target} PRIVATE /W4 /permissive-)
    elseif(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
        target_compile_options(${target} PRIVATE -Wall -Wextra -Wpedantic)
    endif()

Цель interesting содержит общий код. target_link_libraries связывает с ним приложение и тесты. include(CTest) вводит настройку BUILD_TESTING; add_test регистрирует тестовый исполняемый файл. CTest учитывает код завершения: 0 — успех, ненулевой — отказ.

Как выглядит отказ работающего теста

В предыдущем примере правильная проверка Check(9, 1) проходит: среди 1..9 подходит одно число. Для ошибочного ожидания Check(9, 2) та же функция получает фактическое значение 1 и печатает:

n=9: expected 2, got 1

Check возвращает false, выражение !Check(...) увеличивает failures, а тестовая программа завершается с кодом 1. CTest показывает отказ. Так отрицательный контроль связывает реальную проверку, диагностическое сообщение и статус запуска; зелёный результат без выполненных проверок ничего не подтверждает. Возвращение ожидания 1 восстанавливает успешный результат.

Другая ошибка — замена формулы (n + 1) / 10 на n / 10. Для 8 обе формулы дают 0, но для 9 правильный ответ 1, а ошибочный 0. Именно поэтому соседние точки границы информативнее одного произвольного большого значения.

Тестирование и измерение времени решают разные задачи. Быстрый запуск не означает правильный ответ. Отображаемые 0 мс могут быть следствием разрешения таймера. Для сравнения скорости нужны сопоставимые входы, условия запуска и достаточная длительность измерения.

Программа из предыдущего шага работает без GoogleTest: CTest запускает исполняемый файл, а библиотека утверждений нужна лишь для более удобной организации самих проверок.

Цель: различать EXPECT_* и ASSERT_*, правильно сравнивать строки и понимать, какая настройка нужна для запуска тестов GoogleTest.

Это дополнительный шаг. Предыдущий пример уже работает со стандартной библиотекой и CTest. GoogleTest — отдельная зависимость, а не часть C++ или CMake. Ниже приведена сборка с закреплённой версией GoogleTest v1.17.0; другие способы подключения описаны в официальной инструкции CMake. CTest запускает тестовые программы, а GoogleTest предоставляет проверки и организует тесты внутри программы.

Что происходит при неудачной проверке

ПроверкаПоведение при неудачеКогда подходит
EXPECT_*Регистрирует отказ, текущая функция продолжает выполняться.Независимые сравнения, чтобы увидеть несколько ошибок за один запуск.
ASSERT_*Регистрирует отказ и немедленно завершает текущую функцию.Без успешного результата дальнейшие действия в этой функции небезопасны или бессмысленны.

Например, перед обращением к первому элементу полученного вектора можно проверить ASSERT_FALSE(values.empty()). Отказ одной проверки не означает немедленного завершения всей программы со всеми тестами.

Фрагмент для проекта с подключённым GoogleTest

Ниже содержимое отдельного файла gtest_assertions.cpp. Он использует объявление из interesting.hpp и ту же реализацию из interesting.cpp, что и приложение. Это не самостоятельная программа: ей нужны GoogleTest и отдельная цель сборки, показанная далее. GTest::gtest_main предоставляет точку входа; не добавляйте в эту цель прежний tests.cpp с собственным main. Готовая цель interesting_tests из предыдущего шага остаётся отдельным примером.

#include "interesting.hpp"
#include <gtest/gtest.h>
#include <string>

TEST(InterestingNumbers, HandlesCarryBoundary) {
    EXPECT_EQ(0LL, CountInterestingInInterval(8));
    EXPECT_EQ(1LL, CountInterestingInInterval(9));
    EXPECT_EQ(1LL, CountInterestingInInterval(10));
}

TEST(StringComparisons, ComparesContents) {
    const std::string text{"cpp"};
    EXPECT_EQ(std::string{"cpp"}, text);

    const char expected[] = "cpp";
    const char actual[] = "cpp";
    EXPECT_STREQ(expected, actual);
}

Первый тест содержит три независимые проверки функции на границе переноса разряда. InterestingNumbers — имя набора, HandlesCarryBoundary — имя теста. Оба имени — допустимые идентификаторы C++; согласно рекомендациям GoogleTest выбираем имена без подчёркиваний.

Второй тест иллюстрирует выбор сравнения. Для std::string подходит EXPECT_EQ: сравнивается содержимое строк. Для C-строк, то есть нуль-терминированных последовательностей char, содержимое сравнивает EXPECT_STREQ (или ASSERT_STREQ). Обычное сравнение двух указателей через EXPECT_EQ проверяет адреса. Два разных массива могут содержать одинаковый текст и иметь разные адреса.

К проверке можно добавить пояснение, например EXPECT_EQ(1LL, CountInterestingInInterval(9)) << "carry at 9";. Оно появится в сообщении при отказе. Держите ожидание независимым от реализации: вычислять обе стороны одной и той же формулой не полезнее, чем сравнивать результат с собой.

Если нескольким тестам понадобится одинаковая подготовка, позже можно изучить тестовые фикстуры — классы с общей настройкой. Для текущих проверок они не требуются. Подробности: GoogleTest Primer и справочник проверок.

Разбор выбора инструмента и проверки

Для программы из 13 проверок GoogleTest не требуется: обычные условия и коды завершения уже сообщают результат CTest. Несколько независимых EXPECT_EQ позволяют увидеть несколько несовпадений за один запуск. ASSERT_* завершает текущую функцию, когда продолжение в ней лишено смысла или небезопасно. Эти различия относятся к наблюдаемому контракту проверок. Установка библиотеки не заменяет выбор ожидаемого ответа и анализ границ.

Очередь и её инвариант FIFO

Очередь хранит последовательность элементов и обслуживает их по правилу first in, first out: раньше добавленный элемент удаляется раньше. Предварительные знания — интерфейс и реализация, контракт функции.

В абстрактной очереди enqueue(x) добавляет значение в конец, front() показывает первое значение, dequeue() удаляет его. Чтение и удаление требуют непустой очереди; конкретный интерфейс определяет, возвращает ли удаление значение. У std::queue::pop() результат имеет тип void.

ОперацияСостояние от начала к концуСмысл
Начало[]Очередь пуста.
Добавить A, затем B[A, B]A будет обработан первым.
Прочитать начало[A, B]Получено A; очередь не изменена.
Удалить начало[B]A больше не хранится.
Добавить C[B, C]B предшествует C.

Инвариант: относительный порядок ещё не удалённых элементов совпадает с порядком добавления. Перемещать все элементы в памяти при каждом удалении не требуется. В связном списке меняется указатель начала, в кольцевом буфере — индекс.

У кольцевого буфера ёмкости c > 0 индексы обходят массив циклически. Размер нужно отличать от ёмкости: по одному совпадению индексов начала и конца нельзя определить одновременно и пустоту, и заполненность без дополнительного соглашения. При заполнении заранее выбирают политику: отказ, рост или перезапись. Перезапись меняет договор: часть старых данных теряется.

FIFO описывает порядок, а не безопасность параллельного доступа. Очередь сообщений между потоками требует отдельной синхронизации. В следующем шаге сравним FIFO с другими правилами выбора элемента.

У этих интерфейсов разный договор о том, какое значение доступно следующим. Ограниченная ёмкость — отдельное свойство хранения, а не ещё один порядок обслуживания.

Заголовок <queue> определяет адаптер std::queue. Для std::queue<T> базовым контейнером служит std::deque<T>. Подходящий иной контейнер должен предоставлять front, back, push_back и pop_front: например, std::list подходит, а std::vector не имеет pop_front.

Разобранный пример

Полная программа C++17/20 сначала копирует текущее значение в локальный объект, затем удаляет элемент из очереди. Локальная строка продолжает жить независимо от очереди.

#include <iostream>
#include <queue>
#include <string>

int main() {
    std::queue<std::string> pending;
    pending.push("parse");
    pending.push("save");
    while (!pending.empty()) {
        std::string current = pending.front();
        pending.pop();
        std::cout << current << '\n';
    }
}

Вывод — parse, затем save на отдельных строках. Ссылка, полученная от front(), после pop() удаляемого элемента стала бы недействительной: поэтому переменная current хранит собственную строку.

Итераторов begin/end и индексирования у queue нет. Обработка с удалением соответствует её интерфейсу; если нужен обход без удаления, можно обойти копию очереди либо выбрать контейнер с итераторами. Конструктор без аргументов создаёт пустую очередь; конструктора queue(n) с размером нет. Готовый базовый контейнер можно передать конструктору.

Указатели, ссылки и итераторы — разные гарантии

Вставка на любом конце deque сохраняет ссылки на прежние элементы, но делает прежние итераторы недействительными. Это относится и к ранее сохранённому end(). Вставка в середину делает недействительными и итераторы, и ссылки. При удалении на краю ссылки на не удалённые элементы сохраняются; отдельные правила для итераторов и end() зависят от удаляемого края. Надёжный простой приём — заново получать итераторы после изменения контейнера.

Полная программа C++17/20 выводит 20 30, затем 10 20 30 40. Ссылка first по-прежнему обозначает прежний объект со значением 20, хотя его индекс изменился.

#include <deque>
#include <iostream>

int main() {
    std::deque<int> values{20, 30};
    int& first = values.front();
    values.push_front(10);
    values.push_back(40);
    std::cout << first << ' ' << values.at(2) << '\n';
    // References survive insertion at the ends; old iterators do not.
    for (auto it = values.begin(); it != values.end(); ++it) {
        std::cout << *it << ' ';
    }
    std::cout << '\n';
}

Как это может быть устроено

Распространённая реализация хранит элементы в нескольких блоках, а адреса блоков — в отдельной таблице. Пара «номер блока, позиция внутри» позволяет вычислять адрес элемента за постоянное число операций. Размер блока, политика его выделения и устройство таблицы адресов зависят от библиотеки: стандарт не требует конкретного каркаса T**.

Такое устройство объясняет, почему из &d[0] и d.size() нельзя получить единый массив всех элементов. Для API, ожидающего непрерывный диапазон, подходит отдельный vector. Размер служебных структур и реальное быстродействие измеряют на конкретной задаче: из таблицы сложности нельзя вывести, что один контейнер всегда быстрее другого.

static_cast: преобразование с известными предпосылками

static_cast<T>(expression) явно выбирает разрешённую языком категорию преобразования. Компилятор проверяет допустимость формы, но не все условия, зависящие от значения и фактического объекта.

Числовое значение и возвращение исходного указателя

В полной программе C++17/20 целое 7 преобразуется до деления, поэтому результат равен 3,5. Обратное приведение из void* корректно, поскольку там сохранён адрес того же живого объекта int.

#include <iostream>

int main() {
    const int total = 7;
    const int count = 2;
    const double average = static_cast<double>(total) / count;
    int value = 42;
    void* storage = &value;
    int* same_object = static_cast<int*>(storage);
    std::cout << average << ' ' << *same_object << '\n';
}

Вывод: 3.5 42. Запись static_cast<double>(total / count) дала бы 3,0: целочисленное деление уже отбросило дробную часть. При преобразовании плавающего значения в целое дробная часть отбрасывается; если усечённое значение не представимо целевым типом, поведение не определено. Явная запись не заменяет проверку диапазона.

Вниз по иерархии

Из Derived* в доступную однозначную базу Base* обычно можно перейти неявно. Обратный static_cast<Derived*> не проверяет динамический тип: исходный указатель должен обозначать подходящую базовую часть объекта Derived либо быть нулевым. Для ссылки нулевого случая нет. Несоответствие объекта этому условию ведёт к неопределённому поведению, а не к возвращению nullptr.

Когда фактический тип требуется проверить, подходит следующий dynamic_cast для полиморфной базы. Если цель — вызвать общую операцию, проще оставить базовую ссылку и виртуальную функцию. Приведение не передаёт владение: объект по-прежнему принадлежит прежнему владельцу.

dynamic_cast: проверка фактического типа

Нужны понятия наследования и виртуальной функции. Для проверяемого приведения вниз или поперёк иерархии исходный тип должен быть полиморфным: иметь виртуальную функцию. Преобразование вверх к доступной однозначной базе возможно и без полиморфизма.

dynamic_cast<Derived*>(base_pointer) возвращает подходящий указатель или nullptr, если проверка не удалась. Нулевой исходный указатель даёт нулевой результат. Приведение к ссылке не имеет нулевого результата: при неудаче оно выбрасывает std::bad_cast из <typeinfo>.

Разобранная полная программа C++17/20

Локальные объекты живут до конца main; указатели в массиве ими не владеют. Виртуальный деструктор делает базу полиморфной и обеспечивает корректное уничтожение через базовый указатель в тех программах, где оно требуется.

#include <iostream>
#include <typeinfo>

struct Shape {
    virtual ~Shape() = default;
};
struct Circle : Shape {
    int radius = 3;
};

int main() {
    Circle circle;
    Shape other;
    Shape* shapes[]{&circle, &other, nullptr};
    for (Shape* shape : shapes) {
        if (const auto* found = dynamic_cast<const Circle*>(shape)) {
            std::cout << found->radius << '\n';
        } else {
            std::cout << "not a circle\n";
        }
    }
    try {
        (void)dynamic_cast<Circle&>(other);
    } catch (const std::bad_cast&) {
        std::cout << "reference cast failed\n";
    }
}

Вывод: 3, два раза not a circle, затем reference cast failed, каждое сообщение на новой строке. Здесь один и тот же оператор отличает объект Circle, обычный Shape и отсутствие объекта.

Проверка не делает безопасным висячий указатель: время жизни исходного объекта должно продолжаться. Также dynamic_cast не снимает const. Если ветвление по конкретным типам повторяется в каждом вызывающем коде, стоит рассмотреть виртуальную операцию в общем интерфейсе; выбор зависит от модели задачи.

const_cast: квалификация доступа и константность объекта

const у ссылки или указателя ограничивает действия через этот путь доступа. Это не всегда означает, что исходный объект был создан константным. const_cast меняет допустимую квалификацию выражения, но не меняет происхождение и свойства объекта.

Полная программа C++17/20 показывает два разных случая. В первом исходный int изменяемый. Во втором исходный объект — const int; после приведения его разрешено читать, но попытка записи имела бы неопределённое поведение.

#include <iostream>

int main() {
    int value = 10;
    const int& read_only_view = value;
    int& writable_view = const_cast<int&>(read_only_view);
    writable_view = 12; // The original object is not const.
    std::cout << value << '\n';
    const int immutable = 7;
    const int* pointer = &immutable;
    int* stripped = const_cast<int*>(pointer);
    std::cout << *stripped << '\n'; // Reading is allowed; writing is not.
}

Вывод: 12, затем 7. Само получение stripped не является ошибкой; недопустима последующая запись в immutable. Поэтому проверка только наличия const_cast не заменяет анализ времени жизни и реального объекта.

Для обычной читающей функции правильный интерфейс — const T& или const T*. Добавление const обычно выполняется неявно. Строковый литерал нельзя делать изменяемым снятием const; для изменяемого текста подходит отдельный std::string или массив.

В новом коде const_cast должен иметь явное обоснование совместимостью интерфейсов. Для представления байтов и числовых преобразований он не предназначен.

reinterpret_cast и представление объекта

reinterpret_cast разрешает только перечисленные стандартом низкоуровневые преобразования, например некоторые преобразования указателей. Он не является числовым преобразованием double в unsigned long long и не создаёт объект нового типа в прежней памяти.

Важны три независимых условия: допустимость самого приведения, выравнивание адреса и допустимость доступа к живому объекту через результирующий тип. Успешная компиляция приведения не доказывает остальные условия. Преобразование int* в double* не разрешает разыменовать его как double.

#include <array>

#include <iostream>

    std::array<unsigned char, sizeof(value)> bytes{};
    std::memcpy(bytes.data(), &value, sizeof(value));
    std::cout << bytes.size() << '\n';
    for (unsigned char byte : bytes) {
        std::cout << static_cast<unsigned int>(byte) << ' ';

    std::cout << '\n';

Что такое дерево?

Предпосылки: структура данных и интерфейс, вызовы функций, владение. В этом разделе дерево — организация узлов и связей, а множество или словарь — интерфейс, который можно на ней построить.

Дерево — одна из наиболее широко распространённых структур данных в информатике, эмулирующая древовидную структуру в виде набора связанных узлов. Является связным графом, не содержащим циклов.

Справочник терминов

  • Узел — элемент дерева, хранящий данные и связи с другими узлами;
  • Корень — самый верхний узел дерева;
  • Ребро — связь между двумя узлами;
  • Лист — узел, не имеющий узлов-потомков на дереве;
  • Высота узла — максимальное число узлов на пути от него до листа включительно; в дальнейших реализациях высота листа равна 1, пустого поддерева — 0;
  • Глубина узла — число рёбер на пути от корня до него; глубина корня равна 0;
  • Дочерний узел — узел, связанный с родительским узлом, находящийся на более низком уровне дерева;
  • Степень узла — количество его дочерних узлов;
  • Поддерево — часть дерева, состоящая из узла и всех его потомков;
  • Обход дерева — процесс посещения каждого узла дерева ровно один раз.

Бинарные деревья

Теперь рассмотрим особый тип деревьев, называемых бинарными или двоичными деревьями.

В информатике бинарным (двоичным) деревом называется иерархическая структура данных, в которой каждый узел имеет не более двух дочерних узлов. Их называют левым и правым ребёнком, а узел, с которым они непосредственно связаны сверху, — их родителем.

Способы обхода дерева

Пусть имеем дерево, где A — корень, B и C — левое и правое поддеревья.

Рассмотрим три основных порядка обхода дерева в глубину:

  • Обход дерева сверху вниз (в прямом порядке): A, B, C — префиксная форма.
  • Обход дерева в симметричном порядке (слева направо): B, A, C — инфиксная форма.
  • Обход дерева в обратном порядке (снизу вверх): B, C, A — постфиксная форма.

Порядок обхода — ещё не порядок ключей

В записи A, B, C буквы B и C обозначают полные рекурсивные обходы соответствующих поддеревьев. Например, для корня 20 с левым листом 10 и правым листом 30 прямой обход даёт 20, 10, 30; симметричный — 10, 20, 30; обратный — 10, 30, 20. Отсортированным симметричный обход будет при дополнительном инварианте дерева поиска.

В курсе высота считается в узлах: пустое дерево имеет высоту 0, лист — 1. Глубина считается в рёбрах, поэтому у непустого дерева высота равна максимальной глубине плюс 1. В других источниках высоту часто считают в рёбрах; это другое соглашение, а не другой алгоритм.

Рекурсивный обход посещает n узлов за O(n) операций и занимает O(h) памяти стека при высоте h. Позднее балансировка ограничит h величиной O(log n); произвольное дерево такой гарантии не имеет.

Бинарное дерево поиска: инвариант и владение

Бинарное дерево поиска (BST) добавляет к форме дерева условие порядка. В модели с уникальными ключами для любого узла x все ключи левого поддерева меньше x.key, а все ключи правого — больше. Это требование относится ко всему поддереву, а не только к непосредственным детям.

Ключи в примере — int. Повторная вставка ключа не меняет прежнее значение и возвращает false; это явный договор, одинаковый у последующих BST, AVL и RB. Другой интерфейс мог бы обновлять значение, но это уже отдельная операция.

Полная программа C++17/20

Корень и связи к детям — владельцы unique_ptr. У каждого узла один владелец, общего владения нет. Функция принимает ссылку на владеющий указатель, чтобы заменить именно нужную связь, в том числе корень. Она создаёт новый узел только на пустом месте.

#include <iostream>
#include <memory>
#include <string>
#include <utility>

struct BstNode {
    int key;
    std::string value;
    std::unique_ptr<BstNode> left, right;
    BstNode(int k, std::string v) : key(k), value(std::move(v)) {}
};

bool insert_bst(std::unique_ptr<BstNode>& root, int key, const std::string& value) {
    if (!root) {
        root = std::make_unique<BstNode>(key, value);
        return true;
    }
    if (key < root->key) return insert_bst(root->left, key, value);
    if (key > root->key) return insert_bst(root->right, key, value);
    return false; // Preserve the existing value for a duplicate key.
}

int main() {
    std::unique_ptr<BstNode> root;
    insert_bst(root, 20, "root");
    insert_bst(root, 10, "left");
    insert_bst(root, 30, "right");
    const bool inserted = insert_bst(root, 20, "other");
    std::cout << std::boolalpha << inserted << ' ' << root->value << '\n';
    std::cout << root->left->key << ' ' << root->key << ' ' << root->right->key << '\n';
}

Вывод: false root, затем 10 20 30. Вторая вставка 20 оставила первоначальную строку. При поиске достаточно на каждом узле выбрать одно поддерево по сравнению ключей; в отброшенном поддереве искомого ключа быть не может по инварианту.

Сырой указатель, временно полученный через get() для чтения узла, был бы наблюдателем: он не продлевает время жизни и не должен удалять узел. Здесь узлы открыты ради объяснения; в библиотечном классе их обычно скрывают, чтобы вызывающий код не мог нарушить порядок.

Вставка и поиск требуют O(h) сравнений при высоте h. Эта программа не поддерживает баланс. Последовательная вставка уже упорядоченных ключей может создать цепочку; рекурсивные вставка и уничтожение такой цепочки также требуют глубины стека O(h). Следующий шаг объясняет, зачем ограничивать высоту.

Сбалансированные деревья поиска помогают избежать таких ситуаций, когда высота дерева далека от предполагаемой log2(n).

Почему одного порядка недостаточно

Вставка ключей 1, 2, 3, 4, 5, 6 по возрастанию создаёт цепочку высоты 6. Порядок 4, 2, 6, 1, 3, 5 даёт дерево высоты 3 с теми же ключами. В обоих случаях инвариант поиска верен. Различается число узлов на пути к ответу.

У бинарного дерева высоты h, считаемой в узлах, не более 2h − 1 узлов. Поэтому минимальная возможная высота растёт как log₂(n + 1). Само BST-условие минимальную высоту не гарантирует: для этого добавляют инвариант баланса.

Далее AVL ограничивает разность высот детей, а красно-чёрное дерево — цвета и чёрную высоту. Оба сохраняют порядок ключей, но получают разные правила восстановления баланса.

АВЛ-дерево

Предпосылка — инвариант BST. AVL добавляет к нему ограничение высот; поворот обязан сохранить оба свойства. Как и ранее, h(пусто) = 0, h(лист) = 1.

Наиболее простое, но наглядное сбалансированное дерево поиска – это АВЛ-дерево.

АВЛ-дерево – это сбалансированное дерево поиска, в котором для каждой вершины модуль разности высот её двух поддеревьев не превышает 1.

В реализации ниже баланс узла b(v) = h(left) − h(right). После вставки или удаления в ранее сбалансированном дереве он может стать +2 или −2. Тогда выбирают подходящее вращение по направлению перекоса узла и его ребёнка, чтобы восстановить |b(v)| ≤ 1.

В АВЛ-дереве используются 4 типа вращений, которые позволяют сохранять свойства дерева при изменении его структуры.

1. Малое левое вращение. b(v) = −2 и b(v->right) ≤ 0: правое поддерево тяжелее, а его внешний правый путь не короче внутреннего.

2. Большое левое вращение. b(v) = −2 и b(v->right) > 0: сначала правое вращение правого ребёнка, затем левое вращение самого v.

3. Малое правое вращение. b(v) = +2 и b(v->left) ≥ 0: левое поддерево тяжелее, а его внешний левый путь не короче внутреннего.

4. Большое правое вращение. b(v) = +2 и b(v->left) < 0: сначала левое вращение левого ребёнка, затем правое вращение самого v.

Само вращение сохраняет порядок ключей двоичного дерева поиска при наличии нужного дочернего узла. Однако произвольное вращение не обязательно восстанавливает AVL-баланс. Для описанных случаев предполагается, что дочерние поддеревья уже сбалансированы; именно выбор малого или большого вращения по указанным условиям восстанавливает баланс текущего поддерева.

После выбранного по этим условиям вращения высота исправляемого поддерева не превосходит его высоты непосредственно перед вращением. Это не означает, что вставка вообще не может увеличить высоту дерева: высота могла вырасти при добавлении узла до балансировки. После удаления высота поддерева может уменьшиться, поэтому балансировку при необходимости продолжают вверх к корню.

Большое вращение — композиция двух малых. Условие баланса и высоту проверяют для результата всей композиции; промежуточное малое вращение не обязано само по себе восстанавливать AVL-баланс.

Благодаря свойству балансированности высот, время добавления элемента в АВЛ-дерево составляет O(log(N)), где N - количество вершин в дереве.

Что сохраняет поворот

При левом повороте узла x его правый ребёнок y становится корнем поддерева. Промежуточное поддерево B — прежний левый ребёнок y — становится правым ребёнком x. Все его ключи удовлетворяют x.key < B < y.key, поэтому симметричный порядок не меняется. Правый поворот симметричен. После перепривязки сначала обновляют высоту бывшего корня, затем нового: новая высота зависит от уже исправленных детей.

Для вставки 30, 10, 20 получается внутренний перекос: у 30 баланс +2, у 10 баланс −1. Сначала левый поворот вокруг 10, затем правый вокруг 30 дают корень 20 с листьями 10 и 30. Это разобранный случай LR; случаи LL, RR и RL выбираются той же таблицей знаков.

Минимальное число узлов AVL высоты h удовлетворяет N(h) = 1 + N(h − 1) + N(h − 2), N(0) = 0, N(1) = 1. Эта последовательность растёт экспоненциально по h, поэтому h = O(log n). Именно инвариант, а не удачный порядок входных ключей, обеспечивает логарифмическое число сравнений.

AVL: согласованная реализация и разобранная трассировка

Ниже полный заголовок avl.hpp и программа, которая его использует. У дерева уникальные целочисленные ключи, значения — строки. insert возвращает false для дубликата без изменения значения; erase возвращает false для отсутствующего ключа; find выдаёт невладеющий указатель или nullptr.

  1. Спуск выбирает ветвь по BST-инварианту.
  2. После изменения дочернего поддерева пересчитывается высота.
  3. Если модуль баланса равен 2, выполняется одно или два нужных вращения.
  4. При возвращении к родителю он получает уже сбалансированное поддерево с актуальной высотой.

Ссылки Tree& позволяют менять владеющую связь без копирования узлов. Вращения используют std::move для передачи unique_ptr. В удалении узла с одним ребёнком старый владелец сначала выносится в локальный объект: так мы не используем член уже уничтоженного узла.

Заголовок avl.hpp

#pragma once
#include <algorithm>
#include <memory>
#include <string>
#include <utility>

namespace avl_example {
struct Node {
    int key;
    std::string value;
    std::unique_ptr<Node> left, right;
    int height = 1;
    Node(int k, std::string v) : key(k), value(std::move(v)) {}
};
using Tree = std::unique_ptr<Node>;

inline int height(const Tree& tree) {
    return tree ? tree->height : 0;
}
inline void update(Node& node) {
    node.height = 1 + std::max(height(node.left), height(node.right));
}
inline int balance(const Tree& tree) {
    return tree ? height(tree->left) - height(tree->right) : 0;
}

// Preconditions: tree and tree->right exist.
inline void rotate_left(Tree& tree) {
    Tree new_root = std::move(tree->right);
    tree->right = std::move(new_root->left);
    update(*tree);
    new_root->left = std::move(tree);
    update(*new_root);
    tree = std::move(new_root);
}
// Preconditions: tree and tree->left exist.
inline void rotate_right(Tree& tree) {
    Tree new_root = std::move(tree->left);
    tree->left = std::move(new_root->right);
    update(*tree);
    new_root->right = std::move(tree);
    update(*new_root);
    tree = std::move(new_root);
}

// The children are AVL trees, and the height changed by at most one.
inline void rebalance(Tree& tree) {
    if (!tree) return;
    update(*tree);
    if (balance(tree) > 1) {
        if (balance(tree->left) < 0) rotate_left(tree->left);
        rotate_right(tree);
    } else if (balance(tree) < -1) {
        if (balance(tree->right) > 0) rotate_right(tree->right);
        rotate_left(tree);
    }
}

// A duplicate key preserves the existing value and returns false.
inline bool insert(Tree& tree, int key, const std::string& value) {
    if (!tree) {
        tree = std::make_unique<Node>(key, value);
        return true;
    }
    bool inserted = false;
    if (key < tree->key) inserted = insert(tree->left, key, value);
    else if (key > tree->key) inserted = insert(tree->right, key, value);
    else return false;
    rebalance(tree);
    return inserted;
}

inline const Node* find(const Tree& tree, int key) {
    const Node* node = tree.get(); // Non-owning observer.
    while (node) {
        if (key < node->key) node = node->left.get();
        else if (key > node->key) node = node->right.get();
        else return node;
    }
    return nullptr;
}

inline bool erase(Tree& tree, int key) {
    if (!tree) return false;
    bool removed = false;
    if (key < tree->key) removed = erase(tree->left, key);
    else if (key > tree->key) removed = erase(tree->right, key);
    else {
        removed = true;
        if (!tree->left) {
            Tree old_root = std::move(tree);
            tree = std::move(old_root->right);
        } else if (!tree->right) {
            Tree old_root = std::move(tree);
            tree = std::move(old_root->left);
        } else {
            const Node* successor = tree->right.get();
            while (successor->left) successor = successor->left.get();
            // Copy the potentially throwing value before changing the key.
            std::string replacement = successor->value;
            tree->key = successor->key;
            tree->value = std::move(replacement);
            erase(tree->right, tree->key);
        }
    }
    rebalance(tree);
    return removed;
}
} // namespace avl_example

При двух потомках берётся минимальный ключ правого поддерева. Замещается пара ключ–значение, затем удаляется прежний узел этой пары. Потенциально бросающее копирование строки выполнено до изменения ключа. Это сохраняет соответствие данных при отказе копирования в данной конкретной реализации с int и обычным std::string.

Программа avl_demo.cpp

#include "avl.hpp"
#include <iostream>

int main() {
    avl_example::Tree tree;
    for (int key : {30, 10, 20, 40}) {
        avl_example::insert(tree, key, std::to_string(key));
    }
    avl_example::insert(tree, 20, "replacement");
    std::cout << tree->key << ' ' << tree->height << '\n';
    avl_example::erase(tree, 20);
    for (int key : {10, 20, 30, 40}) {
        if (const auto* node = avl_example::find(tree, key)) {
            std::cout << node->key << ':' << node->value << ' ';
        }
    }
    std::cout << '\n';
}

После 30, 10, 20 двойной поворот даёт корень 20. Вставка 40 увеличивает высоту дерева до 3; повтор 20 оставляет его строку прежней. Первая строка вывода — 20 3. После удаления 20 выводятся 10:10 30:30 40:40: данные преемника перенесены вместе с ключом.

Это объясняющая реализация, а не замена std::map: открытые узлы позволяют внешнему коду нарушить инвариант, нет библиотечного интерфейса итераторов. После удаления не следует сохранять наблюдатели на узлы; удаление с заменой пары также меняет содержимое существующего узла. Поиск, вставка и удаление требуют O(log n) сравнений; рекурсивные операции используют O(log n) памяти стека. Стоимость копирования строки рассматривается отдельно от числа сравнений ключей.

Два-три дерево

2–3-дерево помогает понять идею одинаковой глубины листьев. Для общего красно-чёрного дерева точнее соответствие с 2–3–4-деревом, к которому перейдём в конце шага.

Забегая вперед, скажу, что два-три дерево - это, по сути, родитель нашего КЧД, поэтому важно начать именно с него. Поймем два-три дерево - поймем и КЧД.

Два-три дерево — дерево поиска, в котором узел содержит один или два ключа. Внутренний узел с одним ключом имеет двух детей (2-нода), а с двумя ключами — трёх (3-нода); листья детей не имеют. Ключи внутри узла упорядочены, а поддеревья соответствуют интервалам между ними. Все листья находятся на одной глубине, поэтому высота составляет O(log n), где n — число ключей.

При добавлении элемента в два-три дерево мы всегда спускаемся вниз по дереву и вставляем элемент на место, где он должен находиться, чтобы сохранить порядок сортировки. Если при вставке нарушается балансировка дерева, то происходит перестройка дерева, чтобы восстановить сбалансированность.

Давайте рассмотрим пример создания два-три дерева. Начнем с корневой ноды, которая содержит число 5. Таким образом, 5 становится корнем.

Добавим число 12 в наше два-три дерево. Напомню, что мы всегда добавляем элементы, спускаясь вниз по дереву, и дерево отсортировано. Поскольку у корня уже есть одно значение (5), мы добавляем 12 в корень и получаем ноду с двумя значениями. Теперь нам нужно отсортировать эти значения в порядке возрастания, поскольку в два-три дереве значения отсортированы. Итак, наш корень теперь выглядит как 5-12.

Добавим следующее число. Пусть это будет 17. Давайте пока добавим наш элемент в единственный узел и снова отсортируем его значения. Получился узел 5-12-17.

Внимательный читатель заметит тут подвох - выше я говорил о том, что наши узлы могут содержать не более двух элементов. Здесь применяется правило разделения переполненного узла. Мы берем средний элемент нашего узла и "просачиваем" его наверх. Итог виден на картинке. Корнем стало число 12, левым сыном число 5, правым - 17.

Вышеописанное действие можно назвать балансировкой два-три дерева. Если в узле оказывается три значения, то среднее значение "просачивается" вверх. Алгоритм действий зависит от трех условий:

  • Узел является корнем. В этом случае создается новый узел с одним значением и он становится корнем дерева (как в примере выше).

  • Родительский узел имеет одно значение. В этом случае значение просто добавляется к родительскому узлу и балансировка завершается, появляется третий потомок у родителя.

  • Родительский узел имеет два значения. В этом случае значение снова просачивается вверх, пока не будет выполнено условие 1 или 2.

Второй и третий случай балансировки будут рассмотрены ниже.

Окей, идем дальше. Давайте добавим число 3. Так как теперь мы не ограничиваемся одним узлом, спускаемся вниз. Понятно, что спуститься надо влево и добавить 3 к узлу со значением 5. Не забываем расставить 3 и 5 в нужном порядке. В итоге получился узел 3-5.

Теперь проследим разделение некорневого узла.

Давайте добавим число 4, которое также пойдет влево и присоединится к узлу 3-5. Получится узел 3-4-5, который, как мы уже знаем, нужно привести к нужному виду. Что делаем? Балансируем наше дерево, т.е. "просачиваем" значение 4 наверх.

Теперь самое интересное. Помимо того, что мы добавим 4 к корню, мы также добавим корню третьего потомка - это будет нода, которая была больше 4. В нашем случае это 5. Картина будет выглядеть так:

Почему 5 не могла остаться на месте в своем узле? Тут мы вспоминаем правило отсортированного дерева: значения меньше - слева, значения больше - справа. И так как 5 больше 4, мы не можем оставить 5 слева, т.к. это нарушит наш инвариант. Поэтому узлу со значением 5 ничего не остается, как "переехать", и стать потомком узла 4-12 (кстати, если бы у 5 были потомки, они также "переехали" бы вместе с родителем).

Давайте сделаем небольшую паузу и я объясню, как ориентироваться в узлах с тремя потомками. Все довольно просто:

  • значение, которое меньше левого значения в узле, будет левым потомком;
  • значение, которое больше левого, но меньше правого значения в узле, будет средним потомком;
  • значение, которое больше правого значения в узле, будет правым потомком.

Теперь давайте рассмотрим результат - отсортированное, сбалансированное два-три дерево. Значения меньше расположены слева, а большие - справа (как в случае с 4-5-12, где 5 находится справа от 4 и слева от 12). Корень имеет два значения и три потомка, что соответствует описанию данной структуры. Продолжим разбор: 7 добавляется к среднему листу 5, получая [5, 7]. Вставка 9 временно даёт [5, 7, 9]; ключ 7 поднимается в корень [4, 12], образуя временный [4, 7, 12]. Разделение корня создаёт новый корень 7; его дети — узлы 4 и 12, а листья — 3, 5, 9 и 17 на одной глубине.

При вставке значения в два-три дерево мы рекурсивно спускаемся вниз и разделяем узлы с тремя значениями, например, узел (3, 4, 5). Однако, мы можем улучшить эту структуру, не разделяя узлы с тремя значениями после вставки. Вместо этого, мы можем позволить 4-узлам находиться в дереве и разделять их только при необходимости при спуске от корня к листу во время вставки.

Такое дерево называется 2-4 деревом.

Теперь, когда мы разобрались с деревом, можно заметить, что оно менее удобно в реализации, чем бинарное дерево. Необходимо следить за количеством потомков и значениями, их порядком, балансировкой и удалением. Это усложняет представление узла и методы работы с ним, но не требует трёх отдельных классов: разные размеры узлов можно описать и одним типом.

Для решения этой проблемы было разработано красно-черное дерево.

Связь с красно-чёрным представлением

В 2–3-дереве устойчивый узел содержит один или два ключа. В 2–3–4-дереве допустимы также три ключа, разделяющие четыре дочерних диапазона. Если в красно-чёрном дереве объединить чёрный узел с непосредственными красными детьми, получится такой много-ключевой узел. Не следует считать любое красно-чёрное дерево точным двоичным представлением именно 2–3-дерева: для такого соответствия нужны дополнительные ограничения варианта алгоритма.

Повороты сохраняют порядок, а перекрашивания меняют группировку ключей в этой модели. Далее оба действия будут объясняться через инварианты, а не через запоминание рисунков.

Определение красно-черного дерева

Предпосылки — BST, поворот и различие владеющих и слабых ссылок. Здесь сохраняем договор уникальных ключей: повторная вставка оставляет прежнее значение.

Следующие три шага составляют одну реализацию: в этом шаге объявлен класс, далее определены вставка и удаление. Отдельный блок объявления не является законченной программой. Реализация ниже использует RBT<int, std::string> как объясняющий пример; требования к произвольным пользовательским типам и гарантии исключений промышленного контейнера здесь не реализованы.

Красно-чёрные деревья - это деревья поиска, которые используются для автоматического балансирования данных во многих приложениях. std::set и std::map часто реализуются через такие деревья, но стандарт C++ задаёт требования к порядку, сложности и действительности итераторов, а не обязательный цвет или устройство узлов.

Красно-чёрные деревья поддерживают логарифмическую высоту без требования одинаковой высоты левого и правого поддеревьев. В рассматриваемом ниже алгоритме балансировка при вставке требует не более двух поворотов, при удалении — не более трёх; перекрашивание и продвижение по предкам могут занять O(log n). Вместе с поиском места вставки или удаления это даёт O(log n) на операцию.

Красно-чёрное дерево - это двоичное дерево поиска, в котором каждый узел имеет атрибут цвета. При этом:

  • Обычный узел может быть красным или чёрным; отсутствующие левого и правого детей представляют условными чёрными NIL-листьями без данных;
  • В выбранной модели корень чёрный. Это правило слабо влияет на работоспособность модели, так как цвет корня всегда можно изменить с красного на чёрный;
  • Все листья, не содержащие данных, чёрные;
  • Оба потомка каждого красного узла — чёрные;
  • Любой простой путь от узла-предка до листового узла-потомка содержит одинаковое число чёрных узлов.

Благодаря этим ограничениям путь от корня до самого дальнего листа не более чем вдвое длиннее, чем до самого ближнего, и дерево примерно сбалансировано. Операции вставки, удаления и поиска требуют в худшем случае времени, пропорционального высоте дерева, что позволяет красно-чёрным деревьям быть более эффективными в худшем случае, чем обычные двоичные деревья поиска.

 

Для понимания работы красно-черного дерева необходимо рассмотреть свойства 4 и 5 вместе. Если число черных узлов от корня до листа равно B, то кратчайший путь до любого листа содержит B черных узлов. Длинный путь может включать красные узлы, но в дереве не может быть двух красных узлов подряд из-за свойства 4, а путь начинается и заканчивается черным узлом в соответствии с пунктами 2 и 3. Самый длинный путь содержит не более 2B−1 узлов; равенство возможно при чередовании чёрных и красных узлов.

Красно-чёрное дерево связано с 2-3-4-деревом (его также называют 2-4-деревом). Если мысленно объединить чёрный узел с его непосредственными красными детьми, получится узел с одним, двумя или тремя ключами. У внутреннего такого узла соответственно два, три или четыре дочерних поддерева; у листа детей нет. Один чёрный ключ и до двух красных ключей оказываются в одном узле 2-3-4-дерева.

Эту эквивалентность можно увидеть, "подняв" красные узлы в графическом представлении красно-черного дерева на один уровень с их черными предками, чтобы они образовывали страницу. В B-дереве или в модифицированном графическом представлении красно-черного дерева, у всех листовых узлов глубина одинаковая.

В красно-черное дерево новый узел добавляется на место одного из листьев. Для этого узел окрашивается в красный цвет и к нему прикрепляются два листа. После добавления узла, дальнейшие действия зависят от цвета его близлежащих узлов. Важно отметить, что:

  • Свойство 3 (Все листья черные) всегда выполняется.
  • Свойство 4 (Оба потомка любого красного узла - черные) может быть нарушено только при добавлении красного узла, при перекрашивании черного узла в красный или при повороте.
  • Свойство 5 (Все пути от любого узла до листьев содержат одинаковое число черных узлов) может быть нарушено только при добавлении черного узла, перекрашивании красного узла в черный (или наоборот) или при повороте.

Примечание: Для удобства обозначений, текущий узел, окрашенный в красный цвет, обозначается буквой "N". Изначально это новый узел, который добавляется в дерево, но процедура может быть применена рекурсивно к другим узлам (смотрите случай 3). "P" обозначает предка узла "N", "G" - дедушку, а "U" - дядю (узел, имеющий общего родителя с узлом "P"). Важно отметить, что в некоторых случаях роли узлов могут меняться, но каждое обозначение будет представлять тот же узел. Любой цвет, изображенный на рисунке, либо предполагается в данном случае, либо получается из других соображений.

    shared_ptr<Node> find(shared_ptr<Node> node, T key) {
        while (node) {
            if (key < node->key) node = node->left;
            else if (key > node->key) node = node->right;
            else return node;
        }
        return {};

        while (node && node->left) node = node->left;
        return node;
    }
    shared_ptr<Node> max(shared_ptr<Node> node) {
        while (node && node->right) node = node->right;
        return node;
    }

В этом учебном варианте дерево нельзя копировать или перемещать. Неявная копия shared_ptr-корня дала бы двум объектам общее изменяемое дерево, но отдельные указатели root: поворот при вставке в одну копию мог бы оставить другой объект с прежним корнем и потерянной частью ключей. Для поддержки копирования потребовалась бы отдельная реализация независимой копии всех узлов. После явного запрета копирования и пользовательского объявления деструктора неявные операции перемещения также не создаются.

NIL, владение и границы примера

NIL — отсутствующий ребёнок, который при подсчёте цвета считается чёрным. В коде он представлен пустым shared_ptr; создавать для каждого листа отдельный объект не нужно. Это не итератор end(): конец обхода — другая абстракция.

Дочерние ссылки здесь владеющие, родительская — слабая, поэтому цикл владения «родитель ↔ ребёнок» не возникает. shared_ptr выбран для сохранения локальных владельцев во время перестроек; это учебное решение, а не требование алгоритма или рекомендация использовать разделённое владение во всех деревьях. В предыдущем AVL одна владеющая связь на узел выражена через unique_ptr.

Класс не выдаёт наружу узлы и пока не предоставляет итераторы. При удалении с заменой пары меняется содержимое существующего узла, поэтому переносить на этот код гарантии std::map о сохранении итераторов нельзя. Для int и std::string следующие шаги показывают сам алгоритм баланса; произвольные бросающие сравнения и присваивания потребовали бы отдельной разработки гарантий исключений.

Реализация вставки

Продолжение класса RBT. Все блоки этого шага — определения объявленных там методов. После них и методов удаления из следующего шага получается полная учебная реализация.

Дядя и дедушка текущего узла могут быть найдены с помощью функций:

template<class T, class T1>
shared_ptr<typename RBT<T, T1>::Node> RBT<T, T1>::grandparent(shared_ptr<Node> node) {
    shared_ptr<Node> p = node->parent.lock(); // удерживаем родителя локальным shared_ptr
    if (p && !p->parent.expired()) {
        return p->parent.lock();
    } else {
        return shared_ptr<Node>();
    }
}

template<class T, class T1>
shared_ptr<typename RBT<T, T1>::Node> RBT<T, T1>::uncle(shared_ptr<Node> node) {
    shared_ptr<Node> tmp = grandparent(node);

    if (tmp) {
        if ((tmp->left == node->parent.lock())) {
            return tmp->right;
        } else {
            return tmp->left;
        }
    } else {
        return shared_ptr<Node>();
    }
}

    shared_ptr<Node> right = node->right;

    right->parent = node->parent.lock();
    if (!node->parent.expired()) {
        shared_ptr<Node> p = node->parent.lock();

        if ((p->left == node)) {
            p->left = right;
        } else {
            p->right = right;
        }
    } else {
        root = right;
    }

    node->right = right->left;
    if (right->left) {
        right->left->parent = node;
    }

    node->parent = right;
    right->left = node;
}

void RBT<T, T1>::add(T key, T1 value) {
    shared_ptr<Node> tmp = root, p = shared_ptr<Node>();

    // Спускаемся по дереву, ищя, куда вставить новый узел
    while (tmp) {
        p = tmp;

        if (tmp->key > key) {
            tmp = tmp->left;

            tmp = tmp->right;
        } else {
            return;// Если такой узел уже есть, то прото выходим
        }

    tmp->parent = p;

        if (tmp->key > p->key) {
            p->right = tmp;
        } else {
            p->left = tmp;
        }
    } else {
        root = tmp;
    }

    return;
}

Случай 2: Если предок P текущего узла N является чёрным, то это означает, что Свойство 4 (Оба потомка каждого красного узла — чёрные) не было нарушено. В этом случае дерево остаётся корректным. Свойство 5 (Все пути от любого данного узла до листовых узлов содержат одинаковое число чёрных узлов) также не нарушается, поскольку текущий красный узел N имеет двух чёрных листовых потомков. Каждый из этих потомков имеет такое же число чёрных узлов на пути до листа, как и путь до чёрного листа, который был заменен текущим красным узлом. Следовательно, это свойство по-прежнему верно.

Примечание: Для следующих случаев предполагается наличие дедушки G у узла N, поскольку его родитель P красный. Если бы P был корнем, то он был бы чёрным. Поэтому узел N также имеет дядю U, хотя в случаях 4 и 5 он может быть листовым узлом.

Случай 3: Если и родитель P и дядя U красные, то оба могут быть перекрашены в чёрный, а дедушка G - в красный (чтобы сохранить свойство 5). Теперь у текущего красного узла N чёрный родитель. Поскольку любой путь через родителя или дядю должен проходить через дедушку, число чёрных узлов в этих путях не изменится. Однако ставший красным G может нарушить свойство 2, если он корень, или свойство 4, если родитель G красный, поэтому вся процедура рекурсивно выполняется на G из случая 1 для исправления этой ситуации.

        u->color = 1;
        shared_ptr<Node> g = grandparent(node);
        g->color = 0;
        InsCase1(g);
    } else {
        InsCase4(node);
    }
}

Примечание: Далее предполагается, что родитель P является левым потомком своего предка. Если это не так, необходимо поменять лево и право соответствующих операций. Примеры кода будут учитывать это.

Случай 4: Если родитель P красный, а дядя U черный, и текущий узел N является правым потомком P, а P является левым потомком своего предка G, то можно выполнить поворот дерева, чтобы поменять местами текущий узел N и его родительский узел P. После этого для родительского узла P в новой структуре используется Случай 5, так как Свойство 4 (Оба потомка любого красного узла — чёрные) все еще нарушено. При повороте некоторые пути (в поддереве, обозначенном "1" на схеме) проходят через узел N, чего не было раньше, и некоторые пути (в поддереве, обозначенном "3") больше не проходят через узел P. Однако, оба узла P и N являются красными, поэтому Свойство 5 (Все пути от любого данного узла до листовых узлов содержат одинаковое число чёрных узлов) не нарушается при повороте. Однако, Свойство 4 все еще нарушено, поэтому задача сводится к Случаю 5.

template<class T, class T1>
void RBT<T, T1>::InsCase4(shared_ptr<Node> node) {
    shared_ptr<Node> g = grandparent(node), tmp = node;
    shared_ptr<Node> p = node->parent.lock();
    if ((node == p->right) && (p == g->left)) {
        RotateLeft(p);
        tmp = node->left;
    } else if ((node == p->left) && (p == g->right)) {
        RotateRight(p);
        tmp = node->right;
    }

    InsCase5(tmp);
}

Случай 5: Если родитель P является красным, дядя U черный, текущий узел N является левым потомком P, а P в свою очередь является левым потомком своего предка G, то выполняется поворот дерева вокруг G. Это приводит к тому, что бывший родитель P становится родителем текущего узла N и бывшего дедушки G. Также известно, что G чёрный: P уже красный, поэтому красный G нарушал бы свойство 4 ещё до исправляемой вставки. Затем цвета P и G меняются, что приводит к удовлетворению Свойства 4. Свойство 5 остается верным, так как все пути, которые проходят через любой из этих трех узлов, ранее проходили через G, поэтому теперь они все проходят через P. Кроме того, только один из этих трех узлов окрашен в черный цвет в каждом случае.

template<class T, class T1>
void RBT<T, T1>::InsCase5(shared_ptr<Node> node) {
    shared_ptr<Node> g = grandparent(node);
    shared_ptr<Node> p = node->parent.lock();
    p->color = 1;
    g->color = 0;

    if ((node == p->left)) {
        RotateRight(g);
    } else {
        RotateLeft(g);
    }
}

Разобранный случай 10, 20, 30

10 становится чёрным корнем. 20 добавляется красным справа; его родитель чёрный, поэтому исправления нет. При добавлении 30 появляются соседние красные 20 и 30, а дядя отсутствует и считается чёрным. Это внешний правый случай: левый поворот вокруг 10 и обмен цветов дают чёрный корень 20 с красными детьми 10 и 30. Порядок 10 < 20 < 30 и одинаковая чёрная высота сохранены.

При красном дяде поворот не нужен: перекрашивание поднимает возможное нарушение к дедушке. Поэтому число перекрашиваний может расти как O(log n), хотя в этом алгоритме вставка использует не более двух поворотов.

Реализация удаления

Продолжение той же реализации RBT. Сначала BST-удаление сводит задачу к узлу с не более чем одним настоящим ребёнком. Затем исправляется нехватка одного чёрного узла на путях через удалённую ветвь. Это средство рассуждения, а не третий цвет, хранимый в коде.

Далее даны подробные зеркальные случаи. Их цель — восстановить равное число чёрных узлов на путях и запрет соседних красных, сохранив порядок ключей.

При удалении узла с двумя нелистовыми потомками в обычном двоичном дереве поиска мы ищем либо наибольший элемент в его левом поддереве, либо наименьший элемент в его правом поддереве и копируем его ключ и связанное значение в удаляемый узел. Затем удаляем узел-источник. Копирование значения из одного узла в другой не нарушает цветовых инвариантов, так как структура дерева и цвета узлов не изменяются. Стоит заметить, что новый удаляемый узел не может иметь сразу два дочерних нелистовых узла, так как в противном случае он не будет являться наибольшим/наименьшим элементом. Таким образом, получается, что случай удаления узла, имеющего два нелистовых потомка, сводится к случаю удаления узла, содержащего как максимум один дочерний нелистовой узел. Поэтому дальнейшее описание будет исходить из предположения существования у удаляемого узла не более одного нелистового потомка.

В эту текстовую часть можно сильно не вникать, и быстро пробежав переходить к случаям с картинками, потому что запутаться тут довольно просто. После можете обращаться сюда, если совсем не будете понимать рассматриваемые случаи.

Будем использовать обозначение M для удаляемого узла; через C обозначим потомка M, который также будем называть просто «его потомок». Если M имеет нелистового потомка, возьмем его за C. В противном случае за C возьмем любой из листовых потомков.

Если M является красным узлом, заменим его своим потомком C, который по определению должен быть чёрным. (Это может произойти только тогда, когда M имеет двух листовых потомков, потому что если красный узел M имеет чёрного нелистового потомка с одной стороны, а с другой стороны — листового, то число чёрных узлов на обеих сторонах будет различным, таким образом дерево станет недействительным красно-чёрным деревом из-за нарушения Свойства 5.) Все пути через удаляемый узел просто будут содержать на один красный узел меньше, предок и потомок удаляемого узла должны быть чёрными, так что Свойство 3 («Все листья — чёрные») и Свойство 4 («Оба потомка красного узла — чёрные») все ещё сохраняется.

Другим простым является случай, когда M — чёрный и C — красный. Простое удаление чёрного узла может нарушить Свойство 4 («Оба потомка красного узла — чёрные») и Свойство 5 («Всякий простой путь от данного узла до любого листового узла, содержит одинаковое число чёрных узлов»), но если мы перекрасим C в чёрный, оба эти свойства сохранятся.

Сложным является случай, когда и M и C — чёрные. (Это может произойти только тогда, когда удаляется чёрный узел, который имеет два листовых потомка, потому что если чёрный узел M имеет чёрного нелистового потомка с одной стороны, а с другой — листового, то число чёрных узлов на обеих сторонах будет различным и дерево станет недействительным красно-чёрным деревом из-за нарушения Свойства 5.) Мы начнём с замены узла M своим потомком C. Будем называть этого потомка (в своем новом положении) N, а его «брата» (другого потомка его нового предка) — S. (До этого S был «братом» M.) На рисунках ниже мы также будем использовать обозначение P для нового предка N (старого предка M), SL для левого потомка S и SR для правого потомка S (S не может быть листовым узлом, так как если N по нашему предположению является чёрным, то поддерево P, которое содержит N, чёрной высоты два и поэтому другое поддерево P, которое содержит S должно быть также чёрной высоты два, что не может быть в случае, когда S — лист).

Примечание: В некоторых случаях мы меняем роли и обозначения узлов, но в каждом случае любое обозначение продолжает означать тот же узел, что и в начале случая. Любые цвета, изображенные на рисунке либо предполагаются случаем, либо получаются из других предположений. Белый означает неизвестный цвет (либо красный, либо чёрный).

Будем искать «брата», используя эту функцию:

template<class T, class T1>
shared_ptr<typename RBT<T, T1>::Node> RBT<T, T1>::sibling(shared_ptr<Node> node) {
    if (node->parent.expired()) {
        return shared_ptr<Node>();
    }

    shared_ptr<Node> p = node->parent.lock();

    if ((node == p->left)) {
        return p->right;
    } else {
        return p->left;
    }
}

Примечание: Для того, чтобы дерево оставалось верно определенным, нам нужно, чтобы каждый лист оставался листом после всех преобразований (чтобы у него не было потомков). Если удаляемый нами узел имеет нелистового потомка N, легко видеть, что свойство выполняется. С другой стороны, если N — лист, то, как можно увидеть из рисунков или кода, свойство также выполняется.

Мы можем выполнить действия, описанные выше, используя следующий код.

template<class T, class T1>
void RBT<T, T1>::remove(T key) {
    shared_ptr<Node> tmp = root ? find(root, key) : shared_ptr<Node>(); // Ищем узел с нужным ключем
    // Повезло повезло, ниче делать не надо если такого узла нет
    if (!tmp) {
        return;
    }

    // Случай, когда дерево состоит из одного узла
    if (tmp->parent.expired() && !tmp->left && !tmp->right) {
        root = shared_ptr<Node>(); // Обнуляем корень
        return;
    }

    // Если у узла есть и левый и правый потомок
    if (tmp->left && tmp->right)  {
        // Ищем самый правый узел в левом поддереве
        // Этот узел будет ближайшим меньшим к удаляемому, по значнию ключа
        // Что дает нам возможность переместить его значение в удаляемый узел, и удалять уже новый, но у которого будет либо один, либо ноль потомков
        // При таком способе прийдется рассматривать намного меньшее количество вариантов
        shared_ptr<Node> removed = tmp->left;
        while (removed->right) {
            removed = removed->right;
        }
        tmp->data = removed->data;
        tmp->key = removed->key;
        tmp = removed;
    }
    shared_ptr<Node> child = tmp->left ? tmp->left : tmp->right; 
    // Ищем потомка, если таково имеется
    // Случай, когда потомков нет
    if (!child) {
        if (tmp->color) {// Удаление красного узла не привело бы к разбалансировке дерева
            DelCase1(tmp); // А вот удаление черного узла нарушает свойства красно-черного дерева об одинаковой длинне черных путей
        }
        shared_ptr<Node> p = tmp->parent.lock();

        if ((p->left == tmp)) {// Меняем связи, тем самым удаляя узел, после чего тот выйдет из области видимости
            p->left = child;
        } else {
            p->right = child;
        }
    }
    // Случай, когда потомок есть
    else {
        child->parent = tmp->parent.lock(); // Меняем связи
        shared_ptr<Node> p = tmp->parent.lock();

        // Меняем связи
        if (!tmp->parent.expired()) {
            if ((tmp == p->left)) {
                p->left = child;
            } else {
                p->right = child;
            }
        } else {
            root = child; // Если надо, меняем корень дерева
        }
        // Если удаляемы узел был красным, то никакие свойства не нарушаются
        if (tmp->color) {
            if (!child->color) {// Если удаляемый узел был черным, а потомок красный, то можем сохранить свойстав дерева, перекрасив потомка в черныйё
                child->color = 1;
            } else {
                DelCase1(child);
            }
        }
    }
}

Примечание: в приведённом коде NIL-листья представлены пустыми указателями. В трудном случае удаляемый чёрный узел n сам служит временным представителем ветви с недостатком чёрного узла: сначала вызывается DelCase1(n), затем n отсоединяется. Поэтому для балансировки не требуется создавать отдельный NIL-объект. На схемах N обозначает исправляемую ветвь; внутри каждого случая обозначения сохраняются.

После удаления чёрного узла M пути через заменивший его N имеют на один чёрный узел меньше, чем раньше. В сложном случае N также чёрный (вначале это NIL-лист), и одной перекраски N недостаточно. Нужно восстановить одинаковую чёрную высоту ветвей. Рассмотрим следующие случаи:

Случай 1: N — новый корень. В этом случае, все сделано. Мы удалили один чёрный узел из каждого пути и новый корень является чёрным узлом, так что свойства сохранены.

template<class T, class T1>
void RBT<T, T1>::DelCase1(shared_ptr<Node> node) {
    if (!node->parent.expired()) {
        DelCase2(node);
    }
}

Примечание: В случаях 2, 5, и 6 мы предполагаем, что N является левым потомком своего предка P. Если он — правый потомок, left и right нужно поменять местами во всех трех случаях. Опять-таки, примеры кода принимают это во внимание.

Случай 2: S — красный. В этом случае мы меняем цвета P и S, и затем делаем вращение влево вокруг P, ставя S дедушкой N. Нужно заметить, что P должен быть чёрным, если он имеет красного потомка. Результирующее поддерево всё равно имеет черных узлов на единицу меньше, поэтому на этом мы ещё не закончили. Теперь N имеет чёрного брата и красного отца, поэтому мы можем перейти к шагу 4, 5 или 6. (Его новый брат является чёрным потому, что он был потомком красного S.)

Далее через S будет обозначен новый брат N.

template<class T, class T1>
void RBT<T, T1>::DelCase2(shared_ptr<Node> node) {
    shared_ptr<Node> s = sibling(node);
    shared_ptr<Node> p = node->parent.lock();
    bool scol = s ? s->color : 1;

    if (!scol) {
        p->color = 0;
        s->color = 1;

        if ((node == p->left)) {
            RotateLeft(p);
        } else {
            RotateRight(p);
        }
    }

    DelCase3(node);
}

Случай 3: P, S, и дети S — чёрные. В этом случае мы просто перекрашиваем S в красный. В результате все пути, проходящие через S, но не проходящие через N, имеют на один чёрный узел меньше. Так как удаление исходного чёрного узла M уменьшило на один число чёрных узлов на путях через N, то такие действия выравнивают баланс. Тем не менее, все проходящие через P пути теперь содержат на один чёрный узел меньше, чем пути, которые через P не проходят, поэтому свойство 5 (все пути из любой вершины к её листовым узлам содержат одинаковое количество чёрных узлов) все ещё нарушено. Чтобы это исправить, мы применяем процедуру перебалансировки к P, начиная со случая 1.

template<class T, class T1>
void RBT<T, T1>::DelCase3(shared_ptr<Node> node) {
    shared_ptr<Node> s = sibling(node);
    shared_ptr<Node> p = node->parent.lock();

    bool scol = s ? s->color : 1;
    bool lcol = s && s->left ? s->left->color : 1;
    bool rcol = s && s->right ? s->right->color : 1;

    if (p->color && scol && lcol && rcol) {
        if (s) {
           s->color = 0;
        }
        DelCase1(p);
    } else {
        DelCase4(node);
    }
}

Случай 4: S и его дети — чёрные, но P — красный. В этом случае мы просто меняем цвета S и P. Это не влияет на количество чёрных узлов на путях, проходящих через S, но добавит один к числу чёрных узлов на путях, проходящих через N, восстанавливая тем самым влияние удаленного чёрного узла.

template<class T, class T1>
void RBT<T, T1>::DelCase4(shared_ptr<Node> node) {
    shared_ptr<Node> s = sibling(node);
    shared_ptr<Node> p = node->parent.lock();

    bool scol = s ? s->color : 1;
    bool lcol = s && s->left ? s->left->color : 1;
    bool rcol = s && s->right ? s->right->color : 1;

    if (!p->color && scol && lcol && rcol) {
        if (s) {
            s->color = 0;
        }
        p->color = 1;
    } else {
        DelCase5(node);
    }
}

Случай 5: S — чёрный, левый потомок S — красный, правый потомок S — чёрный, и N является левым потомком своего отца. В этом случае мы вращаем дерево вправо вокруг S. Таким образом левый потомок S становится его отцом и новым братом N. После этого мы меняем цвета у S и его нового отца. Все пути по-прежнему содержат одинаковое количество чёрных узлов, но теперь у N есть чёрный брат с красным правым потомком, и мы переходим к случаю 6. Ни N, ни его отец не влияют на эту трансформацию. (Для случая 6 мы обозначим через S нового брата N.)

template<class T, class T1>
void RBT<T, T1>::DelCase5(shared_ptr<Node> node) {
    shared_ptr<Node> s = sibling(node);
    shared_ptr<Node> p = node->parent.lock();

    bool lcol = s->left ? s->left->color : 1;
    bool rcol = s->right ? s->right->color : 1;

    if (s->color) {
        if ((node == p->left) && rcol && !lcol) {
            s->color = 0;
            s->left->color = 1;
            RotateRight(s);
        } else if ((node == p->right) && lcol && !rcol) {
            s->color = 0;
            s->right->color = 1;
            RotateLeft(s);
        }
    }

    DelCase6(node);
}

Случай 6: S — чёрный, правый потомок S — красный, и N является левым потомком своего отца P. В этом случае мы вращаем дерево влево вокруг P, после чего S становится отцом P и своего правого потомка. Далее мы меняем местами цвета у P и S (P принимает цвет S, S принимает цвет P), и делаем правого потомка S чёрным. Поддерево по-прежнему имеет тот же цвет корня, поэтому свойства 4 (Оба потомка каждого красного узла — чёрные) и 5 (все пути из любой вершины к её листовым узлам содержат одинаковое количество чёрных узлов) не нарушаются. Тем не менее, у N теперь появился дополнительный чёрный предок: либо P стал чёрным, или он был чёрным и S был добавлен в качестве чёрного дедушки. Таким образом, проходящие через N пути проходят через один дополнительный чёрный узел.

Между тем, если путь не проходит через N, то есть 2 возможных варианта:

  • Он проходит через нового брата N. Тогда, он должен проходить через S и P, которые просто поменяли цвета и места. Поэтому путь содержит то же количество чёрных узлов.
  • Он проходит через нового дядю N, правого потомка S. Когда-то он проходил через S, отца S и правого потомка S (который был красным), но теперь он проходит только через S, который принял на себя цвет своего прежнего родителя, и правого потомка S, который был перекрашен из красного в чёрный (Предполагаем, что цвет S: чёрный). Эффект заключается в том, что этот путь проходит через такое же количество чёрных узлов.

В любом случае, число чёрных узлов на этих путях не изменится. Поэтому, мы восстановили свойства 4 (Оба потомка каждого красного узла — чёрные) и 5 (все пути из любой вершины к её листовым узлам содержат одинаковое количество чёрных узлов). Белый узел на диаграмме может быть как красным так и чёрным, но должен указывать на тот же цвет как в начале, так и в конце трансформации.

template<class T, class T1>
void RBT<T, T1>::DelCase6(shared_ptr<Node> node) {
    shared_ptr<Node>  s = sibling(node);
    shared_ptr<Node> p = node->parent.lock();
    s->color = p->color;
    p->color = 1;

    if ((node == p->left)) {
        if (s->right) {
            s->right->color = 1;
        }
        RotateLeft(p);
    } else {
        if (s->left) {
            s->left->color = 1;
        }
        RotateRight(p);
    }
}

Приведённая рекурсивная реализация может занимать O(log n) дополнительной памяти стека. C++ не гарантирует устранение хвостовых вызовов; здесь локальные shared_ptr также должны уничтожаться при возврате. Итеративная реализация с явным переходом между случаями может использовать O(1) дополнительной памяти. В последовательности случаев возврат к случаю 1 происходит из случая 3 для предка текущего узла.

Рекурсивный переход к случаю 1 выполняется к родителю, а не к потомку; поэтому продвижение идёт вверх по дереву. Произойдет не более чем O(log n) циклических возвратов к случаю 1 (где n — общее количество узлов в дереве до удаления). Если в случае 2 произойдет вращение (единственно возможное в цикле случаев 1-3), тогда отец узла N становится красным после вращения и мы выходим из цикла. Таким образом будет произведено не более одного вращения в течение этого цикла. После выхода из цикла произойдет не более двух дополнительных поворотов. А в целом произойдет не более трех поворотов дерева.

Разобранный переход: чёрный узел с красным ребёнком

Пусть после вставки 10, 20, 30 получено чёрное 20 с красными листьями 10 и 30. Удаление 10 просто убирает красный лист. Если затем удалить 20, его единственный настоящий ребёнок 30 заменяет корень и становится чёрным. Чёрная высота сохраняется; сложные случаи с братом не нужны.

При удалении чёрного листа без настоящих детей код временно оставляет этот узел на месте как представителя будущей пустой ветви, выполняет DelCase1 и только затем отсоединяет узел. Поэтому рисунок с NIL и код с временным настоящим узлом описывают одну нехватку чёрной высоты. Восстановление идёт к предкам; к завершению все пять инвариантов снова выполнены.

Имена ключей и значений копируются вместе, но данная реализация не обещает сильной гарантии исключений для произвольных типов. В следующем шаге отдельно рассмотрен контракт обхода; его нельзя добавлять к этим методам случайными связями, не проверяя время жизни и операции удаления.

Обход дерева и граница end()

Симметричный обход BST посещает ключи по возрастанию. Нужны порядки обхода, понятие диапазона [begin, end) и время жизни узлов. Здесь обсуждается алгоритм итерации; неполные методы не добавляются к предыдущему классу RBT.

Как найти следующий узел

  1. Если у текущего узла есть правое поддерево, следующий — его самый левый узел.
  2. Иначе поднимаемся по родителям, пока идём из правого ребёнка: эти предки уже посещены.
  3. Первый родитель, к которому пришли из левого ребёнка, — следующий.
  4. Если такого родителя нет, текущий ключ был наибольшим: достигнут конец обхода.

Это полный алгоритм поиска преемника при корректных родительских связях. Предшественник определяется зеркально. Например, в дереве с корнем 20 и листьями 10, 30 после 10 идёт его родитель 20; после 20 — минимум правого поддерева 30; после 30 подходящего предка нет.

Один переход может пройти O(h) рёбер. Полный обход n узлов требует O(n) переходов по рёбрам в сумме: ребро используется ограниченное число раз. Поэтому последовательный обход имеет амортизированную постоянную стоимость перехода; это не обещание O(1) для каждого отдельно взятого ++.

Конец диапазона не является ключом

end() обозначает позицию после последнего элемента. Её нельзя разыменовывать или увеличивать. Для непустого двунаправленного диапазона --end() даёт последний элемент; --begin() недопустим. У пустого контейнера begin() == end().

Внутреннее представление конца может содержать пустой указатель вместе с указателем на контейнер, служебный заголовок или иной маркер. Стандарт не требует «фантомного ключа» и не требует временно отсоединять его перед каждой вставкой. Такой маркер также нельзя смешивать с NIL-листом цветовой модели.

Разобранная программа со стандартным интерфейсом

Полная программа C++17/20 использует std::map. Она показывает именно договор обхода; устройство его узлов не требуется.

#include <iostream>
#include <map>
#include <string>

int main() {
    const std::map<int, std::string> labels{{20, "B"}, {10, "A"}, {30, "C"}};
    for (auto it = labels.begin(); it != labels.end(); ++it) {
        std::cout << it->first << ':' << it->second << ' ';
    }
    std::cout << '\n';
    auto last = labels.end();
    if (!labels.empty()) {
        --last;
        std::cout << last->first << '\n';
    }
}

Вывод: 10:A 20:B 30:C, затем 30. Проверка пустоты нужна перед --end(). Проверка it != end() предшествует каждому разыменованию.

Собственный итератор дополнительно обязан определить принадлежность контейнеру, время жизни, правила инвалидирования, допустимые операции и результат разыменования. В предыдущем учебном RB удаление с копированием пары меняет ключ существующего узла; поэтому он пока не предоставляет итераторы с гарантиями std::map. У стандартного ассоциативного контейнера удаление сохраняет итераторы на остальные элементы — это самостоятельное требование к реализации.

Далее хеш-таблица предложит доступ по ключу без отсортированного обхода. Разница между интерфейсом и устройством снова определит выбор.

Хеш-код, индекс корзины и равенство

Разделим два действия: h(key) получает хеш-код, а index = h(key) % m в простой учебной схеме выбирает одну из m > 0 корзин. Стандартная библиотека не обязана использовать именно это вычисление индекса.

Согласованность хеша и равенства — часть контракта: если ключи считаются равными, их хеш-коды должны совпадать. Обратное неверно: равный хеш не доказывает равенство ключей. Например, при сравнении строк без учёта регистра нельзя оставить хеш, различающий A и a.

Равномерность — желательное свойство распределения для выбранных данных, а не доказательство отсутствия коллизий. Хеш контейнера также не является криптографической защитой. Коллизии, заполнение и стоимость

Коллизия хеш-кодов означает одинаковый код у разных ключей. Даже при разных кодах редукция к конечному числу корзин может дать один индекс. В обоих случаях таблица должна сохранить все различные ключи и уметь отличить их при поиске.

Метод цепочек

Корзина хранит последовательность записей. В примере с четырьмя корзинами ID 1, 5, 9 образуют цепочку в корзине 1. Поиск 5 просматривает записи и сравнивает ID; замена имени для 5 обновляет только эту запись. Считать одинаковый индекс дубликатом было бы ошибкой.

Пусть n — число элементов, m — число корзин. Коэффициент заполнения α = n / m — среднее число записей на корзину, а не доля непустых корзин. Для метода цепочек α может быть больше 1. При подходящем распределении поиск занимает ожидаемо O(1 + α) сравнений, в худшем случае вся таблица попадает в одну цепочку и поиск занимает O(n).

Открытая адресация

Записи хранятся непосредственно в массиве. Линейное пробирование при занятой позиции последовательно проверяет следующие с циклическим переходом через конец. Оно должно различать существующий ключ, подходящее место для вставки и отсутствие ключа. Длинные скопления занятых ячеек ухудшают поиск; перед заполнением таблицу расширяют.

Удаление нельзя свести к пометке ячейки «никогда не использовалась»: это оборвало бы поиск элементов, сдвинутых туда прежней коллизией. Применяют отдельную метку удалённой ячейки или алгоритм восстановления цепочки пробирования. Одна проба не должна бесконечно обходить заполненный массив: число просмотренных позиций ограничено.

Перестройка

При изменении m все записи заново размещаются по новому правилу индекса. Простое увеличение массива без переноса оставит элементы в неверных корзинах. Один rehash требует прохода по записям и может быть дорогим; стратегия редких увеличений ёмкости позволяет распределить эту стоимость на много вставок.

Для цепочек нет физического ограничения «одна запись на корзину», но рост α ухудшает ожидаемый поиск. Для открытой адресации нужна свободная ёмкость и своя политика нагрузки. Эти методы нельзя оценивать одной формулой без указания предпосылок. Далее дан законченный пример цепочек.

Инварианты: каждый ID встречается не более одного раза; запись находится в корзине id % m; число элементов отличается от числа корзин и от числа непустых корзин. Внутренние записи наружу не выдаются, поэтому внешний код не может изменить ключ, не переместив запись.

Копирование контейнеров создаёт независимые записи; специальный деструктор и ручной delete не нужны — это правило нуля. После перемещения объект может иметь ноль корзин; методы следующего шага учитывают это и позволяют повторное использование. Учебная таблица не увеличивается автоматически: rehash вызывается явно, поэтому поддержание низкого α — часть условия её ожидаемой эффективности.

Цепочки: полная реализация и разбор

Здесь весь заголовок hash_table.hpp и использующая его программа C++17/20. Все объявленные операции определены; скрытых методов списка и отдельного ручного освобождения памяти нет.

hash_table.hpp

#pragma once
#include <cstddef>
#include <list>
#include <optional>
#include <stdexcept>
#include <string>
#include <utility>
#include <vector>

class ItemTable {
    struct Entry {
        std::size_t id;
        std::string name;
    };
    std::vector<std::list<Entry>> buckets_;

public:
    explicit ItemTable(std::size_t bucket_count = 8) : buckets_(bucket_count) {
        if (bucket_count == 0) throw std::invalid_argument("zero buckets");
    }
    // Copying and moving are provided by the owning standard containers.
    std::size_t bucket_count() const { return buckets_.size(); }
    std::size_t size() const {
        std::size_t result = 0;
        for (const auto& bucket : buckets_) result += bucket.size();
        return result;
    }
    double load_factor() const {
        return buckets_.empty() ? 0.0
            : static_cast<double>(size()) / static_cast<double>(buckets_.size());
    }
    // true: a new ID; false: replacement of an existing name.
    bool insert_or_assign(std::size_t id, std::string name) {
        // A moved-from table can have no buckets; reuse remains valid.
        if (buckets_.empty()) buckets_.resize(8);
        auto& bucket = buckets_[id % buckets_.size()];
        for (auto& entry : bucket) {
            if (entry.id == id) {
                entry.name = std::move(name);
                return false;
            }
        }
        bucket.push_back(Entry{id, std::move(name)});
        return true;
    }
    std::optional<std::string> find(std::size_t id) const {
        if (buckets_.empty()) return std::nullopt;
        const auto& bucket = buckets_[id % buckets_.size()];
        for (const auto& entry : bucket) {
            if (entry.id == id) return entry.name;
        }
        return std::nullopt;
    }
    bool erase(std::size_t id) {
        if (buckets_.empty()) return false;
        auto& bucket = buckets_[id % buckets_.size()];
        for (auto it = bucket.begin(); it != bucket.end(); ++it) {
            if (it->id == id) {
                bucket.erase(it);
                return true;
            }
        }
        return false;
    }
    void rehash(std::size_t bucket_count) {
        if (bucket_count == 0) throw std::invalid_argument("zero buckets");
        std::vector<std::list<Entry>> replacement(bucket_count);
        for (const auto& bucket : buckets_) {
            for (const auto& entry : bucket) {
                replacement[entry.id % bucket_count].push_back(entry);
            }
        }
        buckets_.swap(replacement);
    }
};

Что происходит при операциях

insert_or_assign сначала ищет равный ID в выбранной цепочке. Совпавшая корзина не означает совпадения ключей. Для нового ID запись добавляется в конец списка; для прежнего меняется только имя. find возвращает копию строки: последующий rehash или удаление не сделают найденное значение висячей ссылкой.

rehash строит временный набор корзин и копирует в него записи по новому индексу. Если выделение памяти или копирование строки не удалось, старый набор ещё не изменён. Обмен контейнеров выполняется после успешного заполнения. Это простая гарантия для данного варианта с обычными стандартными аллокаторами, ценой временного хранения второй копии.

Число элементов вычисляется суммой размеров списков. Поэтому size() и load_factor() стоят O(m) по числу корзин; у std::unordered_map::size() другая, константная гарантия. Кэширование счётчика ускорило бы запрос, но потребовало бы поддерживать ещё один инвариант при каждой мутации и перемещении. Здесь этот выбор сделан явно ради простоты.

hash_demo.cpp

#include "hash_table.hpp"
#include <iostream>

int main() {
    ItemTable items(4);
    items.insert_or_assign(1, "pencil");
    items.insert_or_assign(5, "notebook");
    items.insert_or_assign(9, "ruler");
    items.insert_or_assign(5, "book");
    std::cout << items.size() << ' ' << items.load_factor() << '\n';
    if (const auto name = items.find(5)) std::cout << *name << '\n';
    items.rehash(8);
    items.erase(1);
    std::cout << items.size() << ' ' << items.bucket_count() << '\n';
    std::cout << std::boolalpha << items.find(1).has_value() << '\n';
}

При m = 4 ключи 1, 5, 9 находятся в одной корзине. Обновление 5 оставляет три элемента, поэтому первые строки вывода — 3 0.75 и book. После rehash(8) ключи 1 и 9 находятся в корзине 1, а 5 — в корзине 5. Удаление 1 оставляет две записи: далее выводятся 2 8 и false.

Поиск и удаление просматривают одну цепочку: ожидаемо O(1 + α) при подходящем распределении, в худшем O(n). Вставка включает такой же поиск и создание либо замену строки. Rehash в этой реализации требует O(mстарое + mновое + n) операций над контейнерами плюс копирование текста. Простое id % m и отсутствие автоматического роста не дают универсальной гарантии O(1).

Этот класс иллюстрирует алгоритм, а не заменяет библиотечный контейнер: нет настраиваемого хеша, компаратора равенства и итераторов. В следующем модуле std::unordered_map предоставляет готовый интерфейс, управление нагрузкой и собственные гарантии инвалидирования. Их следует читать как контракт стандарта, не выводить из устройства нашего примера.
