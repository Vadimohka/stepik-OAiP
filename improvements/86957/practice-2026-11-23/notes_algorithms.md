## Учебная связь

Пакет опирается на подготовленные объяснения в
`../quality-2026-11-23/steps/770595/` и `../quality-2026-11-23/steps/771129/`.
В частности, используются понятия устойчивости, строгого компаратора,
полуинтервала, нижней границы и отдельного учёта подготовки данных.
Эти объяснения также имеют статус подготовленных материалов: наличие файлов
пакет опубликован, а все изменённые шаги прочитаны обратно через API.

Структуры подробно вводятся позднее в курсе. Поэтому условие сортировки содержит
короткую объяснённую заготовку `struct Record` и обычную функцию сравнения.
Знание лямбд, контейнеров `map`/`set` или продвинутого обобщённого программирования
не требуется. Проверяемый навык — правильно выбрать ключ и сохранить порядок
равных ключей. Python-словарь в авторском оракуле не предъявляется ученику.

## Контракт задачи о сортировке

Вход: `n`, затем `n` пар `priority label`, где `0 ≤ n ≤ 100000`,
оба поля — целые числа в диапазоне `[-1000000000, 1000000000]`.
Метки не обязаны быть уникальными. Совпадение обеих частей записи не даёт
основания удалять повторное вхождение.

Выход содержит ровно те же `n` записей, упорядоченных по возрастанию `priority`.
Внутри каждого значения `priority` последовательность меток совпадает с входной.
В пустом результате нет чисел; наличие или отсутствие завершающего перевода
строки несущественно. Пробельные разделители произвольны.

Эталоны:

- `examples/stable_records.cpp`: `std::stable_sort` с обычной функцией-компаратором;
- `examples/stable_records_index.cpp`: `std::sort` по паре критериев
  «приоритет, исходная позиция».

Для `std::stable_sort` стандарт гарантирует устойчивость. Оценка количества
сравнений зависит от доступной дополнительной памяти: при достаточной памяти —
`N log N`, иначе — не более `N log² N`. Поэтому условие не приписывает
`stable_sort` безусловную гарантию `O(N log N)` при любой доступной памяти.
Для варианта с явным индексом `std::sort` гарантирует `O(N log N)` сравнений.
Ссылки: [stable.sort](https://eel.is/c++draft/stable.sort),
[sort](https://eel.is/c++draft/sort).

В наборе 23 случая, из них один образец. Есть пустой и единичный вход,
полностью одинаковые записи, одинаковые ключи с разными метками,
повторяющиеся метки при разных ключах, отрицательные числа, крайние значения,
уже отсортированные и обратные данные, детерминированно сгенерированные случаи
и три входа длины 100000. Случай `max_equal` сохраняет обратный порядок меток,
поэтому сортировка по метке не может случайно выглядеть правильной.

## Контракт задачи о поиске

Вход: `n q`, затем `n` элементов отсортированной по неубыванию последовательности
и `q` ключей. Обе длины находятся в `[0, 100000]`, все значения — в
`[-1000000000, 1000000000]`. Пустая последовательность допустима, а при `q = 0`
запросов нет. Наличие или отсутствие пустой строки не имеет семантического
значения: ввод читается по токенам.

Выход: ровно `q` целых чисел — первый нулевой индекс либо `-1`, в порядке
запросов. После поиска границы обязательно проверяется конец диапазона и
равенство найденного значения ключу. Обращения к `a[0]` при `n = 0` нет.

Эталоны:

- `examples/first_index.cpp`: `std::lower_bound` и проверка существования;
- `examples/first_index_manual.cpp`: ручной двоичный поиск на `[left, right)`.

На `std::vector` поиск даёт логарифмическое число сравнений. В условии отдельно
учтены чтение `n` элементов, чтение и вывод `q` запросов. Проверка `is_sorted`
перед каждым запросом не нужна, поскольку сортировка гарантирована входным
контрактом. Ссылки: [lower.bound](https://eel.is/c++draft/lower.bound),
[alg.binary.search](https://eel.is/c++draft/alg.binary.search),
[is.sorted](https://eel.is/c++draft/is.sorted).

В наборе 22 случая, из них три образца. Покрыты пустая последовательность,
нулевое количество запросов, один и два элемента, группы повторов в начале
и конце, отсутствующие ключи внутри промежутков и за границами, крайние
целые значения, повторные запросы, смешанные входы и предельные длины.

## Реальная схема проверяющей программы

В текущем экспорте этого курса `block.source` у code-шагов содержит `code`,
`execution_time_limit`, `execution_memory_limit`, `samples_count`,
`templates_data`, флаги масштабирования и запуска, ручные лимиты,
`test_archive` и `test_cases`. Мы сохраняем эту схему без новых API-полей.

В официальном открытом исходном коде плагина Stepik `CodeQuiz.get_tests()`
получает список пар `(dataset, clue)` от `generate()`, вызывает `solve(dataset)`
и проверяет ответ через механизм `check(reply, clue)`. Первые случаи образуют
образцы; допускается от 1 до 100 случаев. Свойство `code_templates` разбирает
строки `::<language>` и подставляет стандартную заготовку, если тело пусто.
Источник:
[StepicOrg/stepik-plugins, code/__init__.py](https://github.com/StepicOrg/stepik-plugins/blob/master/stepic_plugins/quizzes/code/__init__.py).

Это публичный исходный код плагина, а не доказательство текущей серверной версии
Stepik. Дополнительно проверена реальная экспортная практика самого курса:
`courses/86957/steps/778426/10_4927308_code.step` использует генератор при пустом
`source.test_cases`. Общая справка:
[Stepik, практические задания](https://help.stepik.org/article/54796).

Для каждого нового задания:

- `source.code` дословно совпадает с соответствующим файлом `graders/*.py`;
- `generate()` детерминированно возвращает полный список пар «вход, ответ»;
- `source.test_cases = []` и `source.test_archive = []`, чтобы не дублировать
  генерируемые случаи и не оставлять тесты прежней задачи;
- `options.samples` совпадают с первыми `samples_count` парами;
- `solve()` выдаёт проверяемый ответ; для поиска авторский оракул использует
  словарь первых позиций, независимо от бинарного алгоритма C++;
- `check()` сравнивает количество и значения целочисленных токенов, допускает
  произвольные пробельные разделители, ведущие нули и знак `+`, отвергает
  вещественную запись, лишние числа и недостающие значения;
- лимиты, доступные языки, шаблоны и флаги запуска сохранены: 2 с / 32 MiB
  для сортировки и 1 с / 32 MiB для поиска; образцов по-прежнему 1 и 3;
- прежний URL `block.tests_archive` сохранён как метаданные того же шага.

## Воспроизведение локальной проверки

Из корня репозитория:

```bash
python3 improvements/86957/practice-2026-11-23/verify.py
```

Для изучения каждого входа и ответа используйте пустой каталог вне репозитория:

```bash
python3 improvements/86957/practice-2026-11-23/verify.py \
  --testdata /tmp/stepik-86957-practice-testdata
```

Скрипт создаст `index.json` и пары файлов
`<step_id>/<number>_<case_name>.in` / `.out` в UTF-8. Поля `input_sha256`,
`answer_sha256` и длины в байтах должны совпасть с `cases.json` в пакете.
Это также формат для независимого запуска любых других решений. Без
`--testdata` временные входы и исполняемые файлы удаляются после проверки.

Основной отчёт — `validation.json`. Сразу при запуске он получает
`status: running` и `all_passed: false`; неуспех меняет состояние на `failed`.
Только после завершения всех проверок записывается `passed` / `true`.
Сохраняются SHA256 всех проверяемых исходников, шагов и каталога случаев,
версия компилятора, фактические счётчики выполненных проверок и контрпример
для каждого намеренно неверного C++-решения.

Полные эталоны собираются в C++17 и C++20 с
`-O2 -Wall -Wextra -Wpedantic -Werror`. Каждый из четырёх эталонов выполняется
на всех случаях своей задачи в обоих стандартах: 180 запусков. Проверяются
11 неверных решений: удаление равных ключей или одинаковых записей, обратный
порядок равных ключей, сортировка по метке, убывающая сортировка, последнее
либо произвольное вхождение, индексация с единицы, позиция вставки вместо
признака отсутствия, ответ 0 для пустого входа и ответ 0 для отсутствующего
ключа. Для каждого требуется отказ хотя бы на одном **скрытом** случае,
после исключения публичных образцов.

Проверяющий скрипт отдельно сравнивает ответы с независимыми локальными
оракулами: группировкой записей и `bisect_left`. Пробы checker проверяют
правильное число токенов, пробелы, альтернативную запись целых чисел,
ошибочные значения и пустой результат.

Есть отдельные таймауты компиляции, генерации/оракулов и запуска решения.
По умолчанию это 45, 45 и 5 секунд. Они защищают локальную проверку от зависания
и **не подменяют** лимиты 1/2 секунды на Stepik. Локальная проверка не
воспроизводит контейнеры, ограничения памяти, язык `c++` конкретной серверной
версии или сохранённые результаты учащихся. Она также не доказывает
асимптотическую сложность произвольного решения по конечному набору тестов.
