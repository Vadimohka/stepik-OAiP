<h3>Библиотека: интерфейс, реализация и зависимость</h3>
<p>Библиотека объединяет средства для некоторой области: функции, типы и другие объявления вместе с необходимой реализацией. Пользователь работает через интерфейс и его контракт, а детали вычисления могут меняться. <a href="https://stepik.org/lesson/770592/step/2" rel="noopener noreferrer nofollow">Пример factorial</a> уже разделяет эти роли: <code>factorial.hpp</code> сообщает контракт, <code>factorial.cpp</code> реализует его, <code>main.cpp</code> использует.</p>
<p>Подключение готовой библиотеки обычно затрагивает три разных этапа:</p>
<ol><li><strong>Компиляция:</strong> доступны заголовки и нужный режим языка; компилятор понимает вызовы и типы.</li><li><strong>Компоновка:</strong> доступны необходимые определения из объектных файлов или библиотек. Одного <code>#include</code> для этого недостаточно.</li><li><strong>Запуск:</strong> если используется разделяемая библиотека, загрузчик должен найти совместимый файл и его зависимости.</li></ol>
<p>Не все библиотеки требуют отдельного бинарного файла. Реализация <strong>header-only</strong> доступна из заголовков — например, через шаблоны и inline-функции. Подключение такого заголовка тоже требует соблюдения его условий и может увеличить время компиляции. Это не то же самое, что статическая библиотека.</p>
<p>Стандартная библиотека C++ задаётся стандартом языка и поставляется реализацией C++; сторонние библиотеки имеют собственные версии, поддержку и правила распространения. Наличие готового кода само по себе не доказывает его пригодность. Важны документированный контракт, поддерживаемые платформы, совместимость, лицензия и стоимость сопровождения зависимости.</p>
<p>В <a href="https://stepik.org/lesson/770593/step/2" rel="noopener noreferrer nofollow">следующем шаге</a> сравниваются способы поставки реализации, а затем тот же factorial собирается как статическая и разделяемая библиотека. Смысл вызова функции и диапазон её аргументов от упаковки не меняются.</p>

<h3>Статическая и разделяемая библиотека: что различается</h3>
<p>Язык C++ описывает объявления, определения и поведение программы. Форматы объектных файлов, имена архивов и механизм динамической загрузки относятся к инструментам и платформе. Поэтому слово DLL означает конкретный вариант Windows, а не универсальное имя любой библиотеки C++.</p>
<table><thead><tr><th>Форма</th><th>Где находится реализация</th><th>Что требуется при запуске</th></tr></thead><tbody>
<tr><td>Статическая библиотека</td><td>Обычно архив объектных файлов; компоновщик выбирает нужные объектные модули и включает код в результат компоновки.</td><td>Сам исходный архив этой библиотеки обычно не нужен. Другие динамические зависимости программы могут остаться.</td></tr>
<tr><td>Разделяемая библиотека</td><td>Отдельный бинарный модуль, с которым связана программа.</td><td>Совместимый модуль и его зависимости должны быть доступны загрузчику.</td></tr>
<tr><td>Header-only</td><td>Доступная из заголовков реализация, часто шаблонная или inline.</td><td>Отдельного бинарного файла именно этой библиотеки обычно нет; могут требоваться её зависимости.</td></tr>
</tbody></table>
<p>Типичные расширения: статический архив <code>.a</code> у многих Unix-инструментов и <code>.lib</code> у MSVC; разделяемые файлы <code>.so</code> в Linux, <code>.dylib</code> в macOS, <code>.dll</code> в Windows. В Windows <code>.lib</code> бывает и библиотекой импорта для DLL, поэтому расширение само по себе не отличает статическую компоновку от динамической.</p>
<p>Для вызовов между двоичными компонентами важен <strong>ABI</strong>: соглашения о вызове, представление данных, имена символов и совместимость среды выполнения. Совпадение заголовков и формальное использование одного языка ещё не гарантируют, что бинарные файлы разных компиляторов можно связать. Изменение интерфейса или ABI может потребовать пересборки клиента.</p>
<p>Статическая форма упрощает доставку конкретной библиотеки, но обновление её кода обычно требует новой компоновки приложения. Разделяемая форма допускает отдельную поставку совместимой версии; поиск файлов, версии и зависимости становятся частью развёртывания. Повторное использование кода не означает автоматического уменьшения всей памяти процесса или ускорения запуска.</p>
<p>Следующие два шага показывают обе формы на одних исходниках и одном контракте.</p>

[Открыть на Stepik](https://stepik.org/lesson/770593/step/3?unit=773034) · [Исходник step-source](../../raw/step-sources/3215032.json) · [Объект step](../../raw/steps/3215032.json)

<h3>Статическая библиотека на примере factorial</h3>
<p>Используем без изменений три файла из <a href="https://stepik.org/lesson/770592/step/2" rel="noopener noreferrer nofollow">многофайлового примера</a>: <code>factorial.hpp</code>, <code>factorial.cpp</code>, <code>main.cpp</code>. Добавление библиотечной цели меняет организацию сборки, а не контракт <code>0 ≤ n ≤ 20</code>. Заголовок остаётся доступен и реализации, и приложению.</p>
<p>Полное описание сборки <code>CMakeLists.txt</code>:</p>
<pre><code class="language-cmake">cmake_minimum_required(VERSION 3.22)
project(FactorialLibrary LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20 CACHE STRING "C++ language standard")
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
option(BUILD_SHARED_LIBS "Build a shared library" OFF)

add_library(course_math factorial.cpp)
target_include_directories(course_math PUBLIC "${CMAKE_CURRENT_SOURCE_DIR}")
set_target_properties(course_math PROPERTIES WINDOWS_EXPORT_ALL_SYMBOLS ON)

add_executable(factorial_demo main.cpp)
target_link_libraries(factorial_demo PRIVATE course_math)

foreach(target IN ITEMS course_math factorial_demo)
    if(MSVC)
        target_compile_options(${target} PRIVATE /W4 /permissive-)
    elseif(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
        target_compile_options(${target} PRIVATE -Wall -Wextra -Wpedantic)
    endif()
endforeach()
</code></pre>

<p><code>add_library</code> создаёт цель <code>course_math</code>. Без явного типа она выбирает STATIC или SHARED по <code>BUILD_SHARED_LIBS</code>; здесь значение по умолчанию — OFF, то есть статическая библиотека. Эквивалентный жёстко заданный вариант — <code>add_library(course_math STATIC factorial.cpp)</code>. Каталог заголовка задан как PUBLIC: он нужен самой библиотеке и передаётся использующему её приложению. <code>target_link_libraries</code> сообщает зависимость компоновщику через систему сборки.</p>
<p>Свойство <code>WINDOWS_EXPORT_ALL_SYMBOLS</code> пригодится для варианта DLL в следующем шаге; в статической сборке оно не меняет контракт. Это средство CMake для MS-совместимых инструментов Windows, а не ключевое слово C++.</p>
<p>Команды для статического варианта:</p>
<pre><code class="language-text">cmake -S . -B build-static -DBUILD_SHARED_LIBS=OFF -DCMAKE_BUILD_TYPE=Debug
cmake --build build-static --config Debug
</code></pre>

<p>Для одно-конфигурационных генераторов Make/Ninja конфигурацию задаёт <code>CMAKE_BUILD_TYPE</code>. У Visual Studio нужную конфигурацию выбирает <code>--config Debug</code>, а её файлы обычно находятся в подкаталоге <code>Debug</code>. В результате есть статический архив и исполняемая программа. Для Linux с Make/Ninja пример запуска — <code>printf '5\n' | ./build-static/factorial_demo</code>, вывод <code>120</code>. На Windows имя исполняемого файла обычно оканчивается на <code>.exe</code>.</p>
<p>При прямой сборке GNU-инструментами роль архива хорошо видна:</p>
<pre><code class="language-bash">g++ -std=c++20 -Wall -Wextra -Wpedantic -c factorial.cpp -o factorial.o
ar rcs libcourse_math.a factorial.o
g++ -std=c++20 -Wall -Wextra -Wpedantic main.cpp libcourse_math.a -o factorial_demo
</code></pre>

<p>Архив в этой команде стоит после использующего его исходника: порядок статических библиотек имеет значение для некоторых компоновщиков. CMake позволяет описывать зависимости целями вместо ручного перечисления платформенных путей. Сам файл <code>libcourse_math.a</code> при запуске полученного приложения не требуется, но из этого не следует, что приложение целиком статически связано со всеми системными библиотеками.</p>
<p>Код примера совместим с C++17 и C++20. По умолчанию CMake выбирает C++20; параметр <code>-DCMAKE_CXX_STANDARD=17</code> меняет этот выбор при настройке. Следующий шаг использует то же описание сборки с включённой разделяемой библиотекой.</p>

<h3>Разделяемая библиотека: компоновка и загрузка</h3>
<p>Исходники и <code>CMakeLists.txt</code> из <a href="https://stepik.org/lesson/770593/step/3" rel="noopener noreferrer nofollow">предыдущего шага</a> остаются прежними. Отдельная директория сборки и значение ON создают разделяемый вариант:</p>
<pre><code class="language-text">cmake -S . -B build-shared -DBUILD_SHARED_LIBS=ON -DCMAKE_BUILD_TYPE=Debug
cmake --build build-shared --config Debug
</code></pre>

<p>В Linux это обычно <code>libcourse_math.so</code>, в macOS — <code>libcourse_math.dylib</code>, в Windows — <code>course_math.dll</code> и библиотека импорта для компоновки. Приложение всё так же вызывает <code>factorial</code> через заголовок и печатает 120 для входа 5. Отдельный бинарный модуль теперь нужен при запуске.</p>
<h4>Что должен знать загрузчик</h4>
<p>Успешная компоновка ещё не означает, что библиотека будет найдена на другом компьютере. Нужны доступный путь поиска, совместимый ABI, подходящая архитектура и необходимые зависимости. CMake обычно настраивает запуск связанных целей внутри дерева сборки согласно платформе; установка и распространение готового приложения требуют отдельного описания. В нашем простом Windows-примере DLL и EXE оказываются в каталоге одной конфигурации. Перенос одного EXE без DLL нарушает эту схему.</p>
<h4>Экспортируемый интерфейс и Windows</h4>
<p>В DLL доступность определения для внешнего клиента задаётся экспортом. В этом небольшом примере свойство CMake <code>WINDOWS_EXPORT_ALL_SYMBOLS</code> автоматически экспортирует обычную функцию при MS-совместимых инструментах. Это удобное ограниченное решение для свободной функции; импорт глобальных данных и некоторые случаи классов требуют явной разметки. У промышленной библиотеки обычно контролируют публичные символы через экспортный заголовок или иной механизм инструментов.</p>
<p><code>__declspec(dllexport)</code>, <code>__declspec(dllimport)</code>, файлы <code>.def</code> и <code>LoadLibrary</code> относятся к Windows. Для явной загрузки плагина приложение отдельно открывает модуль, ищет символы и управляет временем его использования. В Linux типичная пара API — <code>dlopen/dlsym</code>. Эти интерфейсы не являются стандартной библиотекой C++ и не нужны для показанного обычного связывания через CMake.</p>
<p>Нельзя вызывать сохранённую функцию из выгруженного модуля. Время жизни модуля должно охватывать все обращения к его коду и данным — это ещё один пример зависимости доступа от времени жизни владельца ресурса. В теме RAII та же идея будет выражена через объекты.</p>
<p>Статический и разделяемый варианты дают одинаковый математический результат при соблюдении контракта, но по-разному доставляют реализацию. Описание заголовков, связывания, загрузки и платформенных ограничений здесь самодостаточно; видео для понимания не требуется. Далее <a href="https://stepik.org/lesson/778425/step/1" rel="noopener noreferrer nofollow">тестирование</a> свяжет контракт функции с наблюдаемым результатом.</p>
