<h2>Как сравнивать стоимость операций контейнеров</h2>
<p><strong>Цель:</strong> назвать размер данных, конкретную операцию и условия оценки, прежде чем записывать O. Для словаря далее <code>n</code> — количество разных ключей, а <code>q</code> — число поисковых запросов.</p>
<p>Оценка «контейнер работает за O(log n)» слишком расплывчата. Поиск, обход всех элементов, вставка одного ключа и построение словаря из входа — разные действия. Например, поиск в <code>std::map</code> логарифмический, а вывод всех его элементов требует линейного числа посещений.</p>
<h3>Граница роста и случай входа — разные понятия</h3>
<ul><li><strong>O(f(n))</strong> — верхняя асимптотическая граница: при достаточно большом n затраты не превышают постоянный множитель f(n).</li>
<li><strong>Ω(f(n))</strong> — нижняя граница при достаточно большом n.</li>
<li><strong>Θ(f(n))</strong> — одновременно верхняя и нижняя границы одного порядка.</li></ul>
<p>Каждая запись применяется к выбранной функции: затратам в худшем случае, лучшем случае или в среднем при заданной модели входов. Ω не означает автоматически лучший случай. Для последовательного поиска первый элемент даёт Θ(1), а отсутствующий элемент — Θ(n). Худшие затраты этого поиска одновременно O(n) и Ω(n).</p>
<h3>Из чего состоит одна «операция»</h3>
<p>Для таблицы контейнеров обычно считаем сравнение ключей или вычисление хеша действием постоянной стоимости. С целыми ключами это часто удобная модель. С длинными строками одного количества сравнений недостаточно: сравнение может просмотреть общий префикс, а вычисление хеша обычно обрабатывает символы ключа. Если максимальная длина строки L, грубая верхняя оценка поиска в дереве через сравнения может быть O(L log n). Это объясняет, почему одинаковая запись O(log n) не обещает одинаковое время для целых чисел и строк.</p>
<h3>Один запрос и много запросов</h3>
<table><thead><tr><th>Подход к данным, которые далее не меняются</th><th>Подготовка</th><th>q запросов</th></tr></thead><tbody>
<tr><td>Неупорядоченный вектор + линейный поиск</td><td>Хранение n элементов: O(n)</td><td>O(qn) в худшем случае</td></tr>
<tr><td>Отсортированный вектор + двоичный поиск</td><td>Сортировка: O(n log n) сравнений</td><td>O(q log n) сравнений</td></tr>
<tr><td>Построение <code>set</code> обычными вставками + <code>find</code></td><td>O(n log n) для n разных ключей</td><td>O(q log n)</td></tr></tbody></table>
<p>Для одного запроса к неупорядоченным данным линейный поиск часто разумнее предварительной сортировки. Для множества запросов стоимость подготовки может окупиться. Если между запросами нужно вставлять и удалять ключи, надо учесть стоимость этих операций: у вектора двоичный поиск быстр, но вставка в середину требует сдвигов.</p>
<h3>Среднее и амортизированное</h3>
<p>Средняя оценка зависит от распределения входов или хешей. Амортизированная оценка распределяет общие затраты по последовательности операций: например, отдельный <code>vector::push_back</code> при перераспределении памяти может переместить все элементы, хотя серия добавлений имеет амортизированную постоянную стоимость на добавление. «Амортизированно O(1)» не обещает одинаковую задержку каждого вызова и не является средним по случайным входам.</p>
<h3>Разбор стоимости составной операции</h3><p>Один <code>map::find</code> имеет логарифмическую оценку по числу ключей, но печать всего словаря посещает каждый из <code>n</code> элементов и потому требует <code>Θ(n)</code> посещений. Для <code>n</code> независимых линейных поисков по <code>n</code> элементам худшая суммарная стоимость — <code>Θ(n²)</code>, например когда каждый искомый ключ отсутствует.</p><p>Оценка <code>O(1)</code> в среднем у хеш-таблицы допускает дорогой отдельный запрос. Амортизированная оценка относится к последовательности операций и не требует случайного распределения входа. Эти различия продолжают <a href="https://stepik.org/lesson/770594/step/1" rel="noopener noreferrer nofollow">модель стоимости алгоритмов</a> и <a href="https://stepik.org/lesson/973829/step/3" rel="noopener noreferrer nofollow">разбор заполнения хеш-таблицы</a>.</p>
<p><strong>Справка:</strong> <a href="https://timsong-cpp.github.io/cppwp/n4861/associative.reqmts" rel="noopener noreferrer nofollow">Гарантии ассоциативных контейнеров</a>; <a href="https://timsong-cpp.github.io/cppwp/n4861/unord.req" rel="noopener noreferrer nofollow">Неупорядоченные контейнеры</a>; <a href="https://timsong-cpp.github.io/cppwp/n4861/vector.modifiers" rel="noopener noreferrer nofollow">Модификаторы vector</a>.</p>

<h2>std::map или std::unordered_map: порядок и гарантии</h2>
<p><strong>Цель:</strong> выбрать контейнер под требования задачи и различать гарантии библиотеки и свойства собственной реализации. Ни один вариант не является самым быстрым для всех входов и всех операций.</p>
<h3>Гарантии для уникальных ключей</h3>
<p>В таблице n — число ключей; сравнение, вычисление хеша и сравнение на равенство считаем действиями постоянной стоимости. Речь об обычной одиночной вставке без подсказки и об удалении по ключу.</p>
<table><thead><tr><th>Контейнер</th><th>Поиск / вставка / удаление по ключу</th><th>Обход</th></tr></thead><tbody>
<tr><td><code>std::set</code>, <code>std::map</code></td><td>O(log n)</td><td>В порядке компаратора</td></tr>
<tr><td><code>std::unordered_set</code>, <code>std::unordered_map</code></td><td>В среднем O(1), в худшем O(n)</td><td>Не обещает сортировки и фиксированного порядка</td></tr></tbody></table>
<p>Стандарт не предписывает <code>map</code> конкретную разновидность сбалансированного дерева. У собственной реализации обычного двоичного дерева поиск зависит от высоты h: O(h); без балансировки h может вырасти до n. У списка поиск по ключу — O(n), даже если удаление уже найденного узла само по себе выполняется за O(1). Название абстрактной структуры не заменяет анализ её реализации.</p>
<p>Гарантия <code>erase(iterator)</code> для <code>set</code>/<code>map</code> отличается от поиска и удаления по ключу: она амортизированно постоянная. Для multi-контейнеров удаление всех совпадений зависит ещё и от количества удаляемых элементов. Всегда уточняйте, какая перегрузка и какой результат нужны.</p>
<h3>Хеш-таблица: быстрый поиск без требования порядка</h3>
<p>Следующая программа отвечает на запрос частоты слова. Условия ввода те же, что в предыдущем примере: <code>0 ≤ n ≤ 1000</code>, n слов и слово-запрос; слова состоят из 1–20 строчных латинских букв. Выводит только частоту запроса и число ключей. Она не зависит от порядка обхода хеш-таблицы.</p>
<p><strong>Полная программа C++17/20:</strong></p>
<p>Алфавит и длина слов здесь являются предусловием примера. Код проверяет количество и наличие обязательных слов, но не проверяет их алфавит или длину; полноценная проверка текстового формата — отдельная операция. Число вхождений не превосходит 1000 и помещается в <code>int</code>.</p>
<pre><code class="language-cpp">#include &lt;cstddef&gt;
#include &lt;iostream&gt;
#include &lt;string&gt;
#include &lt;unordered_map&gt;

int main() {
    int n = 0;
    if (!(std::cin &gt;&gt; n) || n &lt; 0 || n &gt; 1000) {
        return 1;
    }
    std::unordered_map&lt;std::string, int&gt; counts;
    counts.reserve(static_cast&lt;std::size_t&gt;(n));
    for (int i = 0; i &lt; n; ++i) {
        std::string word;
        if (!(std::cin &gt;&gt; word)) {
            return 1;
        }
        ++counts[word];
    }
    std::string query;
    if (!(std::cin &gt;&gt; query)) {
        return 1;
    }

    const auto it = counts.find(query);
    if (it == counts.end()) {
        std::cout &lt;&lt; "not found\n";
    } else {
        std::cout &lt;&lt; "count " &lt;&lt; it-&gt;second &lt;&lt; '\n';
    }
    std::cout &lt;&lt; "keys " &lt;&lt; counts.size() &lt;&lt; '\n';
}
</code></pre><p>Для ввода:</p><pre>5
pear apple pear plum apple
pear
</pre><p>Вывод:</p><pre>count 2
keys 3
</pre>
<p><code>reserve(n)</code> заранее готовит таблицу к предполагаемому числу элементов с учётом коэффициента загрузки; он не вставляет ключи, не запрещает коллизии и не превращает худший случай в O(1). Здесь резервируем верхнюю границу числа разных слов. Приведение к <code>std::size_t</code> выполнено только после проверки, что n неотрицательно.</p>
<p><strong>Коллизия не означает равенство ключей.</strong> Разные ключи могут получить одинаковый хеш, поэтому контейнер дополнительно проверяет равенство. Если вы задаёте собственные хеш и сравнение на равенство, эквивалентные ключи должны иметь одинаковый хеш. Для стандартной строки в примере используются готовые согласованные операции.</p>
<p>Вставка может вызвать <em>перехеширование</em> и сделать сохранённые итераторы хеш-таблицы недействительными. Поэтому в примере итератор получают после всех вставок и затем таблицу не изменяют. Указатели и ссылки на существующие элементы при перехешировании сохраняются, но после удаления соответствующего элемента использовать их нельзя. Для начальных программ проще повторно искать элемент после изменения таблицы.</p>
<h3>Разбор выбора словаря</h3><p>Если после каждой правки нужен обход имён по возрастанию, <code>map</code> предоставляет его напрямую. Для запроса частоты, когда порядок не важен, подходят оба словаря; выбор учитывает требования к худшей стоимости, свойства данных и измерения. Для одинакового порядка вывода результатов <code>unordered_map</code> ключи сначала собирают и сортируют либо используют <code>map</code>. Порядок обхода хеш-таблицы не является частью показанного результата.</p><h3>Повторный запрос не меняет данные</h3><p>После слов <code>apple pear apple</code> словарь содержит две записи: <code>apple → 2</code> и <code>pear → 1</code>. Три чтения через <code>find</code> для <code>apple, plum, plum</code> дают частоты <code>2, 0, 0</code>, если отсутствие трактуется как нулевая частота. Число ключей остаётся 2 после каждого запроса. Два чтения отсутствующего слова не создают запись; это следует из выбранной операции, а не из числа запросов.</p><p>Гарантии стандартного контейнера опираются на его контракт. Связь корзин, хеша и равенства разобрана в <a href="https://stepik.org/lesson/973829/step/1" rel="noopener noreferrer nofollow">модуле о хеш-таблицах</a>. Находящееся после теории существующее оценочное задание о языке программирования дополнительно требует разбора выражений и состояния имён.</p>

[Открыть на Stepik](https://stepik.org/lesson/973826/step/3?unit=980685) · [Исходник step-source](../../raw/step-sources/5070446.json) · [Объект step](../../raw/steps/5070446.json)

<p><em><strong>Иногда для успешного решения задачи нужно всего лишь прочитать условие, а затем написать решение - Тренер Belarusian SUIR #1: So Stuffy.</strong></em></p>

<p>Максим Витальевич решил изучить новый язык программирования. Один его знакомый порекомендовал изучить язык Rust, так как он самый перспективный. Да, язык действительно воодушевляет, но заставляет столкнуться с суровой реальностью - великим и могучим borrow checker.</p>

<p>Сказать, что Максим Витальевич был в некоторой растерянности, это ничего не сказать. Чтобы выйти из данной ситуации и разобраться с borrow checker, Максим Витальевич решил упростить язык.</p>

<p>Новый язык поддерживает только заранее определенный набор функций. Всего в языке доступно $n$ функций, описание каждой имеет следующий синтаксис:</p>

<pre><code class="language-rust">&lt;char&gt; := "a" | "b" | ... | "z"
&lt;name&gt; := &lt;char&gt; | &lt;char&gt; &lt;name&gt;
&lt;nameOrRefName&gt; := &lt;name&gt; | "&amp;" &lt;name&gt;
&lt;argument&gt; := &lt;nameOrRefName&gt;
&lt;arguments&gt; := &lt;argument&gt; | &lt;argument&gt; ", " &lt;arguments&gt;
&lt;functionName&gt; := &lt;nameOrRefName&gt;
&lt;functionArguments&gt; := "" | &lt;arguments&gt;
&lt;function&gt; := "fn " &lt;functionName&gt; "(" &lt;functionArguments&gt; ")"</code></pre>

<p>Таким образом, &lt;function&gt; является описанием функции. Можно заметить, что имя функции может быть как «name», так и «&amp;name». В первом случае функция возвращает значение, во втором случае — ссылку. Примеры корректных функций:</p>

<pre><code class="language-rust">fn input()        // Функция input возвращает значение и не содержит аргументов.
fn sum(a, b)      // Функция sum, возвращает значение и принимает два аргумента по значению.
fn add(&amp;a, &amp;b)    // Функция add, возвращает значение и принимает аргументы по ссылке.
fn &amp;ref(a)        // Функция ref, возвращает ссылку и принимает аргумент по значению.
fn assign(a, &amp;b)  // Функция assign, возвращает значение и принимает первый аргумент
                  // по значению, а второй по ссылке. </code></pre>

<p>Приведем также некорректные примеры (такие примеры не могут встречаться во входных данных):</p>

<pre><code class="language-rust">&amp;fn funcd()      // Неверный порядок символов.
fn funcb(a, b&amp;)  // Неверный порядок символов.
fn funcc(&amp;&amp;a)    // Нельзя получить ссылку на ссылку.
fn &amp;&amp;funca()     // Нельзя вернуть ссылку на ссылку.
fn fn()          // Используется fn в качестве имени.
fn funce(fn)     // Используется fn в качестве имени.
fn funcf(a, a)   // Одинаковые имена аргументов.
fn funcg(a, &amp;a)  // Одинаковые имена аргументов.</code></pre>

<p>Чтобы реализовать некоторую программу, в языке доступна конструкция «&lt;declare&gt;» — объявление новой переменной (или ссылки). Можно описать синтаксис следующим образом:</p>

<pre><code class="language-rust">&lt;callArguments&gt; := &lt;expression&gt; | &lt;expression&gt; ", " &lt;callArguments&gt;
&lt;functionCallArguments&gt; := "" | &lt;callArguments&gt;
&lt;functionCall&gt; := &lt;name&gt; "(" &lt;functionCallArguments&gt; ")"
&lt;expression&gt; := &lt;nameOrRefName&gt; | &lt;functionCall&gt;
&lt;declare&gt; := &lt;name&gt; " := " &lt;expression&gt;</code></pre>

<p>Приведем корректные примеры использования конструкции:</p>

<pre><code class="language-rust">a := input()      // Определяем переменную со значением результата input().
b := input()
c := a            // Присваиваем новой переменной старое значение.
d := add(&amp;b, &amp;c)  // Вызываем функцию с передачей аргументов по ссылке.
e := add(ref(b), ref(c))
f := &amp;e</code></pre>

<p>Приведем некорректные примеры использования конструкции (такие примеры не могут встречаться во входных данных):</p>

<pre><code class="language-rust">a := &amp;input()  // Нельзя получить ссылку на результат функции.
fn := a        // Нельзя использовать fn в качестве имени.
&amp;b := c        // Нельзя объявлять имя-ссылку.</code></pre>

<p>Максим Витальевич считает, что такой синтаксис довольно простой, поэтому <strong>синтаксических ошибок при использовании языка он допустить не может</strong>.</p>

<p>Однако Максим Витальевич может допустить следующие ошибки:</p>

<ul>
	<li>
	<p>Использовать ранее не объявленную с помощью «:=» переменную.</p>
	</li>
	<li>
	<p>Использовать несуществующую функцию.</p>
	</li>
	<li>
	<p>Вызывать функцию с неверным числом аргументов (число аргументов должно совпадать с определением).</p>
	</li>
	<li>
	<p>В аргумент функции, принимающий значение, передавать ссылку (либо наоборот).</p>
	</li>
	<li>
	<p><strong>Использовать в выражении ранее перемещенное значение переменной (либо ссылку на такую переменную)</strong>.</p>
	</li>
</ul>

<p>Последний пункт рассмотрим поподробнее. В языке Максима Витальевича предусмотрен собственный механизм borrow checker. Суть заключается в том, что все переменные, которые <strong>используются по значению, перемещаются</strong> и перестают быть доступными. Рассмотрим следующий пример:</p>

<pre><code class="language-rust">a := input()    // a является значением.
b := sum(a, a)  // Ошибка!</code></pre>

<p>В этом случае переменная «a» передается по значению 2 раза, однако после первого же использования она перестает быть доступна, таким образом возникает ошибка. В то же время:</p>

<pre><code class="language-rust">a := input()      // a является значением.
b := sum(&amp;a, &amp;a)  // Корректно, если sum принимает ссылки. Переменная a
                  // остается доступной, так как не была использована по значению.</code></pre>

<p>После объявления переменной с тем же именем (:=), старая переменная (если она является значением) <strong>считается перемещенной</strong> и перестает быть доступной <strong>начиная со следующей строки</strong>.</p>

<p>Для ссылок действуют следующие правила:</p>

<ul>
	<li>
	<p>Нельзя получать ссылку для перемещенной переменной.</p>
	</li>
	<li>
	<p>Нельзя получать ссылку для переменной-ссылки.</p>
	</li>
	<li>
	<p>Нельзя использовать ссылку на перемещенную переменную.</p>
	</li>
	<li>
	<p><strong>Нельзя одновременно передавать переменную-значение и ссылку на эту переменную в той же строке.</strong></p>
	</li>
</ul>

<p>Рассмотрим следующие примеры:</p>

<pre><code class="language-rust">a := input()
b := a
c := &amp;a  // Ошибка, переменная a была перемещена.

a := input()
b := &amp;a
c := move(a) // Аналогично c := a. В любом случае переменная a перемещается.
d := b       // Ошибка, переменная b является ссылкой на значение a, которое было перемещено.

a := input()
b := &amp;a
c := call(a, b) // Ошибка. Переменная a была перемещена, поэтому ссылку использовать нельзя.

a := input()
b := &amp;a
a := a         // Старое значение переменной a перемещено.
c := clone(b)  // Ошибка, переменная b ссылается на старую переменную a, которая
               // была перемещена в предыдущей строке.</code></pre>

<p>Так как Максим Витальевич придумал язык и хочет его использовать, он просит вас реализовать программу, которая будет проверять код Максима Витальевича на наличие ошибок.</p>

<p>В следующей строке задано число $m$ - количество строк в коде Максима Витальевича.</p>

<p>В следующих $m$ строках заданы конструкции объявления новой переменной в соответствии с описанием синтаксиса.</p>
