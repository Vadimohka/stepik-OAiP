<h2>Из чего состоит обычная сборка C++</h2>
<p>Для понимания сообщений об ошибках полезно различать этапы. В традиционной цепочке GCC рассматриваются препроцессорная обработка, собственно компиляция, ассемблирование и компоновка. Они могут запускаться одной командой; промежуточные файлы не обязаны оставаться на диске.</p>
<table><thead><tr><th>Этап</th><th>Смысл</th><th>Типичный результат</th></tr></thead><tbody><tr><td>Препроцессорная обработка</td><td>Обрабатываются директивы, например <code>#include</code>, и макросы</td><td>Исходный материал после включений и преобразований препроцессора</td></tr><tr><td>Компиляция</td><td>Проверяются конструкции C++, определяется их смысл, создаётся код для целевой платформы</td><td>Код ассемблера или внутреннее представление</td></tr><tr><td>Ассемблирование</td><td>Машинные инструкции и служебные данные помещаются в объектный формат</td><td>Объектный файл</td></tr><tr><td>Компоновка</td><td>Объектные файлы и нужные библиотечные части объединяются, внешние ссылки согласуются</td><td>Исполняемый файл либо библиотека</td></tr></tbody></table>
<p>Словом «компиляция» часто называют и несколько первых этапов вместе. Поэтому команда GCC <code>g++ -c main.cpp</code> выполняет необходимые преобразования до объектного файла, хотя внутри работы есть не только собственно компиляция. Ключ <code>-c</code> останавливает процесс перед компоновкой.</p>
<p>Расширения файлов — соглашения инструментов: исходники часто имеют <code>.cpp</code>, объектные файлы — <code>.o</code> или <code>.obj</code>. Программа Windows часто имеет <code>.exe</code>; для исполняемого файла другой системы это расширение не обязательно. Стандарт C++ описывает модель трансляции, но не требует именно таких имён файлов и отдельных процессов для каждого этапа.</p>
<p>Например, пропущенная точка с запятой обнаруживается до компоновки. Отсутствующее определение вызванной обычной внешней функции может обнаружиться позже, когда компоновщик соединяет части программы. <a href="https://stepik.org/lesson/763038/step/4" rel="noopener noreferrer nofollow">Далее разберём эти границы на одной программе</a>.</p>

<h2>Раздельная компиляция и компоновка: один пример</h2>
<p>Возьмём полный файл <code>main.cpp</code> с приветствием из <a href="https://stepik.org/lesson/763037/step/1" rel="noopener noreferrer nofollow">шага о языке программирования</a>. Он выводит <code>Hello C++</code> и перевод строки. Здесь показаны <strong>команды оболочки для GCC в Linux</strong>; они не являются кодом C++.</p>
<pre><code class="language-bash">g++ -std=c++17 -Wall -Wextra -Wpedantic -c main.cpp -o main.o
g++ main.o -o hello
./hello
</code></pre>
<p>Первая команда обрабатывает исходник в режиме C++17 и создаёт объектный файл <code>main.o</code>. Ключи <code>-Wall -Wextra -Wpedantic</code> включают полезные предупреждения, а <code>-o</code> задаёт имя результата. Вторая команда запускает необходимую компоновку через драйвер <code>g++</code>, который знает о библиотеке C++. Третья запускает готовый файл. Вывод:</p>
<pre><code class="language-text">Hello C++
</code></pre>
<p>После первой команды нельзя подставить <code>main.o</code> вместо готовой программы: объектный файл ещё не является результатом полной сборки. Две первые команды можно объединить: <code>g++ -std=c++17 main.cpp -o hello</code> выполнит необходимые этапы до исполняемого файла. Для режима C++20 меняют значение соответствующего ключа на <code>-std=c++20</code>.</p>
<p>Если убрать точку с запятой после вывода, первая команда завершится ошибкой. Если же исходник корректно обращается к объявленной функции, но её определения нет среди соединяемых частей, объектный файл может быть создан, а компоновка завершится ошибкой. Это разные причины, поэтому исправление должно соответствовать сообщению этапа.</p>
<p>Команды запуска и имена результатов зависят от платформы и оболочки. В среде разработки эти действия могут быть скрыты за кнопкой, но граница между исходником, объектным файлом и исполняемой программой сохраняет смысл. <a href="https://stepik.org/lesson/763038/step/5" rel="noopener noreferrer nofollow">Теперь уточним роль включаемых заголовков</a>.</p>

<h2>Препроцессор и директива include</h2>
<p>Перед обычным разбором конструкций C++ выполняются преобразования препроцессора. Он обрабатывает директивы и макросы. Это часть трансляции, а не набор команд, которые программа исполняет при каждом запуске.</p>
<p>В приветствии строка <code>#include &lt;iostream&gt;</code> обеспечивает доступ к объявлениям стандартного ввода и вывода. Упрощённо можно думать, что нужный заголовок включается в обрабатываемый исходный материал. Стандартные заголовки при этом не обязаны быть обычными текстовыми файлами на диске.</p>
<p>Для заголовков стандартной библиотеки применяют форму с угловыми скобками, например <code>&lt;iostream&gt;</code>. Для заголовка проекта часто используют кавычки, например <code>"calculations.hpp"</code>. Порядок и места поиска определяются реализацией и настройками; кавычки не означают универсальный поиск только рядом с исходником.</p>
<p>Директива начинается с <code>#</code> после возможных пробелов в начале логической строки. В отличие от обычной инструкции-выражения C++, она не требует завершающей точки с запятой. Следующий фрагмент содержит директиву и обычную инструкцию; инструкция допустима внутри тела функции:</p>
<pre><code class="language-cpp">#include &lt;iostream&gt;
// В теле функции:
std::cout &lt;&lt; "Hello C++\n";
</code></pre>
<p><code>#include</code> не вызывает <code>std::cout</code>, не скачивает библиотеку и не заменяет компоновку. Он помогает предоставить объявления и определения, нужные при обработке исходника. Где находится исполняемый код библиотеки и как он подключается к программе, — отдельный вопрос сборки.</p>
<p>Простейшая программа, не использующая библиотечные средства, может обходиться без <code>#include</code>. <a href="https://stepik.org/lesson/763038/step/6" rel="noopener noreferrer nofollow">Следующий шаг связывает исходник и его включения с единицей трансляции</a>; организация собственных заголовков будет подробно разобрана в <a href="https://stepik.org/lesson/770590/step/1" rel="noopener noreferrer nofollow">модуле 7</a>.</p>

<h2>Единица трансляции</h2>
<p><strong>Единица трансляции</strong> — исходный материал, который обрабатывается как целое после препроцессорных преобразований. Для рассматриваемой обычной сборки это исходный файл <code>.cpp</code> вместе с включёнными заголовками после обработки директив и макросов. Поэтому «один файл на диске» и «одна единица трансляции» не всегда обозначают одинаковый объём текста.</p>
<p>Например, если <code>main.cpp</code> включает <code>calculations.hpp</code>, объявления из этого заголовка участвуют в обработке <code>main.cpp</code>. Если другой исходник <code>calculations.cpp</code> включает тот же заголовок, он получает нужные объявления в своей единице трансляции. Обычно оба <code>.cpp</code> компилируются отдельно, а полученные объектные файлы соединяются при компоновке.</p>
<p>Компилятор не ищет произвольно по соседним файлам недостающее описание функции. В месте использования должно быть доступно подходящее объявление. Согласование объявлений и определений будет темой <a href="https://stepik.org/lesson/770590/step/1" rel="noopener noreferrer nofollow">модуля 7 о функциях и устройстве проекта</a>. Сейчас достаточно понимать, зачем общие объявления помещают в заголовок.</p>
<p>Если заголовок изменился, может потребоваться заново обработать все исходники, которые от него зависят. Система сборки отслеживает такие зависимости, чтобы не опираться на устаревшие объектные файлы. Изменение только одного <code>.cpp</code> обычно не требует повторной компиляции всех остальных независимых единиц, но итоговую программу нужно заново скомпоновать.</p>
<p>В учебной схеме собственные файлы реализации добавляют в сборку, а не включают друг в друга через <code>#include "file.cpp"</code>. Эта рекомендация объясняется разделением обязанностей заголовка и реализации. Механизм модулей C++20 — отдельное средство организации программы; в данном курсе используется традиционная модель исходников и заголовков.</p>

<h2>Компоновка: соединение частей программы</h2>
<p>После отдельной обработки исходников нужно соединить части программы. <strong>Компоновщик</strong> использует объектные файлы и библиотеки, сопоставляет внешние ссылки с определениями и формирует результат сборки. Одного успешного преобразования каждого исходника для этого недостаточно.</p>
<p>Следующий <strong>полный исходный файл</strong> намеренно не образует готовую программу при компоновке без дополнительных файлов. Это разобранный пример ошибки, а не образец для запуска:</p>
<pre><code class="language-cpp">int twice(int value);

int main() {
    return twice(0);
}
</code></pre>
<p>Первая строка — объявление функции: компилятор знает её имя, тип аргумента и тип результата. Но здесь нет определения, то есть тела функции, объясняющего её работу. Поэтому GCC может получить объектный файл, однако при обычной отдельной компоновке сообщит о неразрешённой ссылке на <code>twice</code>. Текст диагностики зависит от инструмента и платформы.</p>
<p>Чтобы закончить именно этот разбор, добавим определение в тот же исходный файл. Получится <strong>полная корректная программа C++17/C++20</strong>:</p>
<pre><code class="language-cpp">int twice(int value);

int main() {
    return twice(0);
}

int twice(int value) {
    return value * 2;
}
</code></pre>
<p>В этом запуске функция получает 0, возвращает 0, а <code>main</code> сообщает успешное завершение. На экран ничего не выводится. Для произвольного <code>int</code> удвоение требует, чтобы результат был представим; здесь используется только заведомо подходящий аргумент 0. В многофайловой программе определение можно разместить в другом исходнике и включить его объектный файл в сборку.</p>
<p>Повторное включение заголовка не заменяет отсутствующее определение обычной внешней функции. И наоборот, несовместимые определения в разных файлах нарушают правила программы.
