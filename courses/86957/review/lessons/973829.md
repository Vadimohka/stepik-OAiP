<h2>Хеш-таблица: доступ по ключу без порядка</h2>
<p>Предпосылки: <a href="https://stepik.org/lesson/973837/step/1" rel="noopener noreferrer nofollow">АТД и реализация</a>, <a href="https://stepik.org/lesson/770594/step/1" rel="noopener noreferrer nofollow">модель стоимости</a>, <a href="https://stepik.org/lesson/853539/step/2" rel="noopener noreferrer nofollow">дерево поиска</a>. Хеш-таблица реализует множество ключей или словарь «ключ → значение». В отличие от упорядоченного дерева, она не поддерживает порядок ключей как основной инвариант.</p>
<p>Хеш-функция вычисляет код ключа. По коду выбирается <strong>корзина</strong> или начальная позиция в таблице. Это место, где ищут кандидатов; окончательный ответ даёт сравнение ключей на равенство. Разные ключи могут попасть в одно место.</p>
<table><thead><tr><th>Множество с уникальными ключами</th><th>Вставка с проверкой дубликата</th><th>Удаление по ключу</th><th>Поиск</th></tr></thead><tbody><tr><td>Неупорядоченный массив</td><td>O(n)</td><td>O(n)</td><td>O(n)</td></tr><tr><td>Связный список</td><td>O(n)</td><td>O(n)</td><td>O(n)</td></tr><tr><td>Отсортированный массив</td><td>O(n)</td><td>O(n)</td><td>O(log n)</td></tr><tr><td>Сбалансированное дерево</td><td>O(log n)</td><td>O(log n)</td><td>O(log n)</td></tr><tr><td>Хеш-таблица</td><td>Ожидаемо амортизированно O(1)</td><td>Ожидаемо O(1)</td><td>Ожидаемо O(1)</td></tr></tbody></table>
<p>В таблице стоимость сравнения и хеширования считается O(1), размер — n. Для списка вставка при <em>известной позиции</em> может стоить O(1), но здесь включён поиск дубликата. У дерева гарантии следуют из инварианта высоты. У хеш-таблицы ожидаемые оценки требуют подходящего распределения и контроля заполнения; отдельная операция в худшем случае может потребовать O(n). Перестройка при росте объясняет слово «амортизированно».</p>
<p>Если ключ — строка длины L, вычисление её хеша обычно само требует O(L); сравнение строк также не считается бесплатно. Поэтому «O(1) поиск» относится к указанной модели, а не означает независимость от длины входного текста.</p>
<p>Цена быстрого ожидаемого доступа — запас корзин, работа с коллизиями и отсутствие отсортированного обхода. Для диапазонов ключей и гарантированного логарифмического числа сравнений подходит дерево; для доступа по точному ключу часто удобна хеш-таблица. Следующие шаги объясняют условия этой оценки.</p>

[Открыть на Stepik](https://stepik.org/lesson/973829/step/2?unit=980690) · [Исходник step-source](../../raw/step-sources/4035461.json) · [Объект step](../../raw/steps/4035461.json)

<h2>Хеш-код, индекс корзины и равенство</h2>
<p>Разделим два действия: <code>h(key)</code> получает хеш-код, а <code>index = h(key) % m</code> в простой учебной схеме выбирает одну из <code>m &gt; 0</code> корзин. Стандартная библиотека не обязана использовать именно это вычисление индекса.</p>
<p>Согласованность хеша и равенства — часть контракта: <strong>если ключи считаются равными, их хеш-коды должны совпадать</strong>. Обратное неверно: равный хеш не доказывает равенство ключей. Например, при сравнении строк без учёта регистра нельзя оставить хеш, различающий <code>A</code> и <code>a</code>.</p>
<table><thead><tr><th>Целочисленный ключ</th><th>Учебный хеш h(id) = id</th><th>Корзина при m = 4</th></tr></thead><tbody><tr><td>1</td><td>1</td><td>1</td></tr><tr><td>5</td><td>5</td><td>1</td></tr><tr><td>9</td><td>9</td><td>1</td></tr></tbody></table>
<p>Здесь исходные хеш-коды различны, но индексы корзин совпали. В реализации следующего урока эти действия объединены в остаток <code>id % bucket_count</code> для неотрицательного беззнакового ID. Пример намеренно прост и позволяет проследить коллизию; для последовательностей с регулярным шагом распределение может оказаться плохим.</p>
<p>Пока ключ хранится в таблице, результат используемых хеша и сравнения должен оставаться согласованным. Иначе повторный поиск отправится в другую корзину. После изменения числа корзин индекс пересчитывается — это <strong>rehash</strong>, а не изменение смысла равенства.</p>
<p>Равномерность — желательное свойство распределения для выбранных данных, а не доказательство отсутствия коллизий. Хеш контейнера также не является криптографической защитой. Значения <code>std::hash</code> не следует считать переносимыми идентификаторами для хранения в файле между разными реализациями и запусками.</p>

[Открыть на Stepik](https://stepik.org/lesson/973829/step/3?unit=980690) · [Исходник step-source](../../raw/step-sources/4035460.json) · [Объект step](../../raw/steps/4035460.json)

<h2>Коллизии, заполнение и стоимость</h2>
<p>Коллизия хеш-кодов означает одинаковый код у разных ключей. Даже при разных кодах редукция к конечному числу корзин может дать один индекс. В обоих случаях таблица должна сохранить все различные ключи и уметь отличить их при поиске.</p>
<h3>Метод цепочек</h3>
<p>Корзина хранит последовательность записей. В примере с четырьмя корзинами ID 1, 5, 9 образуют цепочку в корзине 1. Поиск 5 просматривает записи и сравнивает <em>ID</em>; замена имени для 5 обновляет только эту запись. Считать одинаковый индекс дубликатом было бы ошибкой.</p>
<p>Пусть n — число элементов, m — число корзин. <strong>Коэффициент заполнения</strong> α = n / m — среднее число записей на корзину, а не доля непустых корзин. Для метода цепочек α может быть больше 1. При подходящем распределении поиск занимает ожидаемо O(1 + α) сравнений, в худшем случае вся таблица попадает в одну цепочку и поиск занимает O(n).</p>
<h3>Открытая адресация</h3>
<p>Записи хранятся непосредственно в массиве. Линейное пробирование при занятой позиции последовательно проверяет следующие с циклическим переходом через конец. Оно должно различать существующий ключ, подходящее место для вставки и отсутствие ключа. Длинные скопления занятых ячеек ухудшают поиск; перед заполнением таблицу расширяют.</p>
<p>Удаление нельзя свести к пометке ячейки «никогда не использовалась»: это оборвало бы поиск элементов, сдвинутых туда прежней коллизией. Применяют отдельную метку удалённой ячейки или алгоритм восстановления цепочки пробирования. Одна проба не должна бесконечно обходить заполненный массив: число просмотренных позиций ограничено.</p>
<h3>Перестройка</h3>
<p>При изменении m все записи заново размещаются по новому правилу индекса. Простое увеличение массива без переноса оставит элементы в неверных корзинах. Один rehash требует прохода по записям и может быть дорогим; стратегия редких увеличений ёмкости позволяет распределить эту стоимость на много вставок.</p>
<p>Для цепочек нет физического ограничения «одна запись на корзину», но рост α ухудшает ожидаемый поиск. Для открытой адресации нужна свободная ёмкость и своя политика нагрузки. Эти методы нельзя оценивать одной формулой без указания предпосылок. Далее дан законченный <a href="https://stepik.org/lesson/973831/step/1" rel="noopener noreferrer nofollow">пример цепочек</a>.</p>
