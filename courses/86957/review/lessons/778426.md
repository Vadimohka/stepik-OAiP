<h3>Модульные тесты: проверяем поведение функции</h3>
<p>Модульный тест вызывает небольшую часть программы с известными входными данными и сравнивает фактический результат с ожидаемым. Например, функцию подсчёта можно проверить без ручного ввода в консоль. Проверка запуска всей программы и её формата ввода-вывода — отдельная задача.</p>
<p>В этом уроке мы сначала найдём эффективный алгоритм, затем выделим его в функцию и проверим её автоматически. Приложение и тесты будут использовать <strong>одну и ту же реализацию</strong>. Если скопировать формулу в тест, ошибка может появиться в обеих копиях, а исправление одной копии не изменит другую.</p>
<p>У каждой функции нужен контракт: допустимые входы и ожидаемый результат. Тесты должны включать обычные значения и границы этого контракта. Ожидаемые ответы выводятся независимо от проверяемой реализации: иначе одинаковая ошибка может оказаться и в формуле, и в её «проверке».</p>
<p>Для первой проверки достаточно стандартной библиотеки и отдельной тестовой программы. Затем CTest позволит запускать её одной командой. Более крупные проекты часто используют библиотеку GoogleTest: она предоставляет именованные тесты, проверки <code>EXPECT_*</code>/<code>ASSERT_*</code> и удобные сообщения об ошибках. Библиотека не привязана к Visual Studio.</p>
<p><strong>Маршрут объяснения:</strong> общий исходник приложения и тестов, успешный результат, затем разобранный отказ с неправильным ожиданием. Успешные тесты подтверждают проверенные случаи, но сами по себе не доказывают правильность для всех входных данных.</p>
<p><a href="https://google.github.io/googletest/primer.html" rel="noopener noreferrer nofollow">Официальное введение в GoogleTest</a>.</p>

<h3>Одна задача, два уровня анализа</h3>
<p>Разбираемый пример: среди целых чисел от 1 до <code>n</code> включительно подсчитать те, у которых сумма десятичных цифр больше суммы цифр следующего числа. Для пользовательского ввода <code>1 ≤ n ≤ 10<sup>9</sup></code>. Например, 8 не подходит: 8 &lt; 9. Число 9 подходит: 9 &gt; 1. Среди чисел 1..19 подходят 9 и 19, ответ 2. Эта формулировка не зависит от изображения условия.</p>
<p>Ниже полный фрагмент двух вычисляющих функций; ввода и <code>main</code> в нём нет. Для внутреннего контракта дополнительно разрешён <code>n == 0</code>, означающий пустой интервал.</p>
<pre><code class="language-cpp">// Precondition: num &gt;= 0.
int sum_of_digits(long long num) {
    int result = 0;
    do {
        result += static_cast&lt;int&gt;(num % 10);
        num /= 10;
    } while (num != 0);
    return result;
}

// Precondition: 0 &lt;= interval_end &lt;= 1'000'000'000.
long long count_by_enumeration(long long interval_end) {
    long long count = 0;
    for (long long value = 1; value &lt;= interval_end; ++value) {
        if (sum_of_digits(value) &gt; sum_of_digits(value + 1)) {
            ++count;
        }
    }
    return count;
}
</code></pre>

<p>Операции с остатком и делением выделяют десятичные цифры неотрицательного числа. Тип <code>long long</code> вмещает границу 10<sup>9</sup>, значение <code>value + 1</code> и счётчик во всём заявленном диапазоне даже при минимальных гарантиях стандарта.</p>
<p>Перебор посещает <code>n</code> чисел; обработка цифр добавляет число шагов, пропорциональное их количеству. При переменном числе разрядов это <code>O(n log n)</code> простых операций: обозначение верхней границы роста будет точно определено в <a href="https://stepik.org/lesson/770594/step/2" rel="noopener noreferrer nofollow">модуле 10</a>. Здесь достаточно видеть два множителя — число посещённых чисел и число обрабатываемых цифр. Под ограничением 10<sup>9</sup> разрядов не больше десяти, но миллиард итераций всё равно велик. Точное время зависит от среды; корректность формулы и соответствие лимиту времени — разные вопросы.</p>
<p>Следующий шаг выводит формулу без полного перебора. Перебор остаётся понятной независимой моделью для небольших значений при авторской проверке этой формулы.</p>

<h3>От перебора к формуле и отдельной функции</h3>
<p>Пусть число заканчивается ровно <code>k</code> девятками. При прибавлении единицы они превращаются в нули, а соседний разряд увеличивается на один; если разряда не было, появляется ведущая единица. Поэтому сумма цифр меняется на <code>1 − 9k</code>. Она уменьшается тогда и только тогда, когда <code>k ≥ 1</code>, то есть последняя цифра исходного числа — девятка.</p>
<p>Подходящие числа: <code>9, 19, 29, …</code>. Среди чисел от <code>1</code> до <code>n</code> включительно их ровно <code>(n + 1) / 10</code>, где деление целочисленное. Для <code>n = 8</code> ответ 0, для 9 и 10 — 1, для 19 — 2. Формула выполняет постоянное число арифметических операций, в отличие от перебора всего интервала.</p>
<p><strong>Оптимизация</strong> меняет способ вычисления ради эффективности. <strong>Рефакторинг</strong> меняет внутреннюю структуру с сохранением наблюдаемого поведения. Далее выделим вычисление из консольной программы, чтобы вызывать его и из приложения, и из тестов.</p>
<p>Готовый пример состоит из трёх файлов в одной папке. <code>interesting.hpp</code> содержит объявление функции и её предусловие. Для локальной функции дополнительно разрешим <code>n = 0</code>: в пустом интервале ответ равен нулю. В задании Stepik граница остаётся <code>1 ≤ n ≤ 10<sup>9</sup></code>.</p>
<pre><code class="language-cpp">#ifndef INTERESTING_HPP
#define INTERESTING_HPP

// Precondition: 0 &lt;= interval_end &lt;= 1'000'000'000.
long long CountInterestingInInterval(long long interval_end);

#endif
</code></pre>
<p>Файл <code>interesting.cpp</code> — единственное определение алгоритма:</p>
<pre><code class="language-cpp">#include "interesting.hpp"

long long CountInterestingInInterval(long long interval_end) {
    return (interval_end + 1) / 10;
}
</code></pre>
<p>Тип <code>long long</code> позволяет представить все значения заявленного диапазона и промежуточное <code>n + 1</code>. За пределами предусловия функция здесь не проверяется; этот контракт не следует расширять без анализа переполнения.</p>
<p>Файл <code>main.cpp</code> отвечает за ввод и вывод:</p>
<pre><code class="language-cpp">#include "interesting.hpp"
#include &lt;iostream&gt;

int main() {
    long long n{};
    if (!(std::cin &gt;&gt; n) || n &lt; 1 || n &gt; 1'000'000'000) {
        std::cerr &lt;&lt; "Expected an integer from 1 to 1000000000\n";
        return 1;
    }
    std::cout &lt;&lt; CountInterestingInInterval(n) &lt;&lt; '\n';
}
</code></pre>
<p>Приложение читает одно целое число из диапазона задания и выводит только ответ. При неудачном чтении или недопустимом значении оно сообщает об ошибке в <code>std::cerr</code> и завершает работу с кодом 1.</p>
<p>Для GCC/Clang можно проверить проект непосредственной сборкой:</p>
<pre><code class="language-bash">g++ -std=c++20 -Wall -Wextra -Wpedantic main.cpp interesting.cpp -o interesting_app
</code></pre>
<p>Например, ввод <code>19</code> даёт вывод <code>2</code>. На следующем шаге показаны отдельная программа, вызывающая эту же функцию на нескольких входах, и описание сборки CMake.</p>

<h3>Первые автоматические тесты и CTest</h3>
<p>В разобранном проекте рядом с <code>interesting.hpp</code>, <code>interesting.cpp</code> и <code>main.cpp</code> находится <code>tests.cpp</code>. В нём нет второй копии формулы: тесты подключают заголовок и вызывают функцию из того же <code>interesting.cpp</code>, что и приложение.</p>
<pre><code class="language-cpp">#include "interesting.hpp"
#include &lt;iostream&gt;

bool Check(long long input, long long expected) {
    const long long actual = CountInterestingInInterval(input);
    if (actual == expected) {
        return true;
    }
    std::cerr &lt;&lt; "n=" &lt;&lt; input &lt;&lt; ": expected " &lt;&lt; expected
              &lt;&lt; ", got " &lt;&lt; actual &lt;&lt; '\n';
    return false;
}

int main() {
    int failures = 0;
    failures += !Check(0, 0);
    failures += !Check(1, 0);
    failures += !Check(8, 0);
    failures += !Check(9, 1);
    failures += !Check(10, 1);
    failures += !Check(18, 1);
    failures += !Check(19, 2);
    failures += !Check(20, 2);
    failures += !Check(99, 10);
    failures += !Check(100, 10);
    failures += !Check(880'055'535, 88'005'553);
    failures += !Check(999'999'999, 100'000'000);
    failures += !Check(1'000'000'000, 100'000'000);
    if (failures != 0) {
        return 1;
    }
    std::cout &lt;&lt; "13 checks passed\n";
}
</code></pre>
<p><code>Check</code> возвращает <code>true</code>, если результат совпал. Выражение <code>!Check(...)</code> даёт <code>true</code> при ошибке и при сложении увеличивает счётчик на единицу. Неудачная проверка печатает вход, ожидаемое и фактическое значения. Ненулевой код завершения сообщает системе запуска, что тесты провалились.</p>
<p>Значения 8, 9, 10 и 18, 19, 20 проверяют переход через последнюю цифру 9; 99 и 100 — перенос через несколько разрядов. Есть пустой интервал для локального контракта, минимальный вход задания и большие границы. Ожидаемые ответы записаны явно, а не вычисляются копией проверяемой формулы.</p>
<p>Здесь используются обычные условия, поэтому проверки работают и в сборке Release. Стандартный макрос <code>assert</code> может быть отключён при определении <code>NDEBUG</code>; он не подходит для таких обязательных проверок без контроля настроек.</p>
<p>Полный <code>CMakeLists.txt</code> этого примера:</p>
<pre><code class="language-cmake">cmake_minimum_required(VERSION 3.22)
project(InterestingNumbers LANGUAGES CXX)

add_library(interesting interesting.cpp)
add_executable(interesting_app main.cpp)
target_link_libraries(interesting_app PRIVATE interesting)

include(CTest)
if(BUILD_TESTING)
    add_executable(interesting_tests tests.cpp)
    target_link_libraries(interesting_tests PRIVATE interesting)
    add_test(NAME InterestingNumbers COMMAND interesting_tests)
endif()

set(learning_targets interesting interesting_app)
if(BUILD_TESTING)
    list(APPEND learning_targets interesting_tests)
endif()
foreach(target IN LISTS learning_targets)
    set_target_properties(${target} PROPERTIES
        CXX_STANDARD 20
        CXX_STANDARD_REQUIRED YES
        CXX_EXTENSIONS NO
    )
    if(MSVC)
        target_compile_options(${target} PRIVATE /W4 /permissive-)
    elseif(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
        target_compile_options(${target} PRIVATE -Wall -Wextra -Wpedantic)
    endif()
endforeach()
</code></pre>
<p>Цель <code>interesting</code> содержит общий код. <code>target_link_libraries</code> связывает с ним приложение и тесты. <code>include(CTest)</code> вводит настройку <code>BUILD_TESTING</code>; <code>add_test</code> регистрирует тестовый исполняемый файл. CTest учитывает код завершения: 0 — успех, ненулевой — отказ.</p>
<p>Для Make или Ninja настройка, сборка и запуск записываются так:</p>
<pre><code class="language-bash">cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build
ctest --test-dir build --output-on-failure --no-tests=error
</code></pre>
<p>Для многоконфигурационного генератора Visual Studio:</p>
<pre><code class="language-text">cmake -S . -B build -DBUILD_TESTING=ON
cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure --no-tests=error
</code></pre>
<p>Сначала выполняется сборка: обычный запуск <code>ctest</code> сам не пересобирает изменённые исходники. Здесь CTest запускает <strong>одну</strong> тестовую программу, а внутри неё выполняются <strong>13</strong> проверок. Параметр <code>-V</code> включает вывод успешного теста: здесь это <code>13 checks passed</code>. Параметр <code>--no-tests=error</code> помогает заметить ситуацию, когда тесты вообще не были зарегистрированы.</p>
<p><a href="https://cmake.org/cmake/help/latest/command/add_test.html" rel="noopener noreferrer nofollow">Регистрация теста</a> · <a href="https://cmake.org/cmake/help/latest/manual/ctest.1.html" rel="noopener noreferrer nofollow">запуск CTest</a>.</p>

<h3>Как выглядит отказ работающего теста</h3>
<p>В предыдущем примере правильная проверка <code>Check(9, 1)</code> проходит: среди 1..9 подходит одно число. Для ошибочного ожидания <code>Check(9, 2)</code> та же функция получает фактическое значение 1 и печатает:</p>
<pre><code class="language-text">n=9: expected 2, got 1
</code></pre>
<p><code>Check</code> возвращает <code>false</code>, выражение <code>!Check(...)</code> увеличивает <code>failures</code>, а тестовая программа завершается с кодом 1. CTest показывает отказ. Так отрицательный контроль связывает реальную проверку, диагностическое сообщение и статус запуска; зелёный результат без выполненных проверок ничего не подтверждает. Возвращение ожидания 1 восстанавливает успешный результат.</p>
<p>Другая ошибка — замена формулы <code>(n + 1) / 10</code> на <code>n / 10</code>. Для 8 обе формулы дают 0, но для 9 правильный ответ 1, а ошибочный 0. Именно поэтому соседние точки границы информативнее одного произвольного большого значения.</p>
<p><strong>Тестирование и измерение времени решают разные задачи.</strong> Быстрый запуск не означает правильный ответ. Отображаемые 0 мс могут быть следствием разрешения таймера. Для сравнения скорости нужны сопоставимые входы, условия запуска и достаточная длительность измерения.</p>
<h4>Переход к GoogleTest</h4>
<p>GoogleTest организует проверки в именованные тесты. <code>TEST(InterestingNumbers, Boundary)</code> задаёт имя набора и теста, а <code>EXPECT_EQ(1, CountInterestingInInterval(9))</code> сравнивает результат с ожиданием. Программа из предыдущего шага работает без GoogleTest: CTest запускает исполняемый файл, а библиотека утверждений нужна лишь для более удобной организации самих проверок.</p>
<p>Следующий шаг показывает отдельную закреплённую зависимость и объясняет реакции <code>EXPECT_*</code> и <code>ASSERT_*</code>. <h2>GoogleTest: выбираем подходящую проверку</h2>
<p><strong>Цель:</strong> различать <code>EXPECT_*</code> и <code>ASSERT_*</code>, правильно сравнивать строки и понимать, какая настройка нужна для запуска тестов GoogleTest.</p>
<p>Это дополнительный шаг. Предыдущий пример уже работает со стандартной библиотекой и CTest. <strong>GoogleTest — отдельная зависимость</strong>, а не часть C++ или CMake. Ниже приведена сборка с закреплённой версией GoogleTest <code>v1.17.0</code>; другие способы подключения описаны в <a href="https://google.github.io/googletest/quickstart-cmake.html" rel="noopener noreferrer nofollow">официальной инструкции CMake</a>. CTest запускает тестовые программы, а GoogleTest предоставляет проверки и организует тесты внутри программы.</p>
<h3>Что происходит при неудачной проверке</h3>
<table><thead><tr><th>Проверка</th><th>Поведение при неудаче</th><th>Когда подходит</th></tr></thead><tbody>
<tr><td><code>EXPECT_*</code></td><td>Регистрирует отказ, текущая функция продолжает выполняться.</td><td>Независимые сравнения, чтобы увидеть несколько ошибок за один запуск.</td></tr>
<tr><td><code>ASSERT_*</code></td><td>Регистрирует отказ и немедленно завершает текущую функцию.</td><td>Без успешного результата дальнейшие действия в этой функции небезопасны или бессмысленны.</td></tr>
</tbody></table>
<p>Например, перед обращением к первому элементу полученного вектора можно проверить <code>ASSERT_FALSE(values.empty())</code>. Если проверка написана прямо в теле теста, остальные строки этого тела при отказе не выполнятся. Если она находится во вспомогательной <code>void</code>-функции, завершается только эта функция: вызывающий код автоматически не прерывается. Отказ одной проверки не означает немедленного завершения всей программы со всеми тестами.</p>
<h3>Фрагмент для проекта с подключённым GoogleTest</h3>
<p>Ниже содержимое отдельного файла <code>gtest_assertions.cpp</code>. Он использует объявление из <code>interesting.hpp</code> и ту же реализацию из <code>interesting.cpp</code>, что и приложение. Это не самостоятельная программа: ей нужны GoogleTest и отдельная цель сборки, показанная далее. <code>GTest::gtest_main</code> предоставляет точку входа; не добавляйте в эту цель прежний <code>tests.cpp</code> с собственным <code>main</code>. Готовая цель <code>interesting_tests</code> из предыдущего шага остаётся отдельным примером.</p>
<pre><code class="language-cpp">#include "interesting.hpp"
#include &lt;gtest/gtest.h&gt;
#include &lt;string&gt;

TEST(InterestingNumbers, HandlesCarryBoundary) {
    EXPECT_EQ(0LL, CountInterestingInInterval(8));
    EXPECT_EQ(1LL, CountInterestingInInterval(9));
    EXPECT_EQ(1LL, CountInterestingInInterval(10));
}

TEST(StringComparisons, ComparesContents) {
    const std::string text{"cpp"};
    EXPECT_EQ(std::string{"cpp"}, text);

    const char expected[] = "cpp";
    const char actual[] = "cpp";
    EXPECT_STREQ(expected, actual);
}
</code></pre>
<p>Первый тест содержит три независимые проверки функции на границе переноса разряда. <code>InterestingNumbers</code> — имя набора, <code>HandlesCarryBoundary</code> — имя теста. Оба имени — допустимые идентификаторы C++; согласно рекомендациям GoogleTest выбираем имена без подчёркиваний.</p>
<p>Второй тест иллюстрирует выбор сравнения. Здесь <code>std::string</code> — объект, который хранит строковое значение и управляет его памятью; полное введение следует в <a href="https://stepik.org/lesson/770589/step/1" rel="noopener noreferrer nofollow">модуле 9</a>. Массивы <code>char</code> уже знакомы по <a href="https://stepik.org/lesson/770586/step/4" rel="noopener noreferrer nofollow">примеру нулевого терминатора</a>. Для этого теста достаточно различать содержимое строки и адрес её символов. Для <code>std::string</code> подходит <code>EXPECT_EQ</code>: сравнивается содержимое строк. Для C-строк, то есть нуль-терминированных последовательностей <code>char</code>, содержимое сравнивает <code>EXPECT_STREQ</code> (или <code>ASSERT_STREQ</code>). Обычное сравнение двух указателей через <code>EXPECT_EQ</code> проверяет адреса. Два разных массива могут содержать одинаковый текст и иметь разные адреса.</p>
<p>К проверке можно добавить пояснение, например <code>EXPECT_EQ(1LL, CountInterestingInInterval(9)) &lt;&lt; "carry at 9";</code>. Оно появится в сообщении при отказе. Держите ожидание независимым от реализации: вычислять обе стороны одной и той же формулой не полезнее, чем сравнивать результат с собой.</p>
<p>Если нескольким тестам понадобится одинаковая подготовка, позже можно изучить <strong>тестовые фикстуры</strong> — классы с общей настройкой. Для текущих проверок они не требуются. Подробности: <a href="https://google.github.io/googletest/primer.html" rel="noopener noreferrer nofollow">GoogleTest Primer</a> и <a href="https://google.github.io/googletest/reference/assertions.html" rel="noopener noreferrer nofollow">справочник проверок</a>.</p>
<h3>Воспроизводимая сборка GoogleTest-примера</h3>
<p>Полный пример находится в отдельной папке: <code>gtest_assertions.cpp</code>, общие <code>interesting.hpp</code> и <code>interesting.cpp</code>, а также следующий <code>CMakeLists.txt</code>. Он загружает официальный GoogleTest с закреплённым commit <code>52eb8108c5bdec04579160ae17225d66034bd723</code>, соответствующим тегу <code>v1.17.0</code>. Для первой настройки нужны Git и доступ к GitHub. Это конкретная проверенная версия, а не автоматически обновляемая ссылка на текущую ветку.</p>
<pre><code class="language-cmake">cmake_minimum_required(VERSION 3.22)

    GIT_TAG 52eb8108c5bdec04579160ae17225d66034bd723
)

    "${INTERESTING_SOURCE_DIR}/interesting.cpp")
target_include_directories(interesting_for_gtest PUBLIC
    "${INTERESTING_SOURCE_DIR}")
add_executable(google_examples gtest_assertions.cpp)
target_link_libraries(google_examples PRIVATE
    interesting_for_gtest GTest::gtest_main)

foreach(target IN ITEMS interesting_for_gtest google_examples)
    if(MSVC)
        target_compile_options(${target} PRIVATE /W4 /permissive-)

gtest_discover_tests(google_examples)

<h3>Разбор выбора инструмента и проверки</h3>
<p>Для программы из 13 проверок GoogleTest не требуется: обычные условия и коды завершения уже сообщают результат CTest.
