<h3>Git: сохраняем объяснимую историю программы</h3>
<p><strong>Цель шага:</strong> различать рабочие файлы, подготовленные изменения и сохранённую версию. Git — распределённая система контроля версий: обычный локальный репозиторий хранит историю проекта, поэтому коммиты и просмотр истории доступны без подключения к серверу.</p>
<table><thead><tr><th>Часть рабочего процесса</th><th>Смысл</th><th>Команда</th></tr></thead><tbody>
<tr><td>Рабочее дерево</td><td>Файлы, которые вы сейчас редактируете.</td><td><code>git diff</code> показывает изменения отслеживаемых файлов относительно индекса.</td></tr>
<tr><td>Индекс (staging area)</td><td>Содержимое, подготовленное для следующего коммита.</td><td><code>git add main.cpp</code>, затем <code>git diff --staged</code>.</td></tr>
<tr><td>Коммит</td><td>Сохранённый снимок подготовленного состояния с сообщением и связью с историей.</td><td><code>git commit</code>, <code>git log</code>.</td></tr>
</tbody></table>
<p><code>git add</code> запоминает содержимое файла на момент вызова. Если после этого снова отредактировать файл, новые изменения не попадут в индекс автоматически. Команда <code>git status</code> помогает увидеть обе группы изменений.</p>
<p>Git и GitHub — разные вещи. Git ведёт историю локально; GitHub и другие серверы помогают хранить общую копию и обсуждать изменения. Локальный коммит ещё не отправлен на сервер: для отправки служит <code>git push</code>.</p>
<p>Обычное полное клонирование даёт историю репозитория; поверхностное клонирование может ограничивать её глубину. История помогает восстановить закоммиченные версии, но не является резервной копией никогда не сохранённых изменений.</p>
<h3>Разобранная ситуация</h3><p>После <code>git add main.cpp</code> автор дописал строку и выполнил коммит без повторного <code>add</code>. Эта строка не вошла в коммит: индекс сохранил более раннее содержимое. Она остаётся рабочим изменением, видимым через <code>git diff</code>.</p><p>Официальное руководство: <a href="https://git-scm.com/docs/gittutorial" rel="noopener noreferrer nofollow">gittutorial</a>.</p>

<h2>Снимок, история и идентификаторы Git</h2>
<p>Коммит описывает сохранённое состояние проекта и ссылается на предшествующие коммиты. Git хранит объекты содержимого, деревья каталогов и коммиты; их идентификаторы вычисляются из содержимого. В представлении истории это позволяет связать конкретную версию файла с конкретным изменением.</p>
<p>Логическая модель — снимки состояния. Внутреннее хранение может использовать сжатие и дельты похожих объектов, но разработчик работает с версиями, а не вручную собирает цепочку текстовых исправлений.</p>
<p><strong>Разбор:</strong> если в коммите изменена строка вывода, новый коммит имеет другой идентификатор. Старый коммит продолжает обозначать прежний снимок, пока остаётся доступным в репозитории. Имя ветки может передвинуться на новый коммит; идентификатор старого коммита от этого не меняется.</p>
<p>Хеш помогает обнаруживать несоответствие содержимого идентификатору, но сам по себе не подтверждает личность автора. Проверка подписи и доверия к ключу — отдельный механизм. История исходников также не восстанавливает никогда не сохранённые изменения и не заменяет резервное копирование всех рабочих данных.</p>

<h2>Ветки, общий репозиторий и обсуждение изменений</h2>
<p>Ветка Git — перемещаемая ссылка на коммит. Она даёт отдельной линии изменений имя. В одном рабочем дереве переключение ветки обычно меняет видимые файлы; ветка не является отдельной физической папкой.</p>
<p><strong>Разбор:</strong> <code>main</code> и <code>explain-output</code> сначала указывают на один коммит. После нового коммита во второй ветке она продвигается, а <code>main</code> сохраняет прежнюю позицию. При объединении веток Git пытается совместить изменения. Если они несовместимы автоматически, возникает конфликт, который требует осмысленного разрешения.</p>
<p>Удалённый репозиторий хранит другую доступную копию истории. <code>fetch</code> получает сведения и объекты из него, <code>push</code> передаёт локальные изменения согласно правилам сервера. Сам по себе локальный коммит ещё не опубликован.</p>
<p>GitHub и похожие сервисы дополняют Git обсуждениями, pull request и автоматическими проверками. Pull request — запрос на рассмотрение и объединение изменений в сервисе, а не отдельный вид коммита Git. Ни наличие ветки, ни успешное слияние автоматически не доказывают корректность C++.</p>
<p>Эта модель останется полезной при обновлении функций: история отвечает «что изменилось», сборка — «собирается ли версия», а проверка результата — «соответствует ли она контракту».</p>

<h2>Изменение программы как последовательность решений</h2>
<p>История полезна, когда коммит выражает понятную причину изменения: исправлен контракт функции, уточнено сообщение или добавлено описание сборки. Сообщение «всё исправлено» почти не помогает понять последствия.</p>
<p>Рассмотрим изменение функции: раньше вход предполагался положительным, теперь разрешён и ноль. До изменения реализации важно уточнить обещанный результат для нуля. Затем меняются объяснение, код и проверки этого контракта. Проверка различий показывает, что в коммит не попали посторонние файлы.</p>
<p>При рассмотрении изменения сравниваются не только строки кода, но и смысл: сохранились ли требования, корректно ли обрабатываются границы и воспроизводима ли сборка. Это связывает Git с темами функций и тестирования.</p>
<p>В репозитории обычно хранят исходники и описание сборки. Восстанавливаемые объектные и исполняемые файлы помещают в отдельный каталог сборки и исключают из обычной истории. <code>.gitignore</code> действует на неотслеживаемые файлы; уже отслеживаемый файл не исчезает из истории от добавления правила.</p>

<h2>Разобранная история двух версий</h2>
<p>Пусть в репозитории уже есть полный <code>main.cpp</code>, выводящий <code>Hello, C++!</code>. В этом объяснении команды иллюстрируют действия автора; создавать отдельный учебный репозиторий для чтения не требуется.</p>
<pre><code class="language-bash">git add main.cpp
git diff --staged
git commit -m "Add greeting"</code></pre>
<p><code>add</code> поместил текущее содержимое в индекс. <code>diff --staged</code> показал будущую разницу с последним коммитом. <code>commit</code> сохранил подготовленное состояние. Имя и адрес автора должны быть настроены заранее; это метаданные коммита, а не вход на GitHub.</p>
<p>Далее автор заменил приветствие на <code>Hello, reader!</code>, успешно собрал программу и получил именно этот вывод. Следующая последовательность сохраняет вторую версию:</p>
<pre><code class="language-bash">git diff
git add main.cpp
git diff --staged
git commit -m "Clarify greeting"
git show HEAD~1:main.cpp</code></pre>
<p>Первый <code>diff</code> показывает рабочие изменения относительно индекса; после <code>add</code> версия для коммита уже выбрана. Последняя команда показывает файл из предыдущего коммита этой простой линейной истории и не заменяет рабочий файл.</p>
<p>Если после <code>add</code> исходник был ещё раз изменён, новые строки останутся только в рабочем дереве до повторного добавления. Сохранение исходника в редакторе, подготовка версии и коммит — три разные операции.</p>
<p>Для каталога сборки <code>build</code> правило <code>/build/</code> в <code>.gitignore</code> исключает неотслеживаемые результаты из обычного добавления. Смысл примера — сохранять воспроизводимые исходники и понимать, какая именно версия попала в историю. Далее '+link(774618,1,'CMake')+' описывает, как эту версию собрать.</p>
