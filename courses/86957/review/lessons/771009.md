<h3>Система контроля версий Git</h3>

<p>Git — абсолютный лидер по популярности среди современных систем управления версиями. Это развитый проект с активной поддержкой и открытым исходным кодом. Система Git была изначально разработана в 2005 году Линусом Торвальдсом — создателем ядра операционной системы Linux. Git применяется для управления версиями в рамках колоссального количества проектов по разработке ПО, как коммерческих, так и с открытым исходным кодом. Система используется множеством профессиональных разработчиков программного обеспечения. Она превосходно работает под управлением различных операционных систем и может применяться со множеством интегрированных сред разработки (IDE).</p>

<p>Git — система управления версиями с распределённой архитектурой. При обычном полном клонировании разработчик получает локальный репозиторий с историей проекта и рабочее дерево файлов. Это позволяет просматривать историю и создавать коммиты без постоянного обращения к центральному серверу. Существуют и специальные режимы, например поверхностное клонирование с ограниченной историей.</p>

<p>Разработка в Git ориентирована на обеспечение высокой производительности, безопасности и гибкости распределенной системы.</p>

<h3>Производительность, Безопасность и Гибкость Git</h3>

<p>Git показывает очень высокую производительность в сравнении со множеством альтернатив. Это возможно благодаря оптимизации процедур фиксации коммитов, создания веток, слияния и сравнения предыдущих версий. Алгоритмы Git разработаны с учетом глубокого знания атрибутов, характерных для реальных деревьев файлов исходного кода, а также типичной динамики их изменений и последовательностей доступа.</p>

<p>Некоторые системы управления версиями руководствуются именами файлов при работе с деревом файлов и ведении истории версий. Вместо обработки названий система Git анализирует содержимое. Это важно, поскольку файлы исходного кода часто переименовывают, разделяют и меняют местами. Git может хранить отдельные сжатые объекты целиком, а при упаковке в pack-файлы — дополнительно использовать дельта-кодирование для похожих объектов. Кроме того, такие файлы в чистом виде хранят объекты с содержимым каталога и метаданными версий.</p>

<p><em>Вместе с тем распределенная архитектура системы сама по себе обеспечивает существенный прирост производительности.</em></p>

<p>Git идентифицирует объекты по хешам их содержимого и связывает ими файлы, деревья, коммиты и теги. Это позволяет проверять целостность объектов и обнаруживать изменение содержимого относительно известных идентификаторов. Само хеширование не подтверждает личность автора и не запрещает создавать новую историю.</p>

<p>Для проверки подлинности коммитов и тегов можно использовать криптографические подписи и проверять доверие к ключам подписантов. Обычное наличие истории в Git само по себе не гарантирует её авторство.</p>

<p>В некоторых других системах управления версиями отсутствует защита от тайного внесения изменений. Это может стать серьезной угрозой информационной безопасности в любой организации, занимающейся разработкой ПО.</p>

<p>Гибкость — одна из основных характеристик Git. Она проявляется в поддержке различных нелинейных циклов разработки, эффективности использования с малыми и крупными проектами, а также совместимости со многими системами и протоколами.</p>

<p>В отличие от SVN, система Git рассчитана прежде всего на создание веток и использование тегов. Поэтому процедуры с участием веток и тегов (например, объединение и возврат к предыдущей версии) сохраняются в истории изменений. Не все системы управления версиями обладают настолько широкими возможностями отслеживания.</p>

<h3>Git — признанный стандарт</h3>

<p>Git является самым популярным инструментом своего класса и поэтому привлекателен по ряду причин. В Atlassian управление исходным кодом проектов практически всегда осуществляется в Git.</p>

<p>Великое множество профессиональных разработчиков уже получили опыт использования Git, а выпускники высших учебных заведений зачастую знакомы только с этой системой. В некоторых организациях работникам требуется обучение при переходе на Git с других систем управления версиями, однако многие разработчики (как штатные, так и будущие сотрудники) уже обладают необходимыми знаниями.</p>

<p>Однако привлекательность Git обусловлена не только высокой популярностью среди разработчиков. В системе также предусмотрена интеграция различных инструментов и сервисов, включая интегрированные среды разработки и собственные инструменты Atlassian. В число последних входит настольный клиент для распределенных систем управления версиями <a href="http://www.sourcetreeapp.com/ru/" rel="noopener noreferrer nofollow">Sourcetree</a>, система отслеживания задач и проектов <a href="https://www.atlassian.com/ru/software/jira" rel="noopener noreferrer nofollow">Jira</a>, а также сервис размещения кода <a href="https://bitbucket.org/product/ru/" rel="noopener noreferrer nofollow">Bitbucket</a>.</p>

<p>Начинающим разработчикам, которые хотят приобрести ценные навыки работы с инструментами разработки ПО, следует изучить Git как одну из систем управления версиями.</p>

<h3>Git — это качественный проект с открытым кодом</h3>

<p>Проект Git имеет открытый исходный код, а также активно поддерживается и непрерывно развивается уже более 10 лет. Кураторы проекта продемонстрировали взвешенный и продуманный подход к выполнению требований пользователей, регулярно выпуская релизы для повышения удобства и расширения функциональных возможностей системы. Качество ПО с открытым исходным кодом легко проверяется, и многие организации всецело доверяют таким продуктам.</p>

<p>Вокруг Git сформировалось многочисленное сообщество пользователей, а сам проект получает активную поддержку со стороны сообщества. Система обладает подробной и качественной документацией: всем желающим в числе прочего доступны книги, учебные руководства, специализированные веб‑сайты, подкасты и обучающие видеоролики.</p>

<p>Git — это система с открытым исходным кодом, поэтому разработчики‑любители могут пользоваться ей совершенно бесплатно. В сфере разработки ПО с открытым исходным кодом Git определенно выступает главным преемником успешных систем управления версиями предыдущих поколений, таких как SVN и CVS.</p>

<h3>Критика Git</h3>

<p>Git нередко критикуют за сложность освоения: одни термины могут быть незнакомы новичкам, а другие — иметь иное значение. Так, понятие <code>revert</code> (в Git — отмена изменений с записью нового коммита) в Git имеет другой смысл, нежели в SVN и CVS. Тем не менее Git — очень мощная система, предлагающая пользователям широкие возможности. Их изучение займет какое‑то время, однако усвоенные навыки помогут участникам команды работать намного быстрее.</p>

<p>Команды, перешедшие на Git с нераспределенной системы управления версиями, могут захотеть и дальше пользоваться центральным репозиторием. Несмотря на распределенную архитектуру, Git допускает возможность создания классического репозитория, где сохраняются все изменения проекта. При этом в Git продуктивность разработчиков не зависит от доступности и производительности «центрального» сервера. Каждому пользователю доступна полная копия репозитория, в которой он может просматривать всю историю проекта даже в периоды отсутствия соединения с сетью и перебоев в системе. Распределенная архитектура и гибкость Git позволяют участникам проекта работать в удобном ритме и пользоваться уникальными преимуществами, о которых они могли не подозревать раньше.</p>

<h3>Git в разработке ПО</h3>

<p>Переход с централизованной системы управления версиями на Git меняет подход команды к разработке программного обеспечения. А если ваша компания полагается на свое программное обеспечение для критически важных приложений, изменение процесса разработки повлияет на весь бизнес.</p>

<p style="text-align: center;"><img alt="" height="191" name="image.png" src="https://ucarecdn.stepik.net/b28e5f84-ad7f-4c30-88a4-3b5b69cad8d8/" width="323"></p>

<p> </p>

<h3>Рабочий процесс с функциональными ветками</h3>

<p>Одно из самых больших преимуществ Git — возможность ветвления. В отличие от централизованных систем управления версиями, в Git ветки не требуют много ресурсов и легко объединяются. Это позволяет реализовать рабочий процесс с функциональными ветками, который так популярен среди пользователей Git.</p>

<p style="text-align: center;"><img alt="" height="210" name="image.png" src="https://ucarecdn.stepik.net/4be7634e-e6c0-4bc9-8d72-fa8851b6bd42/" width="256"></p>

<p> </p>

<p>Функциональные ветки служат изолированной средой для каждого изменения в базе кода. Когда разработчик хочет приступить к работе над частью проекта — неважно, большой или маленькой, — он создает новую ветку. Это помогает сохранять главную ветку пригодной к развёртыванию, если изменения проверяют и тестируют перед слиянием.</p>

<p>Использование функциональных веток не только более надежно, чем прямое редактирование окончательного кода, но и дает организационные преимущества: процесс разработки можно согласовать с <a href="https://www.atlassian.com/ru/agile/scrum/backlogs" rel="noopener noreferrer nofollow">бэклогом agile</a>. Например, можно реализовать политику, в которой каждая задача <a href="https://www.atlassian.com/ru/software/jira" rel="noopener noreferrer nofollow">Jira</a> будет выполняться в отдельной функциональной ветке.</p>

<h3>Распределенная разработка</h3>

<p>В SVN каждый разработчик получает рабочую копию, которая ссылается на единый центральный репозиторий. Git же — это распределенная система управления версиями. При обычном полном клонировании каждый разработчик получает и рабочее дерево, и локальный репозиторий с историей коммитов.</p>

<p style="text-align: center;"><img alt="" height="206" name="image.png" src="https://ucarecdn.stepik.net/08388fba-2de7-49a1-9010-cc161cbb0f23/" width="384"></p>

<p>Благодаря локальной доступности всей истории Git работает быстро, поскольку для создания коммитов, проверки предыдущих версий файла или вычисления разницы между коммитами не требуется сетевое подключение.</p>

<p>Распределённая разработка также позволяет продолжать локальную работу при недоступности общего сервера: разработчик может создавать коммиты в своём репозитории. Для передачи изменений на сервер соединение всё равно потребуется. Ошибочный коммит сам по себе не блокирует возможность других разработчиков работать ни в Git, ни в SVN.</p>

<p>Распределенная разработка, как и функциональные ветки, повышает надежность среды. Даже если разработчик вдруг уничтожит свой репозиторий, он может клонировать сохранившийся репозиторий и восстановить имеющуюся там историю. Неопубликованные локальные изменения таким способом не восстанавливаются.</p>

<h3>Пул-реквесты</h3>

<p>Многие инструменты управления исходным кодом, такие как <a href="https://bitbucket.org/" rel="noopener noreferrer nofollow">Bitbucket</a> и <a href="https://github.com" rel="noopener noreferrer nofollow">GitHub</a>, дополняют базовую функциональность Git запросами pull. С помощью запроса pull можно попросить другого разработчика объединить одну из ваших веток со своим репозиторием. Благодаря этому руководителям легче отслеживать работу над проектом, а разработчикам — получать отзывы о своем коде, прежде чем интегрировать его с остальной базой кода.</p>

<p> </p>

<p style="text-align: center;"><img alt="" height="208" name="image.png" src="https://ucarecdn.stepik.net/d6b2ceda-2110-4abf-9c16-67742a056582/" width="286"></p>

<p>Поскольку запросы pull — это, по сути, потоки комментариев к функциональной ветке, они чрезвычайно универсальны. Например, если разработчик сталкивается с трудной задачей, он может открыть запрос pull, чтобы попросить помощи у остальной команды. А для младших разработчиков запрос pull даёт возможность получить проверку кода до его слияния с основной веткой.</p>
