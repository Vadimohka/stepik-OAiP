<h2>Точка входа исполняемого файла и функция main</h2>
<p>Это дополнительное объяснение процесса запуска. Для первых программ достаточно стандартной модели: реализация подготавливает нужную среду, затем выполняется <code>main</code>. Имена системных процедур и устройство исполняемого файла зависят от платформы и не требуются для написания обычного <code>main</code>.</p>
<p>У исполняемого файла может быть низкоуровневая <strong>точка входа</strong> — адрес, с которого среда начинает передавать управление коду этого файла. В некоторых цепочках инструментов на ELF она связана с именем <code>_start</code>. Имя не является ключевым словом C++: например, GNU linker позволяет отдельно задавать точку входа. Не каждая платформа использует именно <code>_start</code>.</p>
<table><thead><tr><th>Уровень</th><th>Роль в типичном запуске пользовательского процесса</th></tr></thead><tbody><tr><td>Операционная система и загрузка</td><td>Подготавливают адресное пространство и предусмотренные форматом данные для исполнения</td></tr><tr><td>Динамический загрузчик, если он используется</td><td>Подключает необходимые разделяемые компоненты и выполняет связанные с ними действия</td></tr><tr><td>Стартовый код и библиотека среды выполнения</td><td>Организуют оставшуюся подготовку и переход к main по соглашениям платформы</td></tr><tr><td>main</td><td>Выполняет основную логику пользовательской программы</td></tr></tbody></table>
<p>Точное распределение действий между этими частями различается. Это не обещание четырёх обязательных отдельных программ или неизменного порядка всех операций. Например, детали динамической инициализации объектов определяются правилами C++, а не одним фиксированным списком действий <code>_start</code>.</p>
<p><strong>Концептуальная схема действий реализации, не код C++ и не ассемблер:</strong></p>
<pre><code class="language-text">подготовить условия выполнения программы
передать управление основной функции main
после её возврата выполнить предусмотренное нормальное завершение
передать статус завершения окружению
</code></pre>
<p>Стандарт не разрешает использовать <code>main</code> как обычную вызываемую функцию в программе C++. Поэтому схема не предлагает написать собственный вызов <code>main()</code>. Включение процессорных кэшей и начальная настройка аппаратуры после сброса — задачи другого уровня; их нельзя автоматически приписывать <code>_start</code> обычного процесса в операционной системе.</p>
<p><a href="https://stepik.org/lesson/776128/step/3" rel="noopener noreferrer nofollow">Следующий шаг разделяет инициализацию объектов и библиотеки</a>, а <a href="https://stepik.org/lesson/776128/step/6" rel="noopener noreferrer nofollow">заключение урока сопоставляет запуск процесса с запуском машины</a>.</p>

<h3>Настройка среды выполнения</h3>

<p>Ниже перечислены типичные обязанности кода запуска и загрузчика в рассматриваемой ELF/Linux-среде. Набор действий и их распределение зависят от платформы; это не универсальный список функций runtime, обязательный для любой программы C++:</p>

<ol>
	<li>Выполнить необходимые релокации (если они не обрабатываются загрузчиком или компоновщиком)</li>
	<li>Обеспечить требуемую начальную инициализацию объектов</li>
	<li>Подготовить argc и argv согласно требованиям main: argc неотрицателен, argv указывает на массив, а argv[argc] — нулевой указатель</li>
	<li>Выполнить дополнительные шаги настройки, требуемые реализацией стандартной библиотеки C/C++.</li>
</ol>

<p>Для объектов со статической продолжительностью хранения различают статическую и, если она нужна, динамическую инициализацию. Это правила жизни объектов; их нельзя свести к одному обязательному списку действий до <code>main</code>.</p>

<p>Во-первых, должна быть обеспечена статическая инициализация объектов со статической продолжительностью хранения: постоянная инициализация, когда она применима, либо нулевая инициализация. Это не определяется только наличием знака = в объявлении: возможны и другие формы инициализатора. В типичном ELF-образе данные с начальным нулевым содержимым размещаются в .bss; обнуление соответствующей памяти обеспечивает загрузчик или код запуска. Объём памяти при этом не становится нулевым — нулевым становится её содержимое.</p>

<p>Во-вторых, может понадобиться динамическая инициализация. У нелокальных объектов со статической продолжительностью хранения она может выполняться до <code>main</code> или откладываться в предусмотренных стандартом случаях. Отдельное правило действует для локальной переменной <code>static</code>: её динамическая инициализация происходит при первом прохождении через объявление. Поэтому локальный объект может быть создан уже после начала <code>main</code>, хотя его память имеет статическую продолжительность хранения. Подробное различие памяти и живого объекта дано в <a href="https://stepik.org/lesson/853536/step/1" rel="noopener noreferrer nofollow">модуле 15: продолжительность хранения и время жизни</a>. В реализациях на основе ELF для вызова функций инициализации могут использоваться .init, .init_array и другие механизмы. GCC также предоставляет расширение __attribute__((constructor)), помечающее функцию для вызова до main; это не стандартный синтаксис C++.</p>

<p>Эти дополнительные шаги инициализации среды выполнения выполняются для многих программ (но не для всех):</p>

<ol>
	<li>Инициализация кучи</li>
	<li>Инициализация stdio (т.е. stdin, stdout, stderr)</li>
	<li>Инициализация поддержки исключений (при использовании C++)</li>
	<li>Регистрация деструкторов и другие функции очистки, которые будут выполняться при выходе из программы (используя atexit и __cxa_atexit)</li>
	<li>Подготовка переменных среды</li>
</ol>

<p>На практике грань между обязанностями _start и инициализацией среды выполнения языка C может быть нечеткой. Некоторые реализации _start обрабатывают части настройки среды выполнения напрямую, такие как установка содержимого раздела .bss равным 0 и вызов глобальных конструкторов. Другие реализации обрабатывают эти задачи как часть процедур настройки среды выполнения языка C.</p>

<p>В некоторых цепочках GNU в компоновке участвуют готовые объектные файлы <code>crti.o</code>, <code>crtbegin.o</code>, <code>crtend.o</code> и <code>crtn.o</code>. Это части поддержки запуска и завершения, а не обязательные исходники программы ученика. Например, для большинства соответствующих целей GCC файлы <code>crtbegin.o</code> и <code>crtend.o</code> получают из <code>crtstuff.c</code>; считать все эти компоненты исходными файлами ассемблера с расширением <code>.s</code> неверно. Состав и имена зависят от платформы; их подготовку организует набор инструментов. Это продолжает различие между исходным и объектным файлом из <a href="https://stepik.org/lesson/763038/step/3" rel="noopener noreferrer nofollow">объяснения этапов сборки</a>.</p>

<h2>Вспомогательная инфраструктура программы</h2>
<p>Словом <em>scaffolding</em> иногда называют служебную инфраструктуру, которая поддерживает выполнение программы. Это удобный неформальный термин, а не отдельный обязательный этап трансляции или стандартная функция C++ с фиксированным набором обязанностей.</p>
<p>Часть поддержки нужна для реализации правил языка и библиотеки: работы стандартных потоков, завершения объектов, обработки исключений в программе, которая их использует. Другая часть зависит от платформы, режима сборки и подключённых инструментов: диагностические проверки, сбор статистики, профилирование. В одной реализации эти действия могут находиться в библиотеке среды выполнения, в добавленном компилятором коде или в отдельных компонентах.</p>
<p>Например, обычная программа с <code>std::cout</code> опирается на стандартный поток вывода. Но из этого не следует, что любая её ошибка обращения к памяти будет автоматически обнаружена. C++ допускает операции с предусловиями, нарушение которых приводит к неопределённому поведению. Дополнительный инструмент может диагностировать некоторые такие случаи, однако отсутствие сообщения не доказывает отсутствие ошибки.</p>
<p>Поэтому в разборе запуска полезно спрашивать, к какому уровню относится действие: это требование языка, документированная обязанность конкретной библиотеки или выбранная диагностическая возможность? Термин «служебная инфраструктура» сам по себе не отвечает на этот вопрос и не обещает обязательного журнала всех действий программы.</p>
<p>Для изучения программы сначала достаточно понимать её собственные данные и операции. В <a href="https://stepik.org/lesson/778425/step/1" rel="noopener noreferrer nofollow">модуле 8 о тестировании</a> будет объяснено, как проверки поддерживают уверенность в поведении; время жизни и автоматическое освобождение ресурсов рассматриваются в <a href="https://stepik.org/lesson/853536/step/1" rel="noopener noreferrer nofollow">модуле 15</a>. Эти модели позволяют объяснять работу программы независимо от конкретного имени её стартовой процедуры.</p>

<h2>Возврат из main и завершение программы</h2>
<p>В обычной программе C++ значение, возвращённое из <code>main</code>, сообщает окружению статус завершения. <code>return 0;</code> и возврат <code>EXIT_SUCCESS</code> обозначают успех; <code>EXIT_FAILURE</code> обозначает неуспех. Два именованных обозначения предоставляет <code>&lt;cstdlib&gt;</code>. Конкретное представление статуса в системе зависит от окружения.</p>
<p>Достижение конца тела <code>main</code> равнозначно <code>return 0;</code>. Это специальное правило основной функции, которое нельзя переносить на любую функцию, возвращающую значение. Например, уже разобранная программа с приветствием успешно завершается после инструкции вывода без явного <code>return</code>.</p>
<p>При обычном выходе из <code>main</code> сначала уничтожаются его локальные объекты с автоматической продолжительностью хранения, как при выходе из другой функции. Затем выполняется предусмотренное нормальное завершение программы, связанное со <code>std::exit</code>: в частности, выполняются предусмотренные правилами завершения действия для объектов со статической продолжительностью хранения и зарегистрированных функций очистки.</p>
<p>Сами понятия объектов, времени хранения и деструкторов будут подробно введены в модулях 6 и 13–15. Сейчас важно различие: <strong>возврат из функции</strong> завершает жизнь локальных объектов с автоматической продолжительностью хранения, а <strong>прямой вызов std::exit</strong> не раскручивает текущую цепочку вызовов с уничтожением её автоматических объектов. Локальный <code>static</code> следует другим правилам: его жизнь не заканчивается при каждом выходе из функции. Это различие раскрыто в <a href="https://stepik.org/lesson/853536/step/1" rel="noopener noreferrer nofollow">объяснении видов хранения</a>. Поэтому этот вызов не является безусловной заменой <code>return</code>.</p>
<p>Также нельзя обещать, что очистка выполнится при любом прекращении работы. Аварийное завершение, принудительная остановка процесса и отказ системы не равнозначны нормальному возврату из <code>main</code>. Первые примеры используют обычный выход из функции, чтобы поведение оставалось понятным. Связь такого выхода с освобождением ресурсов будет завершена в <a href="https://stepik.org/lesson/853536/step/2" rel="noopener noreferrer nofollow">разборе RAII</a>.</p>

<h2>Запуск процесса и запуск компьютера — разные уровни</h2>
<p>Двойной щелчок по программе или команда в терминале обычно запускают её в уже работающей операционной системе. Это не повторная загрузка всей машины. <strong>Исполняемый файл</strong> хранит программу в определённом формате, а <strong>процесс</strong> связан с её выполнением, адресным пространством и предоставленными ресурсами.</p>

<p>Даже для первой строки нет единственного универсального алгоритма «скопировать весь файл в оперативную память». Система может отображать области файла в виртуальную память и подгружать страницы по мере необходимости. Динамические библиотеки, права доступа и передача аргументов зависят от интерфейсов платформы.</p>
<p>Стандарт C++ различает <em>hosted</em>-среду, для которой описана обычная основная функция <code>main</code>, и <em>freestanding</em>-среду, где вопросы запуска определяются реализацией. Курс использует hosted-модель для полных обычных программ. Упоминание <code>_start</code> иллюстрирует возможную реализацию нижнего уровня и не добавляет обязанность писать такую функцию в учебном исходнике.</p>
<p>Сборка и запуск тоже разные действия. Изменение исходника требует успешной повторной сборки, прежде чем новый исполняемый файл сможет показать изменённое поведение. <a href="https://stepik.org/lesson/771009/step/1" rel="noopener noreferrer nofollow">Git сохраняет историю исходников</a>, а <a href="https://stepik.org/lesson/774618/step/1" rel="noopener noreferrer nofollow">система сборки организует получение программы из выбранного состояния проекта</a>. Так модель запуска соединяется с практическими ролями инструментов без зависимости от рекламных описаний конкретной IDE.</p>
