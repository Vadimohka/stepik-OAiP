<h3>Статья повышенной сложности</h3>

<p><em>Данная информация крайне сложна для освоения на старте обучения, однако даже обычное прочтение помогает разобраться в вопросе «А как же запускается и выполняется программа?».</em></p>

<p>Для большинства программистов жизненный цикл программы на C или C++ начинается с функции <code>main()</code>. Они пребывают в блаженном неведении о скрытых шагах, которые произошли между вызовом программы и выполнением <code><em>main</em></code>. В зависимости от программы и компилятора, это всевозможные интересные функции, которые запускаются перед main, автоматически вставляются компилятором и компоновщиком и невидимы для случайных наблюдателей.</p>

<p><strong>В шести теоретических шагах этого урока будет исследовано, что нужно, чтобы добраться до</strong> <code>main</code>.</p>

<p>Чтобы начать исследование того, как запускаются программы, мы представим краткое описание того, что происходит в программе перед <code><em style="font-size: inherit;">main</em></code>. Шаги и обязанности, которые будут описаны, обобщены таким образом, что они применимы ко многим системам. В следующих статьях дополнительно будет представлена общая теория с анализом реальных реализаций. </p>

<h3>Функция _start</h3>

<p>В распространённых ELF-системах, например Linux, низкоуровневая точка входа исполняемого файла часто называется _start. Код запуска подготавливает среду выполнения и в конечном счёте вызывает main. Это соглашение конкретной платформы, а не обязательное имя из стандарта C++.</p>

<p>Имя и устройство точки входа зависят от системы, компилятора и среды выполнения. Например, для обычного консольного приложения MSVC используется mainCRTStartup, вызывающая main. Поэтому нельзя переносить детали _start на все программы C/C++.</p>

<p>Компоновщик задаёт точку входа исполняемого файла. Например, GNU ld позволяет указать её параметром -e или командой ENTRY в сценарии компоновки. GCC и Clang обычно выступают драйверами, вызывающими выбранный компоновщик. В обычных учебных программах менять точку входа не требуется.</p>

<p>Реализация функции _start обычно предоставляется libc. Функция _start часто пишется на ассемблере. Многие реализации хранят функцию _start в файле с именем crt0.s. Компиляторы обычно поставляются с предварительно скомпилированными объектными файлами crt0.o для каждой поддерживаемой архитектуры.</p>

<p>Хотя большая часть этого кода обычно реализуется средой выполнения C, поведение кода при запуске программы не определено стандартами C и C++. Вместо этого стандарты описывают условия, которые должны быть выполнены при вызове основной функции. Однако существует много шагов, которые обычно выполняются в большинстве реализаций _start.</p>

<p>На высоком уровне функция _start обрабатывает:</p>

<ol>
	<li>Ранняя низкоуровневая инициализация, например:
	<ol>
		<li>Настройка регистров процессора</li>
		<li>Инициализация внешней памяти</li>
		<li>Включение кэшей</li>
		<li>Настройка блока управления памятью</li>
	</ol>
	</li>
	<li>Инициализация стека и обеспечение его выравнивания согласно двоичному интерфейсу приложений</li>
	<li>Инициализация указателя фрейма (Frame pointer)</li>
	<li>Инициализация среды выполнения C/C++</li>
	<li>Инициализация вспомогательной инфраструктуры среды выполнения (scaffolding), требуемой системой</li>
	<li>Переход к <code>main</code></li>
	<li>Выход из программы с кодом возврата из <code>main</code> </li>
</ol>

<p>Хотя процедура _start обычно включает в себя эти действия, конкретный порядок и реализация варьируются от системы к системе. Например, ранний низкоуровневый код инициализации обычно встречается во встроенных системах без операционной системы, но редко на хост-машинах с ОС. В коде запуска вашей программы Linux или OS X будет несколько функций, которые вы не найдете во встроенном коде запуска.</p>

<p>Давайте взглянем на простую реализацию функции x86_64 _start, взятой из OS Dev wiki. Это учебный пример с заданным ниже контрактом загрузчика; он не является готовой точкой входа обычного процесса Linux. Вспомогательные функции здесь только обозначены.</p>

<p>Приведенный ниже код запуска предполагает, что загрузчик программы поместил:</p>

<ul>
	<li>данные массивов <code>argv</code> и <code>envp</code> в стек</li>
	<li><code>argc</code> в регистр <code>%rdi</code></li>
	<li><code>argv</code> в регистр <code>%rsi</code></li>
	<li><code>envc</code> в регистр <code>%rdx</code></li>
	<li><code>envp</code> в регистр <code>%rcx</code></li>
</ul>

<p> Вот реализация _start (asm код):</p>

<pre><code class="language-cpp">.section .text

.global _start
_start:
    # Set up end of the stack frame linked list
    movq $0, %rbp
    pushq %rbp # rip=0
    pushq %rbp # rbp=0
    movq %rsp, %rbp

    # Save argc and argv on the stack
    # We need those in a moment when we call main
    pushq %rsi
    pushq %rdi

    # Prepare signals, memory allocation, stdio, etc.
    call initialize_standard_library

    # Run the global constructors.
    call _init

    # Restore argc and argv before calling main
    popq %rdi
    popq %rsi

    # Run main
    call main

    # Terminate the process with the exit code 
    # that was returned from main
    movl %eax, %edi
    call exit</code></pre>

<p>На следующем шаге углубимся и посмотрим, что происходит во время процесса настройки среды выполнения (initialize_standard_library).</p>

<h3>Настройка среды выполнения</h3>

<p>Настройка среды выполнения C/C++ является универсальным требованием для запуска программы. На высоком уровне наша настройка среды выполнения должна выполнять следующее:</p>

<ol>
	<li>Выполнить необходимые релокации (если они не обрабатываются загрузчиком или компоновщиком)</li>
	<li>Инициализация глобальной и статической памяти</li>
	<li>Подготовить argc и argv согласно требованиям main: argc неотрицателен, argv указывает на массив, а argv[argc] — нулевой указатель</li>
	<li>Выполнить дополнительные шаги настройки, требуемые реализацией стандартной библиотеки C/C++.</li>
</ol>

<p>Инициализация глобальной и статической памяти разбита на два отдельных этапа, которые заслуживают дополнительной информации.</p>

<p>Во-первых, должна быть обеспечена статическая инициализация объектов со статическим временем хранения: постоянная инициализация, когда она применима, либо нулевая инициализация. Это не определяется только наличием знака = в объявлении: возможны и другие формы инициализатора. В типичном ELF-образе данные с начальным нулевым содержимым размещаются в .bss; обнуление соответствующей памяти обеспечивает загрузчик или код запуска. Объём памяти при этом не становится нулевым — нулевым становится её содержимое.</p>

<p>Во-вторых, для объектов C++ может понадобиться динамическая инициализация. Она часто выполняется до main, однако стандарт допускает и отложенную инициализацию в оговорённых случаях. В реализациях на основе ELF для вызова функций инициализации могут использоваться .init, .init_array и другие механизмы. GCC также предоставляет расширение __attribute__((constructor)), помечающее функцию для вызова до main; это не стандартный синтаксис C++.</p>

<p>Эти дополнительные шаги инициализации среды выполнения выполняются для многих программ (но не для всех):</p>

<ol>
	<li>Инициализация кучи</li>
	<li>Инициализация stdio (т.е. stdin, stdout, stderr)</li>
	<li>Инициализация поддержки исключений (при использовании C++)</li>
	<li>Регистрация деструкторов и другие функции очистки, которые будут выполняться при выходе из программы (используя atexit и __cxa_atexit)</li>
	<li>Подготовка переменных среды</li>
</ol>

<p>На практике грань между обязанностями _start и инициализацией среды выполнения языка C может быть нечеткой. Некоторые реализации _start обрабатывают части настройки среды выполнения напрямую, такие как установка содержимого раздела .bss равным 0 и вызов глобальных конструкторов. Другие реализации обрабатывают эти задачи как часть процедур настройки среды выполнения языка C.</p>

<p>Ассемблерные исходники, которые могут встречаться во время этой части процесса запуска, - это crtbegin.s, crtend.s, crti.s и crtn.s. Компиляторы часто поставляют предварительно скомпилированные объектные файлы для поддерживаемых архитектур. Эти файлы связаны с вызовом глобальных конструкторов и деструкторов. Когда файлы не используются, эквивалентная функциональность часто реализуется на языке C и вызывается во время инициализации среды выполнения.</p>

<h3>Scaffolding</h3>

<p>В этом уроке scaffolding означает вспомогательную инфраструктуру среды выполнения, которую настраивают при запуске программы. Это употребление термина отличается от генерации файлов и каркаса нового проекта при разработке.</p>

<p>Код запуска может вызывать другие функции для настройки каркаса программы, который требуется системе. Настройка скаффолдинга программы перед main может включать:</p>

<ul>
	<li>Настройка поддержки многопоточности и локального хранилища потока</li>
	<li>Обнаружение переполнения буфера</li>
	<li>Ведение журнала стека</li>
	<li>Проверка ошибок во время выполнения</li>
	<li>Настройки локали</li>
	<li>Обработка математических ошибок</li>
	<li>Точность математической библиотеки по умолчанию</li>
</ul>

<p>Конкретные вызываемые функции скаффолдинга различаются в зависимости от реализации стандартной библиотеки и операционной системы.</p>

<h3>Переход к main()</h3>

<p>Получив полностью инициализированную систему, мы можем безопасно перейти к main и выполнить часть приложения, предназначенную для программиста.</p>

<p>Самый важный аспект: как только программа достигает main, она должна быть в состоянии, соответствующем стандартам. В противном случае предположения программы будут признаны недействительными.</p>

<h3>Возвращение из main()</h3>

<p>Мы рассмотрели путь до вызова main(). Теперь закончим объяснение обязанностей кода запуска и разберём завершение программы.</p>

<p>В показанном ранее примере после возврата из main код _start передаёт возвращённое значение в exit. В C++ возврат из main завершает время жизни её локальных объектов, после чего имеет эффект вызова std::exit с этим значением. При нормальном завершении уничтожаются объекты со статическим временем хранения и вызываются зарегистрированные функции очистки в порядке, заданном правилами языка и среды выполнения. Нельзя считать это двумя универсальными фазами «сначала все atexit, затем все деструкторы»: их порядок связан с порядком инициализации и регистрации.</p>

<p>Этот сценарий характерен для обычных программ под управлением операционной системы. Во встроенной системе без ОС завершение программы и действия после возврата из основной функции определяются реализацией.</p>

<h3>Как добраться до _start?</h3>

<p>Теперь, когда мы знаем, как наша программа попадает в main с помощью функции _start, вы можете задаться вопросом, как программа попадает в _start.</p>

<p>Есть три распространенных пути:</p>

<ul>
	<li>"Чистое железо": вектор сброса</li>
	<li>Запуск приложения через загрузчик</li>
	<li>Запуск программы через ОС</li>
</ul>

<h4>"Чистое железо": вектор сброса</h4>

<p>Встроенное приложение на "Чистом железе" без операционной системы представляет собой самый простой путь к _start.</p>

<p>Рассмотрим встроенную платформу с программой во флэш-памяти. После включения питания или сброса процессор начинает выполнение в соответствии с правилами своей архитектуры: например, получает адрес обработчика из вектора сброса. Начальный код может выполняться прямо из флэш-памяти. Если приложению или его данным нужна копия в RAM, соответствующее копирование выполняет код загрузчика или среды выполнения; это не универсальное автоматическое действие процессора до первой инструкции.</p>

<p>Обработчик прерывания сброса встроенной программы инициализирует систему после включения питания или сброса. Обработчик сброса обычно выполняет первоначальную настройку регистров процессора и критических аппаратных компонентов (таких как внешнее ОЗУ, кэш-память или блок управления памятью). Как только эта начальная конфигурация завершена, обработчик сброса переходит к _start.</p>

<p>Некоторые системы не используют стандартную библиотеку C, и в этом случае _start не будет вызываться. Вместо этого обработчик сброса вызовет другие функции настройки или непосредственно выполнит необходимые шаги настройки программы.</p>

<h4>Запуск приложения через загрузчик</h4>

<p>Многие встроенные приложения состоят из нескольких отдельных образов, которые запускаются последовательно в процессе загрузки.</p>

<p>Во многих системах используется загрузчик или гипервизор, который запускается перед загрузкой и выполнением основного приложения. Загрузчики выполняют широкий спектр действий, включая инициализацию системного оборудования, дешифрование, распаковку, проверку правильности образа встроенного ПО перед его загрузкой, выбор образа встроенного ПО для загрузки или определение того, следует ли переходить в режим обновления встроенного ПО. Сложность загрузчика зависит от требований системы; ни одна из перечисленных задач не является обязательной для всех загрузчиков.</p>

<p>Другие системы требуют инкрементного процесса загрузки, особенно когда объем основного приложения превышает объем внутренней оперативной памяти процессора. Первый этап загрузки обычно представляет собой небольшой образ, который помещается во внутреннюю память процессора. Этот образ инициализирует внешнюю оперативную память и загружает основное приложение из флэш-памяти во внешнюю оперативную память. Загрузка на первом этапе может выполнять дополнительные шаги, такие как переназначение вектора процессора или настройка блока управления памятью. Как только основное приложение загружено, загрузка первого этапа вызывает вектор сброса основного приложения.</p>

<p>Многоступенчатые сценарии загрузки усложняют модель запуска программы. Каждый этап загрузки технически представляет собой отдельную программу. Однако не каждый этап будет проходить через полный процесс запуска программы. Простым этапам загрузки может потребоваться только очистить раздел .bss для выполнения своих обязанностей, в то время как сложным загрузчикам требуется полностью инициализированная среда выполнения C/C++. Действия по запуску программы могут быть распределены по всему процессу загрузки, причем каждый этап выполняет определенные задачи.</p>

<h4>Запуск программы через ОС</h4>

<p>Самый сложный сценарий - это запуск программы на хост-машине с полноценной ОС.</p>

<p>Когда пользователь запускает программу, оболочка или графический интерфейс обращаются к средствам операционной системы. В Unix-подобных системах семейство exec заменяет образ текущего процесса новой программой; подготовку образа выполняют ядро и, при необходимости, динамический загрузчик. В Windows для создания нового процесса обычно используется CreateProcess. Это разные интерфейсы и последовательности действий, а не одна универсальная «функция загрузчика».</p>

<p>Загрузчики часто выполняют следующие действия:</p>

<ol>
	<li>Проверить разрешения</li>
	<li>Выделить место для стека программы</li>
	<li>Выделить место для кучи программы</li>
	<li>Инициализировать регистры (например, указатель стека)</li>
	<li>Вставка <code>argc</code>, <code>argv</code> и <code>envp</code> в стек программы.</li>
	<li>Сопоставление виртуальных адресных пространств</li>
	<li>Динамическое связывание</li>
	<li>Релокация</li>
	<li>Вызов функций предварительной инициализации</li>
</ol>

<p>После необходимой подготовки управление передаётся в точку входа образа программы; в рассматриваемом ELF-примере это _start.</p>
